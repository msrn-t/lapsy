## 1. 目的

app shell（LAP-014）の外側にある公開ページ群 — ランディング（`/`）・ログイン（`/login`）・招待受諾（`/invite/[token]`）・パスワードリセット要求/実行（`/password-reset`・`/password-reset/[token]`）— のレイアウトを各ワイヤーフレーム（docs/wireframes 00/13/01/02/03）のセンタリングカード型・グレースケールトークンへ整合させる。あわせて WF にあって現実装に欠けているフォーム要素を補完する:

- **招待受諾**: パスワード確認フィールド + 不一致エラー（確認欄直下）+ 強度メーター
- **リセット実行**: パスワード確認フィールド + 強度メーター
- **reset 系のブランド欠落補完**、4 公開ページ + ランディングの `dark:`/`red-*`/`gray-*` 撤去 → 既存 `@theme` トークン化

確認フィールド・強度メーターは**表示専用の UX 補助**であり、サーバー側の合格条件（8文字）・一様 ACK・遷移・lib 純関数のシグネチャは一切変えない（人間判断 U1-U4 に従う）。

## 3. 設計方針

### 3.0 採用する方針（まとめ）

1. **WF の `.auth-card` を Tailwind 写経**: 全認証ページを「センタリングラッパ + カード（ブランド → タイトル → 説明 → フォーム → フッター注記）」に統一する。login が既にこの形なので、それを基準形（`max-w-[420px]`・login は据え置きの実値・他ページは WF の `.auth-card` の `max-w-[380px]` を採用）として 4 ページ + ランディングに展開する。CSS の新規追加（globals.css 追記）はしない。
2. **トークン整合（`dark:` / 有彩色撤去）**: `dark:*` をすべて撤去し、`gray-*`/`red-*`/`blue-*` を §3.1 対応表で WF トークンへ置換する。エラー枠は WF `.form-error`/`.err-msg`（`border-dashed border-error` + `text-error`・単色）に寄せる。**login/login-form.tsx の gray-* もトークン化**する（チケット受け入れ条件「各公開ページのレイアウトが WF に整合」に含むため）。
3. **強度メーター・確認フィールドは表示専用（U1）**: パスワード文字列から weak/medium/strong を算出する純関数 `scorePasswordStrength` を `src/lib/password.ts` に**新設**（DB/bcrypt 非依存・node テスト対象）。メーターは **WF `.meter` の塗り幅 = 強度に応じて 33% / 66% / 100%** をクライアントで描画するのみ。**サーバー合格条件は 8 文字のまま**（`scorePasswordStrength` はゲートにしない）。確認一致も純関数 `passwordsMatch` を `src/lib/password.ts` に切り出し、クライアント検証で「不一致時は確認欄直下にエラー」を出すが**サーバーへは確認値を送らない/送っても無視**。
4. **client/server 分離の踏襲**: 強度メーター・確認フィールド・表示トグルはクライアント状態（入力中の再描画）が要るため、login と同じ `"use client"` + `useFormStatus` パターンの**子フォームコンポーネントを各ページに新設**する（`invite/[token]/_form.tsx`・`password-reset/[token]/_form.tsx`）。server action は親（server component）から prop で渡す（login と同型）。リセット要求・ランディングは静的なので client 化不要。
5. **サーバー契約の非変更**: `accept`/`resetPassword`/`requestReset` server action の入力契約は `formData.get("password")`・`formData.get("email")` のまま。確認フィールドは `name="passwordConfirm"`（任意）だが**サーバーは読み取らない**（送られても無視・最終防壁は既存の 8 文字検証 + DB 一意制約 + トークン検証）。
6. **純ロジックの単体テスト必須**: `scorePasswordStrength`・`passwordsMatch` を `password.test.ts`（node・新規 or 既存があれば追記）で網羅する（§9）。描画（DOM）テストは追加しない（vitest jsdom 未導入・scope 外）。

### 3.2 強度メーターの判定仕様（U1 確定・`scorePasswordStrength`）

WF の `.meter i{width:55%}` は固定ダミーであり強度基準は SPEC/WF に未定義。U1 により**表示専用の助言 UI** として以下を確定する（サーバー合格条件 8 文字とは独立）。

**入力**: `password: string`
**出力**: `PasswordStrength = "weak" | "medium" | "strong"`（実装内部で 0..4 のスコアを経由してもよいが、公開戻り値はこの 3 値）

**判定ロジック（長さ + 文字種多様性の合算スコア）:**
```ts
// src/lib/password.ts に追加（DB/bcrypt 非依存・node テスト対象）
export type PasswordStrength = "weak" | "medium" | "strong";

export function scorePasswordStrength(password: string): PasswordStrength {
  // 空文字は weak（メーターは塗り 0 相当でもよいが分類は weak）
  if (password.length === 0) return "weak";

  // 文字種の多様性（4 種: 小文字 / 大文字 / 数字 / 記号）
  let variety = 0;
  if (/[a-z]/.test(password)) variety++;
  if (/[A-Z]/.test(password)) variety++;
  if (/[0-9]/.test(password)) variety++;
  if (/[^A-Za-z0-9]/.test(password)) variety++;

  // 長さスコア（短い=0, 8 以上=1, 12 以上=2）
  const lengthScore =
    password.length >= 12 ? 2 : password.length >= 8 ? 1 : 0;

  const total = variety + lengthScore; // 0..6

  // 閾値: 弱 / 中 / 強
  if (total <= 2) return "weak";
  if (total <= 4) return "medium";
  return "strong";
}
```

**メーター塗り幅の対応（クライアント側の表示マップ・純ロジックではない）:**
| strength | 塗り幅 | クラス |
|---|---|---|
| weak | 33% | `w-1/3` |
| medium | 66% | `w-2/3` |
| strong | 100% | `w-full` |

> 強度は**ゲートにしない**: weak でもサーバーは 8 文字を満たせば受理する。メーターは「もっと強くできます」の助言に留め、`help-slot` に「8文字以上 / 強度メーターは目安です」を併記する。

### 3.3 確認一致判定（`passwordsMatch`）

```ts
// src/lib/password.ts に追加（純関数・node テスト対象）
export function passwordsMatch(a: string, b: string): boolean {
  return a === b;
}
```
- クライアント側で `password` 入力と `passwordConfirm` 入力を購読し、**両方に入力があり** `!passwordsMatch(pw, confirm)` のとき確認欄直下に「パスワードが一致しません」（`.err-msg` 相当）を出す。`confirm` が空のうちはエラーを出さない（入力途中の早出し防止）。
- 不一致のあいだは送信ボタンを `disabled` にして UX を補助してよい（任意・クライアントのみ）。ただし**サーバーは確認値を受け取らず 8 文字検証が最終防壁**であるため、JS 無効環境でも壊れない（確認なしで送信 → サーバーが password のみで処理）。

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| 強度をサーバー合格条件に組み込む（8文字超を強制） | U1・investigator Risk③ に反する。`MIN_*_PASSWORD_LENGTH=8`・既存テストと矛盾。表示専用に留める |
| 確認値をサーバーへ送りサーバーで一致検証 | サーバー契約（`password` 1 値）の拡張 = 後退リスク。投資効果が薄く Risk② に反する。クライアント補助 + 8 文字最終防壁で十分 |
| 強度メーターを共通 UI コンポーネント（`components/`）に切り出す | 公開ページ 2 箇所のみで、props 形状も微差。各 page の `_form.tsx` 内ローカルで十分。早すぎる抽象化を避ける（architect Constraints） |
| invite エラーを WF どおり一様着地に変更 | U3 で「現行の理由別表示を維持」と確定。LAP-003 の理由別 UX を後退させない |
| reset-perform で sessionVersion 失効を実装 | U4 で LAP-016 対象外と確定（LAP-005 系の別扱い）。WF 注記は実装しない |

## 4. 実装詳細（ページ別）

各ページ共通: 自前の `dark:*` と `gray-*`/`red-*`/`blue-*` を §3.1 でトークン化。`<main>` のセンタリングラッパは WF どおり `flex min-h-[80vh] flex-col items-center justify-center`（login の既存形）に統一。ブランドアイコンは login の既存 `BrandIcon`（水色 SVG）を踏襲する — WF はグレースケール仮だが、login が既に水色ブランドを使用しており公開ページ間で**ブランド表現を統一**するため login の `BrandIcon` 相当を reset 系にも展開する（WF のモノクロは「パス1の仮」であり、login が確立した水色ブランドが現行の正）。

### 4-1. ランディング `/`（00-index → src/app/page.tsx・U2）

**WF 構造**: 専用ランディング WF は無い（00 は索引）。U2 により「WF カード型・トークン整合でサービス説明 + ログイン誘導カード」を 00/13 の共通レイアウト規約（センタリングカード・グレースケール）に整合させて構成する。

**採用マークアップ**: `<main className="flex min-h-[80vh] flex-col items-center justify-center">` → 中に `.auth-card`（§3.1）。中身:
- ブランド（`BrandIcon` + 「Lapsy」+ sub「ラップで積み上げる、資格学習タイマー」）。
- サービス説明 `p`（現行文言「IT資格学習支援アプリ。…積み重ねていきます。」を `text-sm text-ink-dim` で）。
- ログイン誘導 = `.btn.block` 相当の `<a href="/login">ログイン</a>`（全幅・`bg-btn`）。
- 招待制注記（foot-note）「ご利用は招待制です。アカウントが必要な場合は管理者へご連絡ください。」。

**維持すべき不変条件**: server action なし（静的）。client 化不要。`dark:text-gray-400` 撤去。

### 4-2. ログイン `/login`（13_login → login/page.tsx + login-form.tsx）

**WF 構造**: ブランド → メール（個別エラースロット）→ パスワード（表示トグル）→ remember + リセットリンク（同一行）→ ログインボタン → 招待制注記。**構造は既に合致**（investigator）。本チケットでは**トークン整合のみ**。

**採用マークアップ**:
- `page.tsx`: カードを `rounded-2xl border-gray-300 bg-white p-8` → `rounded-card border border-line bg-card p-8`（`max-w-[420px]` 維持）。status/error バナーの `border-gray-300 bg-gray-50 text-gray-600` → `.ok-note` 系（`border-dashed border-line-2 bg-[#EDEDED] text-ink`）、error は `.form-error`（`border-dashed border-error text-error`）。ブランド word の `text-gray-700` → `text-ink`、sub `text-gray-500` → `text-ink-dim`。注記 `text-gray-500` → `text-ink-dim`。`BrandIcon`（水色 SVG）は据え置き。
- `login-form.tsx`: `inputBase` の `border-gray-400 bg-gray-50 text-gray-800 placeholder:text-gray-400 focus:*gray*` → §3.1 `.input`（`border-line-2 bg-fill text-ink placeholder:text-placeholder focus:border-line-strong`）。SubmitButton の `bg-gray-700 hover:bg-gray-800 text-white` → `bg-btn text-btn-ink hover:opacity-90`。トグルボタン `.eye` トークン化。remember チェック・リセットリンク `text-gray-700` → `text-ink`。**`name`（email/password/remember）・`useFormStatus`・トグル挙動は不変**。

**維持すべき server action / 遷移**: `authenticate`（`signIn("credentials", { redirectTo:"/dashboard" })`・失敗 `/login?error=1`）不変。`accepted`/`reset`/`error` の searchParams 分岐・文言不変。

### 4-3. 招待受諾 `/invite/[token]`（01 → invite/[token]/page.tsx + 新規 _form.tsx）

**WF 構造**: `.auth-card` 内 — ブランド → タイトル「アカウントを登録」→ desc → ①メール（ro 固定）→ ②パスワード（表示トグル + `.meter` + help「8文字以上 / 強度メーター」）→ ③パスワード確認（表示トグル + 不一致時 `.err-msg` を確認欄直下）→ ④登録ボタン → ⑤有効期限 72h 注記。無効リンクは別カードへ着地（理由別・U3 維持）。

**採用マークアップ（page.tsx・server component）**:
- 既存 `ErrorCard`（無効リンク）を `.auth-card` + ブランド + `.form-error` へトークン整合。**理由別 `ERROR_MESSAGES` は維持**（U3）。`text-blue-600` リンク → `.link`。
- 有効時は `<main>` センタリングラッパ + `.auth-card`（ブランド/タイトル/desc）。フォーム本体は**新規クライアントコンポーネント `<InviteAcceptForm action={accept} email={email} initialError={error} />`** に委譲。
- メール表示は readOnly `.input.ro`（`name` 不要・表示のみ。email はサーバーが招待レコードから固定するため hidden 不要）。

**追加フォーム要素（`invite/[token]/_form.tsx`・新規 client・login-form.tsx と同型）**:
- props: `action: (formData: FormData) => Promise<void>`（server action）、`email: string`、`initialError?: string`。
- state: `pw`（パスワード）、`confirm`（確認）、`showPw`/`showConfirm`（トグル）。
- `<fieldset disabled={pending} className="contents">`（`useFormStatus`）。
- パスワード入力 `name="password"` `type={showPw?"text":"password"}` `minLength={8}` `autoComplete="new-password"` → 直下に強度メーター（`scorePasswordStrength(pw)` → §3.2 塗り幅）+ `help-slot`「8文字以上 / 強度は目安です」。
- 確認入力 `name="passwordConfirm"`（**サーバーは読まない**）→ `confirm` が非空 かつ `!passwordsMatch(pw, confirm)` のとき `.input.error` + 直下 `.err-msg`「パスワードが一致しません」。
- 送信ボタン `.btn.block`（pending 中「登録中…」）。不一致中は `disabled`（任意の UX 補助）。
- `initialError`（`?error=weak_password` 等）は WF `.form-error` でフォーム上部に表示（既存 `ERROR_MESSAGES` を流用・`weak_password` は「8文字以上」）。

**維持すべき server action / lib / 遷移（不変）**: `accept` の `validateInvitePassword` → `$transaction`（再検証 + `user.create` + `updateMany pending→accepted`）→ `/login?accepted=1`。`evaluateInvitation`・`already_registered`(P2002) 写像・`AcceptFlowError` は不変。**確認値はサーバーに渡さない/渡しても無視**。自動 signIn しない（LAP-003 §3-E）。

### 4-4. リセット要求 `/password-reset`（02 → password-reset/page.tsx）

**WF 構造**: `.auth-card` 内 — **ブランド（現実装に欠落 → 補完）** → タイトル「パスワードをリセット」→ desc → ①メール → ②送信ボタン → ③「ログイン画面に戻る」link。送信後は `.ok-note` で一様 ACK。

**採用マークアップ**: `<main>` センタリングラッパ + `.auth-card`。**ブランド（`BrandIcon` + word + sub）を新規追加**。`h1`（`text-2xl font-bold`）→ `.auth-title`。desc トークン化。`sent` バナー `border-gray-300 bg-gray-50 …` → `.ok-note`（`RESET_REQUEST_ACK_MESSAGE` 文言不変）。メール入力 `.input` 化。送信ボタン `.btn.block`。「ログインページへ」`text-blue-600` → `.link`（WF 文言「ログイン画面に戻る」へ寄せてよい）。静的なので client 化不要。

**維持すべき不変条件（最重要）**: `requestReset` server action の**一様 ACK / 列挙対策を後退させない**（`isValidEmail` → `findUnique` → 存在時のみ発行+送信、存在有無に関わらず `redirect("/password-reset?sent=1")`）。`RESET_REQUEST_ACK_MESSAGE` 文言・`sent=1` 分岐・送信失敗時の応答不変（§3-G）。`name="email"` 不変。

### 4-5. リセット実行 `/password-reset/[token]`（03 → password-reset/[token]/page.tsx + 新規 _form.tsx）

**WF 構造**: `.auth-card` 内 — **ブランド（欠落 → 補完）** → タイトル「新しいパスワードを設定」→ desc → ①新パスワード（表示トグル + `.meter`）→ ②確認（表示トグル + 不一致 `.err-msg`）→ ③更新ボタン。無効トークンは別カードへ一様着地。

**採用マークアップ（page.tsx・server component）**:
- 既存 `ErrorCard`（無効リンク）を `.auth-card` + ブランド + `.form-error` へトークン整合。**`RESET_INVALID_LINK_MESSAGE` 一様化を維持**。`text-blue-600` → `.link`。
- 有効時は `<main>` + `.auth-card`（ブランド/タイトル/desc）→ フォーム本体を**新規 `<ResetPerformForm action={resetPassword} initialError={error} />`** に委譲。

**追加フォーム要素（`password-reset/[token]/_form.tsx`・新規 client・invite の _form と同型）**:
- props: `action`、`initialError?: string`。state: `pw`/`confirm`/`showPw`/`showConfirm`。
- 新パスワード `name="password"` `minLength={8}` `autoComplete="new-password"` → 強度メーター（`scorePasswordStrength`）+ help。
- 確認 `name="passwordConfirm"`（サーバー無視）→ 不一致時 `.err-msg`。
- `initialError`（`weak_password` → 「8文字以上」/ それ以外 → `RESET_INVALID_LINK_MESSAGE`）を `.form-error` で表示（既存分岐の文言を流用）。
- 更新ボタン `.btn.block`（pending「更新中…」）。

**維持すべき server action / lib / 遷移（不変）**: `resetPassword` の `validateNewPassword` → `$transaction`（再検証 + 条件付き used 化 + `user.update`）→ `/login?reset=1`。`evaluatePasswordResetToken`・一様 `?error=invalid_link`・`ResetFlowError` 不変。**sessionVersion 失効は実装しない（U4・対象外）**。確認値はサーバーに渡さない/無視。

### 4-6. 共通: ブランドコンポーネントの扱い

login の `BrandIcon`（page.tsx 内のローカル関数・水色 SVG）を reset 要求/実行・ランディングでも使う。**重複定義を避けるため、implementer は判断で `src/components/BrandIcon.tsx`（または `src/components/brand-logo` 既存があれば再利用）に切り出してよい**が、これは任意リファクタであり必須ではない（各ページにローカル複製でも受け入れ条件は満たす）。切り出す場合も SVG マークアップ・サイズ（login は 112px・WF は 52px 相当）は各ページ文脈に合わせ、login の見た目を後退させないこと。invite/reset の WF はブランド 52px なので reset 系・ランディングは `width/height` を 52〜56px 程度に。

git log --oneline
