# [LAP-013] ダッシュボードの期限日表示を JST 暦日へ統一（カウントダウン日数との TZ 不整合）設計

> このファイルはarchitectが生成・更新するチケット単位の設計書です。
> チケット LAP-013 に対応します。implementer・tester・reviewerが参照します。
> 1チケット = 1ファイル（`docs/designs/LAP-013.md` が常に現行）。改訂時は本ファイルを上書きし、
> チケットのログに改訂理由を残す。過去の設計はGitヒストリで追える（status等の状態は持たない）。

## 1. 目的

ダッシュボードのカウントダウン表示（`_charts.tsx` の `CountdownList`）で、期限日ラベルが UTC 日付（`toISOString().slice(0,10)`）、残り日数（`daysRemaining`/`isOverdue`）が JST 暦日（`toJstDateKey`）と、基準日のタイムゾーンが食い違っている。deadline が UTC 夕方〜夜（例 `2026-06-30T16:00:00Z` = JST 翌 01:00）のとき両者が最大 1 日ズレ、内部不整合に見える。LAP-011 reviewer 指摘 Medium の是正。期限日ラベルを JST 暦日へ揃え、残り日数と基準日を一致させる。

## 2. 現状

`CountdownList`（`_charts.tsx`）は期限日ラベルを UTC 日付で算出している。残り日数は集計側（`computeDeadlineCountdowns`）が `toJstDateKey` で JST 暦日基準に算出済みのため、ラベルだけが別基準になっている。

**現在のフロー:**
```
computeDeadlineCountdowns (aggregate.ts)
  ├─ daysRemaining / isOverdue ← toJstDateKey(deadline) 基準（JST 暦日）
  └─ deadline: Date をそのまま props で渡す
        ↓
CountdownList (_charts.tsx:233)
  deadlineKey = it.deadline.toISOString().slice(0,10)  ← UTC 日付（不整合の原因）
        ↓
  :250 「期限: {deadlineKey}」を描画
```

UTC 16:00Z（= JST 翌日 01:00）の deadline では、ラベルは UTC 当日、残り日数は JST 翌日基準となり 1 日ズレる。

**関連する既存ファイル:**
- `src/app/(protected)/dashboard/_charts.tsx`: 期限日ラベル算出・描画（`:233` / `:250`）。`@/lib/aggregate` から **type-only import のみ**（`:6-11`）
- `src/lib/aggregate.ts`: `toJstDateKey(date: Date): string`（`:29` export 済み・固定 +9h・`getUTC*` 読みでサーバ TZ 非依存）/ `computeDeadlineCountdowns`（残り日数の算出元）
- `src/lib/aggregate.test.ts`: 純関数テスト（`toJstDateKey` の JST 境界含む）。`_charts.tsx` は非参照

## 3. 設計方針

**採用する方針:**
- `_charts.tsx:233` の UTC 日付算出を、集計側と同一の純関数 `toJstDateKey(it.deadline)` へ置換する。
- `_charts.tsx` の import に値 import `toJstDateKey` を追加する（現状 type-only import のため別経路が必要）。型 import との統合は不可（型と値の混在は `import { type X, fn }` 形式が必要で可読性が落ちるため、**値 import を 1 行追加**する）。
- これによりラベルと `daysRemaining`/`isOverdue` が**同一関数（同一基準日）**で算出され、ズレが構造的に解消される。
- 変更は表示行 + import に閉じ、集計ロジック・型・他コンポーネントには手を入れない（LAP-011 の責務分離＝集計は純関数・`_charts.tsx` は描画のみ、を維持）。

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| 集計側（`computeDeadlineCountdowns`）で `deadlineKey: string` を算出し props で渡す | 変更範囲が `DeadlineCountdown` 型・集計関数・テストへ広がる。表示専用の派生値を集計に持ち込むのは責務逸脱。軽微修正の粒度を超える |
| `_charts.tsx` 内にローカルで JST 変換を再実装 | `toJstDateKey` の重複実装。基準日一致の構造的担保が崩れ、将来のオフセット変更で再びズレる |
| type import 行へ `toJstDateKey` を混在統合 | `import { type A, type B, fn }` 形式となり可読性低下。別行追加の方が差分が小さく明快 |

## 9. 受け入れ条件

チケット受け入れ条件との対応:

- [ ] `CountdownList` の期限日ラベルが JST 暦日（`toJstDateKey(it.deadline)`）で表示される（チケット条件 1）
- [ ] 期限日ラベルと `daysRemaining`/`isOverdue` の基準日が一致する。**双方が同一関数 `toJstDateKey` を使うことで構造的に担保**される（チケット条件 2）
- [ ] UTC 夕方〜夜の deadline（例 `2026-06-30T16:00:00Z`）でラベルと残り日数がズレない（チケット条件 3）。`toJstDateKey` の JST 境界（16:00Z 跨ぎ）は `aggregate.test.ts` の既存テスト（T-TZ-BOUNDARY 系）で検証済みであり、ラベルがその純関数を直接使うため**既存テスト + 構造的整合で担保**する
- [ ] `_charts.tsx` の `@/lib/aggregate` import に値 import `toJstDateKey` が追加されている
- [ ] 既存テストがすべて通過（`npm run test`）（チケット条件 4）
- [ ] `npm run build` / 型チェックが通る（チケット条件 5）
- [ ] topics 系ページ（スコープ外）に変更がないこと（差分が `_charts.tsx` のみ）

**テスト方針（コンポーネントテストの扱い）:**
- 新規コンポーネントテストは**追加しない**。理由: (a) `CountdownList` は純関数化したラベルを描画するだけの presentational コンポーネントで、ラベルの正しさは `toJstDateKey` の正しさに帰着する。(b) `toJstDateKey` の JST 境界は `aggregate.test.ts` で既にテスト済み。(c) ラベルと残り日数が同一関数を共有することで「ズレない」ことが**構造的に**保証される。MVP・軽微修正の文脈でテストインフラ（React コンポーネントテスト環境）を新設するコストは価値に見合わない。
- 受け入れ条件 3「ズレないことを確認できる」は、上記の (a)〜(c) ＝「`aggregate.test.ts` の既存 JST 境界テスト + ラベルが同一純関数を直接使う構造的整合」で代替的に満たす。reviewer は差分が `toJstDateKey(it.deadline)` 置換であることを確認すれば整合を判定できる。
