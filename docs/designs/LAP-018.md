## 1. 目的

ワイヤーフレームは「あえてグレースケール」で作成した仮デザインだったが、LAP-014〜017 の実装にそのグレースケールがそのまま固着した。用意済みブランドパレット（`docs/wireframes/lapsy_brand_color_palette.html`・スカイブルー #54C3F1 / サンイエロー #FFC93C 軸）に従い、`globals.css @theme` のデザイントークンと、トークンを経由しないハードコード配色を実ブランドカラーへ移行する。**機能・server action・認可・レイアウト・DOM 構造・既存テストのアサーションは変更せず、配色（＋カウントダウン緊急度の純粋な分類ロジック追加）のみを行う。**

加えて人間判断（チケット LAP-018 ログ 2026-06-22 17:31）により:
- **U2**: カウントダウン緊急度を **4 段化**（余裕≥15日 / 接近≤14日 / 緊急≤3日 / 超過<0）。`daysRemaining`/`isOverdue` から緊急度を分類する純関数を新設し単体テストを付ける（配色のみを超える軽いロジック追加を許可）。
- **U3**: 状態色（緊急度・ステート）は**色＋テキスト/形を併記**し「色を唯一の手段にしない」を守る。

## 3. 設計方針

### 3.0 採用する方針（まとめ）

1. **`@theme` の 2 層化（核 1）**: ① ブランドパレットの原色をパレット段命名の素トークン（`--brand-*`）で全色定義 → ② 既存の意味トークン `--color-*` がそれを `var(--brand-*)` で参照する。**意味トークン名は一切変えない**ので各ページは無改修で新配色になる。将来のパレット差し替えは①の値変更だけで完結する。
2. **意味トークンの割当を確定表で固定（核 2・U1）**: investigator 提案を土台に btn=Primary500（白文字コントラスト確保）・panel/fill の面色・nav-active=Primary100・`--color-line-strong` の用途分割を architect 裁量で確定（§3.2 / §3.3）。
3. **新設トークン（核 3）**: ステート（success/warning/info）・ヒートマップ 5 段・カウントダウン 4 段・アクセント（sun/coral）を②の意味トークン層に追加。命名規則は既存に倣い `--color-{用途}` / 段ありは `--color-{用途}-{段}`（§3.4）。`error` は既存トークン名を維持して値を #EF4B49 へ。
4. **ハードコード掃き出し（核 4）**: §3.5 の file 別対応表で、arbitrary 値（`bg-[#…]`）・`HEAT_STEPS[].bg`・conic-gradient/SVG stroke の直 hex を新旧トークン参照へ置換する。**DOM 構造・class 構成・ロジックは変えず、色の出所だけを差し替える。**
5. **カウントダウン 4 段化（核 4・U2）**: `daysRemaining`/`isOverdue` → 4 区分の純関数 `classifyDeadlineUrgency` を `aggregate.ts` に新設し node 単体テストを付ける。`CountdownList` は色トークン（`--color-due-*`）＋緊急度ラベル併記で 4 段表示（§3.6）。**DOM 構造は据え置き**（既存の `<li>` 階層・「期限超過」破線バッジの形は維持し、緊急度ラベルとバッジ枠/文字色のトークンを差し替え）。
6. **A11y（U3）**: ステート/緊急度は色のみに依存させない。カウントダウンは緊急度ラベル（「余裕/接近/緊急/超過」）＋既存の `D-n`/`+n` 数値で判別。ヒートマップは凡例＋`title` 属性（既存）で判別。隣接段の判別性に配慮（§3.7）。

### 3.1 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| 1 層のまま意味トークンの hex を直接ブランド色へ書き換える | パレット差し替え・横展開ができず受け入れ条件①未達。原色の再利用（同じ Primary500 を btn と info で使う等）が hex の重複コピーになる |
| 意味トークンをブランド命名へリネーム（例 `--color-primary`） | 全ページの `bg-*`/`text-*`/`var(--color-*)` 参照を改修＝DOM/クラス改変が広範に発生。不変条件（無改修反映）に反する。リネーム禁止 |
| `--color-line-strong` を分割せず進捗塗りに使い続ける | ブランド化で「枠」と「進捗主役色」が同色になり、枠が濃すぎ/塗りが弱すぎのどちらかに倒れる。用途分割が UI 品質と意味の明確化に必要 |
| カウントダウンを 2 段維持（超過色だけ更新） | 人間判断 U2 で 4 段化が確定済み |
| カウントダウン緊急度の閾値判定を `CountdownList`（描画層）にインライン | テスト不能。`aggregate.ts` の純関数方針（time/TZ 注入・node テスト）と不整合。純関数に切り出す |
| ヒートマップの段数/閾値を色と一緒に変更 | 段数(5)・時間境界はデータの意味（学習量）。色のみ差し替えが安全（investigator Risk③） |
| アクセント（sun/coral）を適用先が無いので新設しない | パレットの「達成/連続記録」用途は将来機能で使う。トークン定義のみ先行し語彙を確保する方が一貫（U4 で「適用先ゼロでも定義のみで可」と確定済み・§3.8） |
| ステート色の併記を省き色のみで状態表示 | U3「色を唯一の手段にしない」に反する。テキスト/形を併記 |

### 3.2 `--color-line-strong` の用途分割（核 2・Risk②の確定）

`--color-line-strong` を**意味で 2 つに分ける**。リネーム禁止のため既存名は残し（強枠線の用途として継続）、**進捗塗り用に新トークン `--color-progress` を新設**する。admin トグル ON も「進捗/オン状態の主役色」として `--color-progress` を使う。

| 旧 `line-strong` の用途 | 移行先 | 理由 |
|---|---|---|
| 強枠線（admin バッジ枠 `border-line-strong`・sidenav Admin バッジ枠・chip active 枠 `border-line-strong`） | **`--color-line-strong` を維持**（値は Primary600 #1B95CC のブランド境界色へ） | 「強い境界線」の意味は保持。ブランドの濃いめ境界色に寄せる |
| 進捗塗り（トピックバー fill `bg-line-strong`・移動平均折れ線 stroke・リング進捗・進捗バー fill・強度メーター fill） | **`--color-progress` 新設**（Primary500 #2BAEE8） | 「進捗の主役塗り」はブランド主役色。`bg-progress`/`var(--color-progress)` で参照 |
| admin トグル ON 背景（`bg-line-strong`） | **`--color-progress`**（Primary500 #2BAEE8） | 「オン/有効」の主役色として進捗色を流用（白アイコン/丸とのコントラスト確保） |

> 注: `--color-line-strong` を使う既存クラス `border-line-strong`（枠）はそのまま枠用に残る。進捗系の `bg-line-strong` を使っている箇所（`_charts.tsx:64,219` / `_timer.tsx:117,135` / `_password-form.tsx` メーター fill / `invite|password-reset _form` メーター fill / `admin/users:108` ON）は **`bg-progress` / `var(--color-progress)` へ置換**する。これは「クラス名の変更」だが DOM 構造・要素・ロジックは不変であり、配色の出所差し替えに該当する（実装は §3.5 の対応表に従う）。

### 3.3 意味トークン → パレット割当（確定表・核 2 / U1）

②層（既存意味トークン）の値を、①層の `var(--brand-*)`（§3.4 で定義）へ割り当てる。**トークン名は不変・参照だけ差し替え**。

### 3.4 ①パレット原色トークンの定義（核 1・`@theme`）

パレット HTML の全色を①層 `--brand-*` として定義する。命名はパレットのカテゴリ＋段に対応させる（差し替え時に HTML と 1:1 対応できる）。

```
/* ① ブランドパレット原色（移植元: docs/wireframes/lapsy_brand_color_palette.html）。
   パレット差し替えはこのブロックの値変更だけで完結する。 */
--brand-sky:            #54C3F1;  /* コアブランド: スカイブルー（= primary-400） */
--brand-sun:            #FFC93C;  /* コアブランド: サンイエロー（= yellow-400） */
--brand-snow:           #FFFFFF;  /* スノーホワイト（= surface） */

/* プライマリ（スカイブルー）スケール */
--brand-primary-50:     #EAF6FD;
--brand-primary-100:    #DDEFFB;
--brand-primary-200:    #B6E2F7;
--brand-primary-300:    #8AD3F4;
--brand-primary-400:    #54C3F1;  /* base */
--brand-primary-500:    #2BAEE8;
```

### 4.2 `classifyDeadlineUrgency`（核 4・U2）— `src/lib/aggregate.ts` に追加

**入出力仕様（純関数・DB/時刻非依存）:**
```ts
export type DeadlineUrgency = "safe" | "near" | "urgent" | "over";

/**
 * 期限までの JST 暦日差から緊急度を 4 区分に分類する純関数（LAP-018 U2）。
 * 入力は computeDeadlineCountdowns 由来の daysRemaining（暦日差・今日=0/明日=1/昨日=-1）。
 * 閾値の包含関係（境界の帰属を厳密に固定）:
 *   - over   : daysRemaining < 0           （= 超過・isOverdue と同義）
 *   - urgent : 0 <= daysRemaining <= 3      （当日・3日以内）
 *   - near   : 4 <= daysRemaining <= 14     （4〜14日）
 *   - safe   : daysRemaining >= 15          （15日以上）
 * パレット定義の「緊急≤3日 / 接近≤14日 / 余裕≥15日 / 超過<0」と一致。
 * 境界例: -1→over, 0→urgent, 3→urgent, 4→near, 14→near, 15→safe。
 */
export function classifyDeadlineUrgency(daysRemaining: number): DeadlineUrgency {
  if (daysRemaining < 0) return "over";
  if (daysRemaining <= 3) return "urgent";
  if (daysRemaining <= 14) return "near";
  return "safe";
}
```
- **配置**: `aggregate.ts`（`computeDeadlineCountdowns` の直後）。`DeadlineCountdown` は既に `daysRemaining`/`isOverdue` を持つので **既存型・既存関数の戻り値は変更しない**（後方互換・既存テスト不変）。`classifyDeadlineUrgency` は単独 export の追加関数。
- **入力**: `daysRemaining: number`（`isOverdue` は `daysRemaining < 0` と等価のため引数に取らない。`over` は `< 0` で判定）。`CountdownList` 側で `it.daysRemaining` を渡す。
- **整数前提**: `daysRemaining` は暦日差で常に整数（`dateKeyDiffDays` が `Math.round`）。非整数が来た場合も比較演算で安全に分類される（防御不要だがテストで負値/0/境界を網羅）。

## 10. Open Questions

- [ ] **Q1（要人間確認・ブロッカー候補）**: ボタン背景 `--color-btn` をパレット定義どおり **Primary500 #2BAEE8** にすると、白文字とのコントラスト比が ≈2.4:1 で WCAG AA(4.5:1) を満たさない。パレットは「500 = ボタン・白文字可」と明記しているが、これは AA 厳密ではなく「視認可能」レベルの指針と解釈される。**(a) パレット指針どおり Primary500 を採用（本設計の第一選択・実装可）** / **(b) AA 寄りに Primary600 #1B95CC（≈3.2:1）へ引き上げ** のどちらを採るか。tester のコントラスト実測結果と合わせて人間が最終確認すると安全。**実装は (a) で進めてよい**が、A11y を厳格運用する場合は (b) を選ぶ余地がある（implementer はまず (a)、reviewer/人間が AA 不足を重大と判断した場合のみ (b) へ）。
