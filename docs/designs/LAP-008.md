## 1. 目的

SPEC §4（Must: ポモドーロのラップ数カスタマイズ・ラップごとの個別 work/break 時間・ラップ作業時間 60 秒以上・休憩 0 秒許容・ラップ設定をプリセットとして保存し再利用）を実装する。本チケットの責務は「**ラップ構成（プリセット）の設定・管理**」であり、タイマー実行（StudySession 開始・状態復元・materialize）は LAP-009 のスコープ。

プリセットは `Preset` モデル（`config = [{workSec, breakSec}, ...]` 順序付き JSONB 配列）として個人ごとに管理し（§7.5 データ分離）、全クエリで認証セッション由来 userId をフィルタする。バリデーション・正規化ロジックは DB 非依存の純関数 `src/lib/preset.ts` に集約して単体テスト可能にする（§9）。

**スコープ外（本チケットで実装しない）:**
- タイマー実行（StudySession の作成・`presetSnapshot` への凍結・状態復元・materialize）は **LAP-009**。本チケットは「LAP-009 が再利用する config 型 `LapConfig` を共有エクスポート」するところまで（結合点の準備）に留める。
- プリセット選択 UI をタイマー画面へ組み込む処理（ラン開始フロー）は LAP-009。本チケットは `/dashboard/presets` 配下の CRUD（一覧・作成・編集・削除）のみ。
- ラップ実行中の集計・記録（StudyRecord 生成）は LAP-009/011。

## 2. 現状

LAP-002 で認証・データ分離基盤（`requireUserId()` / 二層保護 / Server Component + server action + ResultBanner パターン）が確立済み。LAP-006 でトピック CRUD の最新パターン（純関数 `src/lib/topic.ts` + `*.test.ts`、`/dashboard/topics` 配下の page.tsx 同居 server action、`ResultBanner` + `revalidatePath` + `redirect("?result=...")`）が整備済み。本チケットはこのパターンをそのまま `preset` に横展開する。

investigator 調査（2026-06-22）の要点:

- **`Preset` モデルは init マイグレーションで確定済み**（`prisma/schema.prisma` L308-318 / `prisma/migrations/20260620172038_init/migration.sql`）。フィールド: `id`(cuid) / `userId` / `name`(String) / `config`(Json=JSONB) / `createdAt` / `updatedAt`。SPEC §7.6 ドラフトと完全一致。
- `config` は**単一 JSONB カラム**（別テーブルではない）。構造は `[{ "workSec": 1500, "breakSec": 300 }, ...]`（順序付き配列でラップごとの個別 work/break を表現）。
- `User.presets Preset[]` リレーション（schema L250）。FK は `onDelete: RESTRICT`（Prisma 既定）、`@@index([userId])` あり。**したがってスキーマ変更・新規マイグレーションは一切不要**。本チケットはアプリ層（純関数 + server action + UI）のみで完結する。
- 認証・データ分離（§7.5）: 全クエリで `where: { userId }` を必須。更新/削除は `updateMany`/`deleteMany({ where: { id, userId } })` の `count === 0` を `not_found` に一様化（行の存在有無を漏らさない）。一般ユーザー機能なので `requireUserId()` を使う（`requireAdmin*` ではない）。
- 配置先（慣習）: `src/app/(protected)/dashboard/presets/` 配下。`(protected)` は edge 層（`auth.config`）+ ページ/action 冒頭 `requireUserId()` の二層保護。
- テスト慣習: Vitest（`npm test` = `vitest run`）。対象の隣に `*.test.ts` 併置（例 `src/lib/topic.test.ts`）。純関数を境界値まで網羅。

**後続 LAP-009 との結合点:**
- `StudySession.presetSnapshot Json`（schema L326）は「開始時に凍結した `[{workSec, breakSec}, ...]`」で **`Preset.config` と同一構造**。LAP-009 は `preset.config` をそのまま `presetSnapshot` へコピー（スナップショット化）すればよい。よって config のラップ要素型 `LapConfig = { workSec: number; breakSec: number }` を本チケットで `src/lib/preset.ts` に確定・共有エクスポートしておく。

## 3. 設計方針

**採用する方針:**

1. **プリセット CRUD は `/dashboard/presets` 配下に置く**（edge 保護を継承）。一覧 + 作成を `presets/page.tsx`、編集を `presets/[id]/edit/page.tsx` に置く。削除は一覧画面の `<form action={deletePreset}>` から実行する。各ページ・各 server action の冒頭で `requireUserId()` を呼び、node 層でも認証・データ分離を再評価する（二層防御）。LAP-006 の topics と同一構成。

2. **バリデーション・正規化は DB 非依存の純関数として `src/lib/preset.ts` に切り出す**（既存慣習・テスト容易性・LAP-009 が再利用できる共有型の置き場）。隣に `src/lib/preset.test.ts` を置く。
   - 共有型 `LapConfig = { workSec: number; breakSec: number }` をエクスポートする（LAP-009 が `presetSnapshot` 型として再利用）。
   - `validatePresetInput(input)`: `name` と `config`（ラップ配列）を検証・正規化する。フォーム由来の生入力（文字列・unknown）を受け取り、成功時は DB にそのまま書ける正規化値 `{ name: string; config: LapConfig[] }` を、失敗時は理由コードを返す。

3. **`config`（JSONB）はランタイムに型保証が無いため、保存前に純関数で厳密検証し、読込後も信頼しない方針を徹底する。**
   - 書き込み前: `validatePresetInput` を通った正規化済み `LapConfig[]` のみを `prisma.preset.create/update` に渡す。フォームの未知入力を直接 JSON 化して保存しない。
   - 読み込み後: DB から取得した `config`（型は Prisma 上 `JsonValue`）は信頼せず、UI 表示・LAP-009 でのスナップショット化の前に `parsePresetConfig`（後述・防御的パーサ）で `LapConfig[]` へ narrowing する。不正なら空配列または UI で「壊れた設定」として扱える形で返す（本チケットは UI 表示にのみ用い、編集画面のプリフィルで活用する）。

4. **データ分離は `requireUserId()` の戻り値のみを userId として使う**（§7.5）。
   - 一覧取得: `prisma.preset.findMany({ where: { userId }, orderBy: [{ createdAt: "desc" }] })`。
   - 編集対象の取得: `prisma.preset.findFirst({ where: { id, userId } })`（クライアント入力 `id` を単独で信頼しない。`null` → `not_found`）。
   - 更新/削除: `prisma.preset.updateMany`/`deleteMany({ where: { id, userId } })` を用い、`count === 0` を「対象なし or 他人の行」として一様に `not_found` 扱い（行の存在有無を漏らさない）。

5. **作成・編集・削除はすべて薄い server action パターン**にする。`<form action={...}>` → `requireUserId()` → （CR/U は）`validatePresetInput` → DB 反映 → `revalidatePath("/dashboard/presets")` → `redirect("?result=...")` → `ResultBanner`。バリデーション失敗時は DB に触れず結果コードで通知する。`Preset` は FK 子（参照する側のモデル）を持たないため、LAP-006 の `P2003`/TOCTOU フォールバックは**不要**（削除は単純な物理削除でよい）。

6. **フォームからの config 入力形式（implementer 裁量の許容範囲を限定）**: ラップ配列はフォームでは「ラップ行ごとの workSec/breakSec」をインデックス付きフィールド（例 `lap[0].workSec` 相当の命名、または `workSec` を name 重複で複数送る形）で受け取る。`validatePresetInput` は **生の文字列配列／unknown を受け取る前提**で書き、パースと検証を純関数内に閉じる（UI の入力エンコード方式が変わってもロジックを再利用できる）。分単位入力（分→秒変換）にするか秒直接入力にするかは UI 裁量だが、**純関数へ渡す時点では秒（Int）に統一**する。

**バリデーション規則（本設計で確定。SPEC 明示なき上限は LAP-006 の `MAX_TITLE_LENGTH=200` 前例にならい設計書で固定しテストで担保）:**

| 項目 | 規則 | 由来 |
|---|---|---|
| `name` | trim 後 1 文字以上（必須）、`MAX_PRESET_NAME_LENGTH = 200` 文字以下 | LAP-006 前例（SPEC 明示なし→200 固定） |
| `config` 要素数（ラップ数） | `1 <= 要素数 <= MAX_LAPS = 20`（空配列拒否＝最低1ラップ） | SPEC §4「ラップ数カスタマイズ」/ 空拒否は妥当・上限は暴走防止 |
| `workSec`（各ラップ） | 整数、`MIN_WORK_SEC = 60 <= workSec <= MAX_WORK_SEC = 14400`（4時間） | SPEC §4/§7.3（60 秒以上必須）/ 上限は §7.3 の 3 時間キャップに余裕を持たせた値 |
| `breakSec`（各ラップ） | 整数、`0 <= breakSec <= MAX_BREAK_SEC = 14400`（4時間、0 許容） | SPEC §4（0=休憩なし許容）/ 上限は work と対称に設定 |
| 整数性 | `workSec` / `breakSec` は `Number.isInteger` を満たすこと（小数・NaN・非数値文字列を拒否） | フォーム由来文字列のパース防御 |

**エラーコード（`validatePresetInput` の失敗 reason・ResultBanner 文言化）:**

| reason | 条件 |
|---|---|
| `name_required` | `name` trim 後 0 文字 |
| `name_too_long` | `name` が `MAX_PRESET_NAME_LENGTH` 超過 |
| `empty_config` | ラップ配列が空（最低1ラップ必須） |
| `too_many_laps` | ラップ数が `MAX_LAPS` 超過 |
| `lap_work_too_short` | いずれかのラップの `workSec < MIN_WORK_SEC`（60 秒未満） |
| `lap_work_too_long` | いずれかのラップの `workSec > MAX_WORK_SEC` |
| `break_negative` | いずれかのラップの `breakSec < 0` |
| `break_too_long` | いずれかのラップの `breakSec > MAX_BREAK_SEC` |
| `invalid_number` | `workSec`/`breakSec` が整数にパースできない（NaN・小数・空・非数値） |

> 検証順は「name → config 空/上限 → 各ラップを先頭から走査し最初に違反したコードを返す」。各ラップ走査内は `invalid_number`（パース不能）→ `lap_work_too_short`/`lap_work_too_long`/`break_negative`/`break_too_long` の順。検証順序はテストで固定する。

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| `config` を別テーブル（`PresetLap`）に正規化 | スキーマ変更・マイグレーション要。SPEC §7.6 は JSONB 配列で確定済み。`presetSnapshot`（§7.1）も同一 JSONB 構造で結合が滑らか。正規化のメリットなし |
| バリデーションを server action 内にインライン展開 | DB 非依存の単体テスト（§9）が書けない。LAP-006 の純関数分離パターンに反する。LAP-009 へ共有型を渡す置き場も失う |
| 読込後 `config` を `as LapConfig[]` で素通り信頼 | JSONB はランタイム型保証が無く、過去データ・手動変更・スキーマ進化で壊れ得る。防御的 `parsePresetConfig` で narrowing（§3-3） |
| ラップ数・秒数に上限を設けない | 暴走入力（巨大配列・非現実的秒数）で UI/集計が破綻。SPEC 明示は無いが LAP-006 前例にならい設計書で固定・テスト担保 |
| 削除で `P2003`/TOCTOU フォールバックを実装 | `Preset` は他モデルから FK 参照されない（子を持たない）ため物理削除は常に成功。LAP-006 固有の論点で不要 |
| `MAX_PRESET_NAME_LENGTH` を独自値に | LAP-006 の `MAX_TITLE_LENGTH=200` と揃え、システム全体の一貫性を優先（200 採用） |

**主要なインターフェース（型・I/F 素案。実装は implementer）:**
```typescript
// src/lib/preset.ts — DB 非依存の純ロジック / LAP-009 共有型の置き場

export const MAX_PRESET_NAME_LENGTH = 200;          // name 上限（LAP-006 前例に合わせ 200）
export const MAX_LAPS = 20;                          // ラップ数上限（暴走防止・SPEC 明示なし→固定）
export const MIN_WORK_SEC = 60;                      // ラップ作業時間の下限（SPEC §4/§7.3）
export const MAX_WORK_SEC = 14400;                   // 作業時間の上限（4h・§7.3 3hキャップに余裕）
export const MAX_BREAK_SEC = 14400;                  // 休憩時間の上限（4h・work と対称、0 許容）

// ラップ1要素。Preset.config / StudySession.presetSnapshot（LAP-009）で共有する正規化済み構造。
export type LapConfig = { workSec: number; breakSec: number };

// フォーム由来の生入力（パース前）。workSec/breakSec は文字列または数値を許容。
export type PresetInput = {
  name: string;
  laps: ReadonlyArray<{ workSec: string | number; breakSec: string | number }>;
};

export type PresetValidationReason =
  | "name_required"
  | "name_too_long"
  | "empty_config"
  | "too_many_laps"
  | "lap_work_too_short"
  | "lap_work_too_long"
  | "break_negative"
  | "break_too_long"
  | "invalid_number";

export type PresetValidationResult =
  | { ok: true; value: { name: string; config: LapConfig[] } }
  | { ok: false; reason: PresetValidationReason };

// 入力検証 + 正規化（§3-2,3-3）。成功時は DB にそのまま書ける { name, config } を返す。
// 検証順: name → config 空/上限 → 各ラップを先頭から走査（invalid_number→work下限→work上限→break負→break上限）。
export function validatePresetInput(input: PresetInput): PresetValidationResult;

// 読込後の防御的パーサ（§3-3）。DB の JsonValue を信頼せず LapConfig[] へ narrowing する。
// 不正な要素は除外、全体が不正なら空配列。UI 表示・編集プリフィル用（保存には validatePresetInput を使う）。
export function parsePresetConfig(raw: unknown): LapConfig[];
```
```typescript
// server action の結果コード（ResultBanner で文言化）
type PresetResultKind =
  | "created" | "updated" | "deleted"
  | "name_required" | "name_too_long"
  | "empty_config" | "too_many_laps"
  | "lap_work_too_short" | "lap_work_too_long"
  | "break_negative" | "break_too_long" | "invalid_number"
  | "not_found";          // 対象なし or 他ユーザーの行（区別せず一様・§7.5）
```

**処理フロー:**

A. 作成（createPreset）
```
1. requireUserId() で userId を確定（未認証は /login へ）
2. FormData から name と各ラップの workSec/breakSec を取得し PresetInput に組み立てる
3. validatePresetInput → 失敗なら redirect("/dashboard/presets?result=<reason>")（DB に触れない）
4. prisma.preset.create({ data: { userId, name, config: value.config } })
   - config は正規化済み LapConfig[] を JSON として保存
5. revalidatePath("/dashboard/presets") → redirect("?result=created")
```

B. 編集（updatePreset / presets/[id]/edit/page.tsx）
```
1. ページ表示: requireUserId() → prisma.preset.findFirst({ where:{ id, userId } })
   - null → not_found（プリフィル不可）。config は parsePresetConfig で LapConfig[] へ narrowing しフォームへ
2. updatePreset action: requireUserId() → FormData から id/name/laps 取得
3. validatePresetInput → 失敗なら ?result=<reason>
4. prisma.preset.updateMany({ where:{ id, userId }, data:{ name, config } })
   - count === 0 → ?result=not_found（他人の行 or 不在を一様に扱う・データ分離）
5. revalidatePath → ?result=updated
```

C. 削除（deletePreset）
```
1. requireUserId() で userId 確定
2. FormData から id 取得
3. prisma.preset.deleteMany({ where:{ id, userId } })
   - count === 0 → ?result=not_found
   （Preset は FK 子を持たないため P2003/TOCTOU フォールバックは不要・§3-5）
4. revalidatePath → ?result=deleted
```

D. 一覧表示（presets/page.tsx）
```
1. requireUserId() → userId
2. const presets = await prisma.preset.findMany({
     where: { userId },              // ← データ分離（§7.5）
     orderBy: [{ createdAt: "desc" }],
   });
3. 各 preset の config は parsePresetConfig で narrowing し「ラップ数・各 work/break」を要約表示
4. 作成フォーム + 各プリセットの編集/削除フォーム + ResultBanner を描画
```

**ResultBanner の文言（要点・implementer 文面裁量）:**
- 成功（`created`/`updated`/`deleted`）は緑バナー、それ以外は赤バナー（LAP-006 と同一スタイル）。
- `name_required`: 「プリセット名は必須です。」 / `name_too_long`: 「プリセット名が長すぎます。」
- `empty_config`: 「ラップを最低1つ設定してください。」 / `too_many_laps`: 「ラップ数が多すぎます（上限 20）。」
- `lap_work_too_short`: 「ラップの作業時間は60秒以上に設定してください。」
- `lap_work_too_long` / `break_too_long`: 「設定時間が長すぎます。」 / `break_negative`: 「休憩時間に負の値は設定できません。」
- `invalid_number`: 「作業時間・休憩時間は整数（秒）で入力してください。」
- `not_found`: 「対象のプリセットが見つかりませんでした。」

## 6. リスク

| リスク | 深刻度 | 軽減策 |
|---|---|---|

## 7. マイグレーション戦略

**マイグレーション不要（Preset は init 既存・スキーマ不変）。**

- `Preset` モデル（`id/userId/name/config(Json)/createdAt/updatedAt`・`@@index([userId])`・FK `onDelete RESTRICT`）は init マイグレーション（`20260620172038_init`）で適用済みで、SPEC §7.6 と一致。
- 本チケットはフィールド追加・削除・FK 変更を一切行わない。`config` の構造（`[{workSec, breakSec}, ...]`）はアプリ層の純関数で検証・正規化するのみで、DB スキーマには現れない（JSONB のまま）。
- よって `prisma/schema.prisma` および `prisma/migrations/` は本チケットで一切変更しない。`npm run prisma:validate` は現状のまま通る想定。

## 8. ロールバック戦略

本チケットは新規ファイル追加（純関数 + 2 ページ）のみで、schema/migration を触らないため、コミット単位の revert で完全に原状回復できる。DB 側のロールバックは不要。

```bash
git log --oneline
git revert <コミットハッシュ>
# 例: [LAP-008][REVERT] プリセット設定機能の取り消し
```
- マイグレーションが無いため DB reset は不要。
- 既に保存済みの `Preset` 行（あれば）は revert 後も残るが、`config` 構造は SPEC §7.6 準拠なので後続再導入時もそのまま利用できる。
- CLAUDE.md ロールバック規約に従い、done/→active/ 戻し・status を implementation_done に戻す運用は orchestrator が担当。
