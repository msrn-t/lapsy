## 1. 目的

SPEC §4(Should) のパスワードリセット機能を実装する。ログイン前のユーザーがメールアドレスを指定すると、有効期限付きのリセットトークンを発行してリセットメール（Resend）を送り、メール内リンクから新しいパスワードを設定できるようにする。SPEC §5（トークンに有効期限を設定 / パスワードは bcrypt でハッシュ化）・§7.6（`PasswordResetToken` モデル）に従う。

担保すること:

- メールアドレス指定でのリセット要求（要求＝トークン発行＋送信）
- リセットトークンの有効期限（短命・1時間。§5 / §3-B）と単一使用（`usedAt`）
- リンクからの新パスワード設定（bcrypt ハッシュで `User.passwordHash` 更新）
- 使用済み・期限切れ・不正トークンの一様なエラー処理（情報漏洩防止）
- ユーザー存在有無を露呈しない列挙対策（要求は常に同一成功応答）
- トークン生成・検証ロジックの単体テスト（SPEC §9）

本チケットは LAP-002（認証基盤・bcrypt）と LAP-003（Resend `Mailer` 抽象）に依存し、`prisma` / `hashPassword` / `getMailer()` / 公開ルートの仕組み・列挙対策の思想を再利用する。LAP-003 招待フローのパターンをほぼ 1:1 で踏襲する。

## 3. 設計方針

### 3-A. トークンの保存方式 — sha256 ハッシュで DB 保存（人間確定方針）

**採用案: 生トークン（256bit 乱数）をメールのリセット URL にのみ載せ、DB の `PasswordResetToken.token` 列には生トークンの sha256 ハッシュを保存する。** 招待（平文 `@unique` 保存）とは異なる方式を本機能でのみ採用する。

理由・整合性:

- **堅牢化**: パスワードリセットはアカウント乗っ取りに直結する高権限操作。DB やバックアップ・ログが漏洩しても、保存されているのはハッシュのみで生トークンは復元できない（リセット URL を踏める時間窓を奪われない）。
- **スキーマ変更なしで両立**: `token` 列はハッシュ済みの 64 文字 hex を格納するだけなので `@unique` 制約・`findUnique({ where: { token } })` の O(1) lookup はそのまま使える。検証時は受領した生トークンを sha256 して同じ列で lookup する。**スキーマ・マイグレーションの変更は一切不要**（招待の平文方式が `@unique` lookup を要求するのと同じ仕組みを、格納値だけハッシュに替えて使う）。
- **bcrypt との役割分担を明記**: bcrypt はユーザーのパスワード保存用（低速・ソルト付きで総当たり耐性が必要）。リセットトークンは sha256（高速・ソルト不要）で十分 — トークン自体が 256bit の高エントロピー乱数のため辞書/総当たり攻撃が成立せず、短命（1時間）かつ単一使用で失効するため、低速ハッシュの保護を必要としない。「パスワード=bcrypt / 高エントロピートークン=sha256」という分担を設計の不変条件とする。
- **純関数化**: sha256 化を `hashResetToken(raw: string): string` として `src/lib/password-reset.ts` に純関数で切り出し、単体テスト可能にする（既知入力→既知 hex を固定値で検証）。

**代替案と却下理由（§3-A）:**
| 案 | 却下理由 |
|---|---|
| 平文保存（招待 LAP-003 踏襲） | スキーマ変更不要という利点はあるが、リセットは権限昇格に直結し漏洩時の被害が招待より重い。人間が「sha256 ハッシュ保存」を確定方針として指定。sha256 でも `@unique` lookup は維持できるため平文を選ぶ理由がない |
| bcrypt でトークンをハッシュ | bcrypt は出力にソルトを含み毎回値が変わるため `@unique` での O(1) lookup ができず（全件照合が必要）スキーマ整合が崩れる。トークンは高エントロピー乱数で低速ハッシュ不要 |

### 3-B. 有効期限（1時間）と単一使用

- **有効期限**: SPEC §5 は「有効期限を設定」とのみ規定し具体値なし。リセットトークンは乗っ取りリスクを抑えるため短命が定石。**`RESET_TOKEN_TTL_MINUTES = 60`（1時間）** を定数で確定し、発行時 `expiresAt = now + 60分` とする。期限計算は純関数 `computeResetExpiry(now)` に切り出す（招待 `computeExpiry` と同型）。
- **単一使用**: 一度使用したトークンは `usedAt` をセットして無効化する。検証は **`usedAt == null` かつ `expiresAt > now`** を要求する。境界 `expiresAt <= now` は期限切れ（招待 `evaluateInvitation` と同じく `<= now` を無効とする）。
- **使用時の原子化**: リセット実行は `prisma.$transaction` 内で「条件付き used 化 ＋ パスワード更新」を原子的に行う（招待受諾の原子化パターン踏襲）。
  - `passwordResetToken.updateMany({ where: { token: hashed, usedAt: null }, data: { usedAt: now } })` の `count === 0` なら「既に使用済み or 不正」として中断（二重使用防止の最終防壁）。
  - 続けて `user.update({ where: { id: userId }, data: { passwordHash } })`。
  - `expiresAt > now` の判定はトランザクション内で再取得したレコードに対し純関数 `evaluatePasswordResetToken` で再検証する（TOCTOU を狭める）。

### 3-C. 列挙対策（ユーザー存在の非露呈）

- **リセット要求は、メールアドレスの存在有無に関わらず常に同一の成功応答を返す**（定石）。
  - 存在する場合のみ実際にトークンを発行してメールを送信する。存在しない場合は何もしないが、応答メッセージは共通化する（例:「入力されたメールアドレスが登録されている場合、リセット用リンクを送信しました。」）。
  - これによりレスポンスからアカウントの存在/非存在を判別できない（招待送信が「既に登録済み」を明示するのとは逆 — 招待は管理者向けで列挙対策不要、リセットは未認証公開機能のため列挙対策が必須）。
  - 一様応答の文言を生成する薄い純関数 / 定数（`RESET_REQUEST_ACK_MESSAGE`）を 1 箇所に定義し、存在分岐に関わらず同一の文字列を返すことをコードレベルで保証する。
- **タイミング差**: 過度な最適化（ダミー bcrypt 実行等）は本 MVP では行わない。要求フローでは存在時のみ送信し、応答は共通化するに留める（送信の有無による多少の時間差は許容範囲とし、設計のブロッカーにしない）。bcrypt はリセット要求では走らない（パスワード更新は実行フローのみ）ため、要求の時間差は主に DB lookup + メール送信の有無に限られる。
- **エラー処理の一様化（実行フロー）**: 使用済み / 期限切れ / 不正（不在）トークンは区別せず一様な「リンクが無効または期限切れです」応答にする（理由を明示すると、有効なトークンの存在推測やトークン総当たりのフィードバックになるため）。内部的には `evaluatePasswordResetToken` が理由種別を返すが、**画面表示は単一の汎用メッセージに集約する**（招待は理由別に出し分けるが、リセットは情報漏洩防止のため一様化する点が招待との相違）。

### 3-D. 既存未使用トークンの扱い（再発行時の無効化）

**採用案: 新規発行時、同一ユーザーの既存の未使用トークン（`usedAt == null`）をすべて used 化してから新規トークンを発行する。**

- リセット要求を複数回送ると、古いリンクと新しいリンクが同時に有効になり、攻撃面が広がる。新規発行時に既存の未使用トークンを `usedAt = now` で一括無効化することで、**常に「有効なリセットリンクは最新の 1 本のみ」** という不変条件を保つ。
- 物理削除（DELETE）ではなく used 化を選ぶ理由: `usedAt` 列が既に単一使用無効化の意味を持ち、監査的に「いつ無効化されたか」が残る。`onDelete: Cascade`（User 削除時）には影響しない。
- 発行は `$transaction` 内で「既存未使用の一括 used 化 → 新規 create」を原子化する（途中失敗で古いトークンだけ無効化される/二重に有効になる状態を防ぐ）。
- 列挙対策との整合: この無効化＋発行はユーザーが存在する場合のみ実行する。存在しない場合は何もしない（応答は §3-C で共通化）。

**代替案と却下理由（§3-D）:**
| 案 | 却下理由 |
|---|---|
| 既存トークンを放置（多重有効を許容） | 古い未使用リンクが期限内なら有効なまま残り、攻撃面が広がる。最新 1 本に絞る方が安全 |
| 既存トークンを DELETE | 無効化の事実（時刻）が履歴に残らない。`usedAt` 埋めで十分・意味が一貫する |

### 3-E. リセット要求フロー（`/password-reset` メール入力）

- **配置**: `src/app/password-reset/page.tsx`（`(protected)` の外＝公開）。メールアドレス入力フォーム + server action。
- **処理**（server action `requestReset(formData)`）:
  1. `email = normalizeEmail(formData.email)`。`isValidEmail` で形式チェック（不正でも列挙を避けるため、原則は一様 ack を返す。明らかな空/形式不正のみフォームエラーにするかは実装で判断・ack 寄せを既定とする）。
  2. `const user = await prisma.user.findUnique({ where: { email } })`。
  3. `user` が存在する場合のみ `$transaction` で:
     a. 既存未使用トークンを一括 used 化（§3-D）。
     b. `const raw = generateResetToken()`（256bit 生トークン）。
     c. `const hashed = hashResetToken(raw)`。
     d. `passwordResetToken.create({ data: { token: hashed, userId: user.id, expiresAt: computeResetExpiry(now) } })`。
  4. （コミット後・存在時のみ）`getMailer().sendPasswordReset({ to: email, resetUrl: buildResetUrl(baseUrl, raw) })`。**URL には生トークン `raw` を載せる**（DB はハッシュ）。
  5. 存在有無に関わらず **同一の ack 応答へ** redirect（`/password-reset?sent=1` 等）。
  - 送信失敗時のハンドリング（§3-G）はユーザー存在を露呈しない範囲で行う。

### 3-F. リセット実行フロー（`/password-reset/[token]` 新パスワード設定）

- **配置**: `src/app/password-reset/[token]/page.tsx`（公開）。GET で検証、POST で更新。
- **GET（ページ表示）**:
  1. URL の生トークン `raw` を `hashResetToken(raw)` で hex 化。
  2. `const rec = await prisma.passwordResetToken.findUnique({ where: { token: hashed } })`。
  3. `const check = evaluatePasswordResetToken(rec, new Date())`。
  4. 無効（`not_found` / `used` / `expired` いずれも）→ **一様な「リンクが無効または期限切れ」エラー画面**（理由を出し分けない・§3-C）。
  5. 有効 → 新パスワード設定フォームを表示。
- **POST（実行・server action `resetPassword(formData)`）**:
  1. `const pw = String(formData.password)`。`validateNewPassword(pw)`（8 文字以上・招待の `validateInvitePassword` 同型）。不正ならフォームエラー再表示。
  2. `const hashed = hashResetToken(raw)`。
  3. `prisma.$transaction(async (tx) => { ... })`:
     a. `tx.passwordResetToken.findUnique({ where: { token: hashed } })` を再取得し `evaluatePasswordResetToken(rec, now)` で再検証（無効なら throw → 一様エラー）。
     b. `const passwordHash = await hashPassword(pw)`（bcrypt）。
     c. **条件付き used 化**: `tx.passwordResetToken.updateMany({ where: { token: hashed, usedAt: null }, data: { usedAt: now } })`。`count === 0` なら二重使用として throw（一様エラー）。
     d. `tx.user.update({ where: { id: rec.userId }, data: { passwordHash } })`。
  4. 成功 → `/login?reset=1`（成功メッセージ付き）へ redirect。自動 signIn はしない（招待 §3-E と同思想・login server action を再利用させる）。

### 3-G. メール送信抽象・送信失敗ハンドリング

- `Mailer` interface に `sendPasswordReset({ to, resetUrl }): Promise<MailerResult>` を追加し、`ResendMailer`（件名・本文をリセット用に）と `NoopMailer`（`resetUrl` をログ）に実装する。`getMailer()` は変更不要（戻り値の型が広がるだけ）。
- 件名・本文は招待（`invitationText/Html`）と同型で `passwordResetText/Html(resetUrl)` を新設。本文に「心当たりがなければ破棄」「有効期限1時間」を明記する。
- **送信失敗**: 招待同様、レコードは既にコミット済み。送信失敗時はサーバーにログを残しつつ、**ユーザーへは一様 ack（§3-C）を返し続ける**（送信成否でレスポンスを変えるとユーザー存在/メール到達性を露呈しうるため）。失敗の可視化は内部ログにとどめ、ユーザー向けには「届かない場合は時間をおいて再度お試しください」程度の汎用文言に寄せる。明示的な再送 UI は本チケットのスコープ外（後続 UX）。

### 採用方針サマリ

**採用する方針:** トークンは `crypto.randomBytes` 256bit を生成し **sha256 ハッシュで `@unique` 保存**（生トークンはメール URL のみ・スキーマ変更不要・§3-A）/ 有効期限 **1時間**・**単一使用**（`usedAt`）で `$transaction` の条件付き used 化＋パスワード更新を原子化（§3-B）/ 要求は **存在有無に関わらず一様 ack**・実行エラーも **一様メッセージ**で列挙/情報漏洩対策（§3-C）/ 新規発行時に **既存未使用トークンを一括 used 化**し有効リンクを最新 1 本に限定（§3-D）/ `/password-reset`（要求）・`/password-reset/[token]`（実行）を公開ルートに新設・server action（§3-E,F）/ `Mailer` に `sendPasswordReset` 追加・送信失敗は内部ログ＋一様 ack（§3-G）。純ロジック（`hashResetToken`・`generateResetToken`・`computeResetExpiry`・`evaluatePasswordResetToken`・`validateNewPassword`・`buildResetUrl`・一様 ack 文言）を `src/lib/password-reset.ts` に集約し単体テスト。

**bcrypt と sha256 の役割分担（設計の不変条件）:** パスワード保存 = bcrypt（低速・ソルト付き）/ リセットトークン = sha256（高速・高エントロピー乱数 + 1h 失効 + 単一使用で十分）。

```typescript
// src/lib/password-reset.ts — 純ロジック（DB/メール非依存・テスト対象）
import { randomBytes, createHash } from "node:crypto";

/** リセットトークンの有効期限（分）。発行から60分=1時間（§3-B）。 */
export const RESET_TOKEN_TTL_MINUTES = 60;

/** 新パスワードの最小文字数。 */
export const MIN_RESET_PASSWORD_LENGTH = 8;

/** ユーザー存在を露呈しない一様応答メッセージ（§3-C）。 */
export const RESET_REQUEST_ACK_MESSAGE =
  "入力されたメールアドレスが登録されている場合、パスワード再設定用のリンクを送信しました。";

/** 無効/期限切れ/使用済みを区別しない一様エラーメッセージ（§3-C）。 */
export const RESET_INVALID_LINK_MESSAGE =
  "このリンクは無効か、有効期限が切れています。お手数ですが再度リセットを要求してください。";

/** crypto.randomBytes による URL セーフな生リセットトークンを生成する（256bit）。メール URL にのみ載せる。 */
export function generateResetToken(): string {
  return randomBytes(32).toString("base64url");
}

/** 生トークンを sha256 hex に変換する純関数。DB の token 列にはこの値を保存・lookup する（§3-A）。 */
export function hashResetToken(raw: string): string {
  return createHash("sha256").update(raw).digest("hex");
}

/** 発行時刻から有効期限（now + 60分）を算出する。 */
export function computeResetExpiry(now: Date): Date {
  return new Date(now.getTime() + RESET_TOKEN_TTL_MINUTES * 60 * 1000);
}

export type ResetTokenCheck =
  | { valid: true }
  | { valid: false; reason: "not_found" | "used" | "expired" };

/** トークンレコード（or null）と現在時刻から有効/無効を判定する純関数（§3-B）。表示は一様化するが内部理由は保持。 */
export function evaluatePasswordResetToken(
  rec: { usedAt: Date | null; expiresAt: Date } | null,
  now: Date,
): ResetTokenCheck {
  if (!rec) return { valid: false, reason: "not_found" };
  if (rec.usedAt !== null) return { valid: false, reason: "used" };
  if (rec.expiresAt.getTime() <= now.getTime()) {
    return { valid: false, reason: "expired" };
  }
  return { valid: true };
}

/** 新パスワードの最小要件（長さ）を検証する純関数。 */
export function validateNewPassword(
  pw: string,
): { ok: true } | { ok: false; error: string };

/** リセットリンク URL を組み立てる（base URL は環境変数 / 引数で受ける）。生トークンを載せる。 */
export function buildResetUrl(baseUrl: string, rawToken: string): string;

// src/lib/mailer.ts — interface 拡張（既存 sendInvitation はそのまま）
export interface Mailer {
  sendInvitation(args: { to: string; inviteUrl: string }): Promise<MailerResult>;
  sendPasswordReset(args: { to: string; resetUrl: string }): Promise<MailerResult>;
}
```

A. リセット要求（公開 `/password-reset` POST server action `requestReset`）
```
1. email = normalizeEmail(formData.email)
   （isValidEmail で明白な形式不正のみ弾く。原則は一様 ack に寄せる）
2. const user = await prisma.user.findUnique({ where: { email } })
3. if (user) {
     await prisma.$transaction(async (tx) => {
       a. await tx.passwordResetToken.updateMany({              // §3-D: 既存未使用を無効化
            where: { userId: user.id, usedAt: null },
            data: { usedAt: now } })
       b. const raw = generateResetToken()
       c. const hashed = hashResetToken(raw)                    // §3-A: DB はハッシュ
       d. await tx.passwordResetToken.create({ data: {
            token: hashed, userId: user.id,
            expiresAt: computeResetExpiry(now) } })
     })
     // コミット後・存在時のみ送信。URL には生トークン raw を載せる。
     const r = await getMailer().sendPasswordReset({
       to: email, resetUrl: buildResetUrl(baseUrl, raw) })
     if (!r.ok) { /* 内部ログのみ。ユーザー応答は変えない（§3-G） */ }

4. redirect("/password-reset?sent=1")  // 存在有無に関わらず同一 ack（§3-C）
```

C. リセット実行（公開 `/password-reset/[token]` POST server action `resetPassword`）
```
1. const pw = String(formData.password); const pv = validateNewPassword(pw)
   if (!pv.ok) → エラー再表示
2. const hashed = hashResetToken(rawTokenFromUrl)
3. await prisma.$transaction(async (tx) => {
     a. const rec = await tx.passwordResetToken.findUnique({ where: { token: hashed } })
        const check = evaluatePasswordResetToken(rec, new Date())
        if (!check.valid) → throw（→ 一様エラー）
     b. const passwordHash = await hashPassword(pw)              // bcrypt（§3-A 役割分担）
     c. const upd = await tx.passwordResetToken.updateMany({     // 条件付き used 化（二重使用防止）
          where: { token: hashed, usedAt: null }, data: { usedAt: new Date() } })
        if (upd.count === 0) → throw（既に使用済み → 一様エラー）
     d. await tx.user.update({ where: { id: rec.userId }, data: { passwordHash } })
   })
4. 成功 → redirect("/login?reset=1")  // 成功メッセージ付き・自動 signIn しない
   失敗（無効/期限切れ/使用済み）→ 一様 RESET_INVALID_LINK_MESSAGE 表示
```

## 6. リスク

| リスク | 深刻度 | 軽減策 |
|---|---|---|
| トークン漏洩によるアカウント乗っ取り | high | §3-A: DB は sha256 ハッシュ保存（生トークンはメール URL のみ）。256bit 乱数・1h 失効・単一使用・再発行時に旧トークン無効化（§3-D）で時間窓と攻撃面を最小化 |
| 二重使用 / TOCTOU（同一リンクの並行実行） | high | §3-B/F: `$transaction` 内で `updateMany(where usedAt=null).count===0` の条件付き used 化を最終防壁とし、パスワード更新と原子化。再取得で再検証 |
| ユーザー列挙（存在/非存在の判別） | high | §3-C: 要求は存在有無に関わらず一様 ack。実行エラーも理由を出し分けず一様メッセージ。送信失敗もユーザー応答を変えない（§3-G） |
| RESET_TOKEN_TTL の判定境界バグ（off-by-one） | medium | `evaluatePasswordResetToken` を純関数化し境界（`expiresAt === now` は expired）を単体テストで固定。招待 `evaluateInvitation` と同方針 |
| sha256 ハッシュ化のミスマッチ（保存と lookup でエンコード不一致） | medium | `hashResetToken` を 1 つの純関数に集約し発行・GET・POST すべてが同関数を経由。既知入力→既知 hex を固定値で単体テスト |
| RESEND_API_KEY 未設定で build/typecheck/test が落ちる | medium | LAP-003 の遅延 import + NoopMailer フォールバックをそのまま継承。`sendPasswordReset` も同方式。テストは `vi.doMock("resend")` でモック |
| リセット URL の base が本番で誤生成 | medium | base は `AUTH_URL` から取得しハードコードしない。本番はドメイン確定後に設定（SPEC §10） |
| 再発行で旧リンクを踏んだユーザーの混乱（UX） | low | 旧トークン無効化は安全のため必須。一様エラー文言に「再度リセットを要求」を含め誘導 |

## 7. マイグレーション戦略

**マイグレーション不要。** `PasswordResetToken` モデルは init マイグレーション（`20260620172038_init`）に既存で完備（`token @unique` / `userId` + FK `onDelete Cascade` / `expiresAt` / `usedAt?` / `@@index([userId])`）。SPEC §7.6 と完全一致。

- `token` 列には **生トークンの sha256 hex（64 文字）を格納する**。列の型（`String @unique`）は変更不要 — ハッシュ済み文字列も一意キーとして O(1) lookup できる。
- スキーマ変更・フィールド追加・index 追加・enum 変更はいずれも不要。`prisma migrate` の新規生成も行わない（既存マイグレーションは編集しない）。
- `prisma generate` 済みの既存クライアントをそのまま使う。

## 8. ロールバック戦略

パスワードリセットは新規追加（既存挙動を破壊しない・スキーマ不変）であり、コミット単位 revert で原状回復可能。

```bash
git log --oneline
git revert <コミットハッシュ>
# 例: [LAP-005][REVERT] パスワードリセットの取り消し
```

- DB のロールバックは不要（マイグレーションを追加しないため）。発行済みの `PasswordResetToken` 行が残るが、`token @unique` 制約・`onDelete: Cascade` は init のままで無害。残置行は期限切れ・単一使用で実害なし。
