## 1. 目的

SPEC §4（Must: ポモドーロタイマー使用・対象トピック選択・1ユーザー1アクティブ・サーバー時刻基準・再open時の状態復元）および §7.1/§7.3/§7.5 を実装する。本チケットの責務は「**ライブのポモドーロ実行（ラン）と進行中の状態導出**」であり、具体的には:

1. 対象トピック + プリセット（または手入力ラップ）を選んで **StudySession を `running` で作成**し、開始時に `presetSnapshot` を凍結する（§7.1）。
2. `startedAt + presetSnapshot + サーバー現在時刻` から進行状態（何ラップ目の作業/休憩か・現ラップ内経過・累計経過・確定期限・expired 判定）を **書き込みなしで導出**する純関数を提供する（§7.3）。
3. ブラウザを閉じて再open しても、サーバーから初期状態を渡してクライアントがカウントを継続できる UI を提供する（§4）。
4. ユーザー操作による**中断（abort）の受け口**として、`StudySession.status=aborted` + `endedAt`（サーバー時刻）の UPDATE までを担う。

**スコープ外（本チケットで実装しない＝ LAP-010 の責務）:**
- **StudyRecord の materialize（生成）は LAP-010**。確定期限を経過したラン（completed / 3hキャップ aborted / ユーザー中断）に対する StudyRecord の書き込み・`countedSeconds < 60` 除外・日割り基準（completedAt）は LAP-010 が担う。本チケットは「確定期限を経過したランを参照したら **`expired` を返すのみ（materialize は呼ばない）**」に留める（§3-3 で境界を確定）。
- 中断時の StudyRecord 生成（完了済みブロック=completed / 中断ブロック=aborted の materialize）は LAP-010。本チケットは中断点（=サーバー受信時刻）を `endedAt` として記録し `status=aborted` へ遷移させるところまで。
- 集計・ヒートマップ・移動平均（§7.4）は LAP-011。

## 3. 設計方針

### 3-0. 全体方針（LAP-008/006 パターンの横展開）

1. **ラン実行 UI は `/dashboard/sessions` 配下に置く**（edge 保護を継承）。`sessions/page.tsx` を起点に「進行中ランがあれば復元表示＋中断ボタン」「無ければ開始フォーム（トピック選択＋プリセット選択 or 手入力ラップ）」を出し分ける。ライブカウントは client component（`_timer.tsx`）に切り出す。各ページ・各 server action の冒頭で `requireUserId()` を呼ぶ（二層防御）。
2. **状態導出は DB 非依存の純関数として `src/lib/session.ts` に切り出す**（既存慣習・テスト容易性）。隣に `src/lib/session.test.ts`。`now: Date` を引数注入し時刻非依存にする（`topic.ts` の前例）。`presetSnapshot` の読込は `preset.ts` の `parsePresetConfig` を再利用して narrowing する（JSONB を信頼しない）。
3. **server action は薄い層**にする。`<form action>` → `requireUserId()` → （開始は）`validatePresetInput`/snapshot 化 → DB 反映（`P2002` 捕捉）→ `revalidatePath("/dashboard/sessions")` → `redirect("?result=...")` → `ResultBanner`。

### 3-1. presetSnapshot の凍結方式（§7.1）

- 開始時に「**正規化済み `LapConfig[]` を JSON として `presetSnapshot` に丸ごとコピー**」する。元 `Preset` 行への FK は持たせない（snapshot は値のコピーであり参照ではない）。これにより元プリセットを後から編集・削除しても進行中ランは影響を受けない（§7.1 要件・受け入れ条件 3）。
- snapshot の入力源は 2 経路を許容する（どちらも最終的に `validatePresetInput` を通した `LapConfig[]` に正規化してから保存する。検証ロジックは LAP-008 の純関数を再利用し重複実装しない）:
  - (a) **保存済みプリセット選択**: フォームから `presetId` を受け取り、`prisma.preset.findFirst({ where:{ id: presetId, userId } })` で取得 → `parsePresetConfig(preset.config)` で narrowing → そのまま snapshot 化（プリセット作成時に検証済みのため）。`null` は `preset_not_found`。
  - (b) **手入力ラップ**: `_form.tsx` の `collectLaps(formData)` + `validatePresetInput` で検証 → 成功時の `config` を snapshot 化（LAP-008 と同じ入力 UI・純関数を共有）。
- snapshot 化の前に snapshot が空配列でないこと（最低 1 ラップ）を保証する。これは `validatePresetInput`（手入力経路）と `parsePresetConfig` 後の長さチェック（プリセット経路・空なら `empty_config`）で担保する。

### 3-2. サーバー時刻基準の状態導出純関数（§7.3）

進行状態の導出は **書き込みを一切行わない純関数** `deriveSessionState(input)` に集約する。`startedAt` と `now` の差（経過秒）を `presetSnapshot` のラップ列に対して順に消化し、現在位置を特定する。クライアント時計は一切信頼せず、サーバーが渡す `startedAt`（DB 値）と `now`（`new Date()`）のみを根拠にする（改ざん対策・受け入れ条件 5）。

**ラップ列の時間モデル（タイムライン）:**
```
[lap0.work][lap0.break][lap1.work][lap1.break]...[lapN.work][lapN.break]
 ←─ 各セグメントを順に消化。経過秒 = floor((now - startedAt)/1000) がどのセグメントに入るかで現在位置を決める。
 breakSec=0 のラップは break セグメントが長さ0で、経過が「またぐ」と即次のラップ work へ。
```

- **ラン総時間** `totalSec = Σ(workSec_i + breakSec_i)`。
- **確定期限** `deadlineSec = min(totalSec, 3*3600)`（= `min(startedAt+ラン総時間, startedAt+3h)` の秒表現・§7.3）。`now - startedAt ≥ deadlineSec` なら `expired`（確定期限を経過済み・materialize は LAP-010）。
- **`breakSec=0` 境界**: 長さ0の break セグメントには「現在位置」を割り当てない（経過が break の開始＝終了に一致しても、次の work へ進む）。実装は「セグメント開始 ≤ 経過 < セグメント終了」の半開区間で判定し、長さ0区間は常に偽になることで自然に除外される。
- **`<60s` 除外は本チケットでは判定しない**。これは materialize（LAP-010）での `countedSeconds < 60` 除外の話であり、進行中の状態導出には関与しない。本チケットの純関数は「今どこか」を返すのみ。

### 3-3. LAP-010（materialize）との責務分界（明示的な境界線）

| 局面 | LAP-009（本チケット）の責務 | LAP-010（materialize）の責務 |
|---|---|---|
| 開始 | StudySession を `running` で作成・snapshot 凍結・`startedAt` 記録 | — |
| 進行中（`now < 確定期限`）参照 | `deriveSessionState` で「現ラップ/種別/経過/累計/確定期限」を返す（**書き込みなし**） | — |
| 確定期限経過済み（`now ≥ 確定期限`）参照 | `deriveSessionState` が **`phase: "expired"` を返すのみ**。StudyRecord を生成しない・status を変えない | 遅延評価で StudyRecord を materialize し `status` を completed/aborted へ確定 |
| ユーザー中断 | `status=aborted` + `endedAt=サーバー受信時刻` の **UPDATE まで**（受け入れ条件 8） | 中断点（=endedAt）と snapshot から completed/aborted ブロックを StudyRecord に materialize |
| 3hキャップ・完了の確定 | 検知（`deriveSessionState` の `expired`）まで | 確定の実行（completed/aborted materialize） |

**境界線の根拠（確定）:**
- 本チケットは「**進行中の状態導出（読み取り専用）**」と「**ラン実体の状態遷移（running 作成 / aborted への UPDATE）**」を担い、**StudyRecord（過去の事実）への書き込みは一切しない**。これにより、materialize の複雑なロジック（completed/aborted の振り分け・countedSeconds 計算・<60s 除外・日割り）を LAP-010 に閉じ込め、本チケットを「ランのライフサイクル＋状態導出」に限定できる。
- expired を返すだけにする理由: materialize を本チケットに含めると LAP-010 とロジックが二重化し、責務が曖昧になる。`deriveSessionState` の出力に `expired` を持たせ、UI は「確定待ち（記録に反映されます）」と表示する。実際の materialize 経路は LAP-010 が遅延評価フックを差し込む（本チケットの純関数・action はその差し込み点を `expired` で明示する）。
- 中断時の `endedAt` を「サーバー受信時刻」に固定する理由: クライアントから中断時刻を受け取ると改ざんできる（§7.3）。server action 内で `new Date()` を `endedAt` に使う（受け入れ条件 8）。

> **注意（implementer 向け）**: 本チケットの中断 action は `status` が `running` のランのみを `aborted` にする（`updateMany({ where:{ id, userId, status:"running" } })`）。既に確定済み（completed/aborted）のランへの二重中断は `count===0`→`not_found` で一様化する。中断時に StudyRecord を作らないため、LAP-010 未実装の段階では「中断したランは StudyRecord 0 件のまま aborted で残る」点を許容する（LAP-010 が後で materialize 経路を追加する。整合は LAP-010 のスコープ）。

### 3-4. running 二重作成時の挙動（§7.5・Unknown #1 の結論）

**結論: 「拒否（エラー返却）」を採用する。** 既存の running があるユーザーが新規開始しようとした場合、新規作成せず `already_running` を返して「進行中のランがあります。中断または完了してから新しく開始してください」と案内する。

**判定と捕捉（多層防御。LAP-006 の P2003 フォールバックと同思想で DB を最終権威にする）:**
1. **プリチェック（UX 層）**: 開始 action 冒頭で `prisma.studySession.findFirst({ where:{ userId, status:"running" } })` を確認し、存在すれば作成せず `already_running` を返す。
2. **DB 最終権威（TOCTOU 対策）**: プリチェックと create の間に並行リクエストで running が生成され得る。`prisma.studySession.create(...)` を try/catch で囲み、`Prisma.PrismaClientKnownRequestError` かつ `e.code === "P2002"`（partial unique index `studysession_user_running_unique` 違反）を捕捉して `already_running` へフォールバックする。

**「既存を abort 確定してから新規作成」を却下する理由:**
- (a) abort→create を採るとユーザーが意図せず進行中ランを失う（UX 上危険）。明示的な中断操作を経るべき。
- (b) abort→create を安全に行うには同一トランザクション内で `abort UPDATE → create` を回さないとレースで再び `P2002` が出る（abort と create の間に別ランが割り込む）。トランザクション境界の複雑化に見合うメリットがない。
- (c) abort は本来 LAP-010 の materialize（中断記録）を伴うべき操作であり、「開始のついでに自動 abort」は §7.3 の確定フローと責務が混ざる。中断は明示的なユーザー操作（§3-3 の中断 action）に一本化する。

**トランザクション境界（確定）:** 開始 action は **単一の `create` のみ**（トランザクション不要）。`P2002` を捕捉して `already_running` に倒すだけで一意制約は DB が保証する。プリチェックは UX 向上のための早期リターンであり、正しさは `P2002` 捕捉が担保する。abort→create を採らないためマルチステートメントトランザクションは不要。

### 3-5. UI / client component の状態受け渡し（§4）

- **サーバー（`sessions/page.tsx`・Server Component）**: `requireUserId()` → 進行中ラン取得 → `deriveSessionState({ snapshot, startedAt, now: new Date() })` で初期状態を計算 → **その導出結果（プレーンオブジェクト）と `startedAt`(ISO 文字列)・`snapshot` を client component に props で渡す**。
- **クライアント（`_timer.tsx`・`"use client"`）**: 受け取った初期状態を起点に、`requestAnimationFrame`/`setInterval` でカウントを継続する。**カウントの基準はサーバーが渡した `startedAt`(ISO)**。クライアントは「`startedAt` からの経過秒」をクライアント時計の差分で更新するが、これは**表示のためのカウントアップに過ぎない**。状態の正（何ラップ目か・expired か・確定）はサーバーが導出済みの値であり、必要に応じてサーバー再取得（再open・router.refresh）で再同期する。
- **再open時の復元（受け入れ条件 7）**: ブラウザを閉じて再度 `/dashboard/sessions` を開くと、Server Component が `now=new Date()` で再導出するため、クライアント側の状態を一切持たなくても進行状態が復元される。client component はサーバーから渡された初期状態をそのまま表示し継続カウントするだけでよい（localStorage 等のクライアント永続化は不要・使わない）。
- **expired のときの表示**: `phase==="expired"` なら client は「確定期限に到達しました。記録に反映されます（集計反映は LAP-010/011）」と表示し、カウントを止める。本チケットでは materialize しないため「確定待ち」の静的表示でよい。

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| running 二重作成で既存を abort 確定してから新規作成 | ユーザーが意図せず進行中ランを失う・abort→create を安全に行うには同一Txが必要でレース対策が複雑・abort は本来 materialize（LAP-010）を伴うべき。明示的中断に一本化（§3-4） |
| 確定期限経過済みランの参照時に本チケットで materialize する | LAP-010 とロジック二重化・責務曖昧化。`expired` を返すだけにして materialize は LAP-010 に閉じ込める（§3-3） |
| 中断時刻をクライアントから受け取る | 改ざん可能（§7.3）。server action 内 `new Date()` をサーバー権威の中断点にする（§3-3） |
| 作業↔休憩の遷移ごとに DB へ書き込む | §7.3 が明示的に禁止（進行中は書き込みなしで導出のみ）。状態導出純関数で代替 |
| 状態を client が localStorage 等に永続化して復元 | サーバー時刻が正（§4/§7.3）。再open は Server Component の再導出で復元でき、クライアント永続化は不要・改ざん面で不利 |
| running 検出をプリチェックのみ（P2002 を捕捉しない） | TOCTOU で並行 create がすり抜け得る。DB の partial unique index を最終権威に P2002 捕捉が必須（§3-4） |
| `presetSnapshot` に Preset への FK / id 参照を持たせる | 元プリセット編集・削除で進行中ランが影響を受ける（§7.1 違反）。値のコピー（snapshot）にする（§3-1） |

**主要なインターフェース（型・I/F 素案。実装は implementer）:**
```typescript
// src/lib/session.ts — DB 非依存の状態導出純ロジック（SPEC §7.3）

import type { LapConfig } from "@/lib/preset"; // presetSnapshot の要素型を共有（§7.1/LAP-008）

/** 終了し忘れ対策の確定キャップ（3 時間・SPEC §4 Should / §7.3）。 */
export const MAX_RUN_SECONDS = 3 * 60 * 60; // 10800

/** 進行中の現在位置の種別。 */
export type SessionPhase =
  | "work"     // 現在は作業区間
  | "break"    // 現在は休憩区間
  | "expired"; // 確定期限を経過済み（materialize 待ち・LAP-010）。本チケットは書き込まない

export type DeriveSessionInput = {
  snapshot: LapConfig[]; // 凍結済みラップ構成（parsePresetConfig で narrowing 済みを渡す）
  startedAt: Date;       // DB の startedAt（サーバー時刻が正）
  now: Date;             // 評価時点のサーバー現在時刻（new Date() を注入。テストは固定値）
};

export type SessionState = {
  phase: SessionPhase;       // work / break / expired
  lapIndex: number;          // 0 始まりの現ラップ番号。expired のときは最終ラップ index（または -1。下記注記）
  totalSec: number;          // ラン総時間 Σ(workSec+breakSec)
  deadlineSec: number;       // 確定期限 = min(totalSec, MAX_RUN_SECONDS)
  elapsedSec: number;        // startedAt からの累計経過秒（floor。負なら 0 へクランプ）
  segmentElapsedSec: number; // 現セグメント（現ラップの work か break）内の経過秒。expired のときは 0
  segmentTotalSec: number;   // 現セグメントの総秒数（workSec or breakSec）。expired のときは 0
  expired: boolean;          // elapsedSec >= deadlineSec（= phase==="expired"）。UI/LAP-010 の境界
};

/**
 * 進行中ランのサーバー時刻基準の状態を導出する純関数（§7.3・書き込みなし）。
 *
 * アルゴリズム（擬似）:
 *   1. elapsedSec = max(0, floor((now - startedAt)/1000))
 *   2. totalSec = Σ(snapshot[i].workSec + snapshot[i].breakSec)
 *      deadlineSec = min(totalSec, MAX_RUN_SECONDS)
 *   3. elapsedSec >= deadlineSec なら expired を返す
 *        → { phase:"expired", expired:true, lapIndex: 最終ラップ index, segmentElapsed/Total:0, ... }
 *   4. それ以外: snapshot を先頭から走査し、累積境界 acc に対して
 *        work セグメント [acc, acc+workSec): 半開区間に elapsedSec が入れば phase="work"
 *          lapIndex=i, segmentElapsedSec = elapsedSec-acc, segmentTotalSec=workSec
 *        break セグメント [acc, acc+breakSec): 入れば phase="break"
 *          lapIndex=i, segmentElapsedSec = elapsedSec-acc, segmentTotalSec=breakSec
 *      ※ breakSec=0 の break セグメントは長さ0 → 半開区間が空 → 必ずスキップ（§3-2）
 *   5. （理論上 elapsedSec < deadlineSec なら必ず 4 でヒットする。ヒットしない場合は
 *      浮動小数/境界の保険として最終 work セグメントへフォールバックする）
 */
export function deriveSessionState(input: DeriveSessionInput): SessionState;
```
> `expired` のときの `lapIndex` の扱いは「最終ラップ index」を返す（UI は『全ラップ完了・確定待ち』を表示するのみで lapIndex を厳密には使わない）。テストでは `expired===true` と `phase==="expired"` の判定に集中し、lapIndex の厳密値はアサートしない（または最終ラップ index を期待値に固定する）。implementer 裁量。

**処理フロー:**

A. 開始（startSession・§3-1/§3-4）
```
1. requireUserId() で userId 確定（未認証は /login へ）
2. FormData から topicId・(presetId または 手入力ラップ) を取得
3. トピック検証: prisma.topic.findFirst({ where:{ id: topicId, userId } })
     null → ?result=topic_not_found（DB に触れず終了）
4. snapshot の確定（§3-1）:
     (a) presetId 指定: prisma.preset.findFirst({ where:{ id: presetId, userId } })
           null → ?result=preset_not_found
           config = parsePresetConfig(preset.config)
           config.length===0 → ?result=empty_config
           snapshot = config
     (b) 手入力: validatePresetInput({ name:"_", laps: collectLaps(formData) })
           失敗 → ?result=<reason>（lap_work_too_short 等を流用）
           snapshot = validation.value.config
5. running 二重作成のプリチェック（UX 早期リターン・§3-4）:
     prisma.studySession.findFirst({ where:{ userId, status:"running" } })
       存在 → ?result=already_running
6. 作成（DB 最終権威で TOCTOU 対策・§3-4）:
     try {
       await prisma.studySession.create({
         data: { userId, topicId, presetSnapshot: snapshot, startedAt: new Date(), status:"running" }
       });
     } catch (e) {
       if (Prisma.PrismaClientKnownRequestError && e.code==="P2002") → ?result=already_running
       else throw e;
     }
7. revalidatePath("/dashboard/sessions") → ?result=started
```
> `startedAt` はサーバー時刻 `new Date()` をその場で生成して保存する（§7.3・受け入れ条件 2/5）。

B. 中断（abortSession・§3-3）

2. FormData から id（StudySession id）取得
3. UPDATE（status は running のみを対象・データ分離・サーバー時刻を中断点に）:

       where: { id, userId, status: "running" },
       data: { status: "aborted", endedAt: new Date() },  // ← サーバー受信時刻（改ざん対策・§3-3）
     });
     count===0 → ?result=not_found（不在・他人・既に確定済みを一様化）
4. revalidatePath("/dashboard/sessions") → ?result=aborted
   （StudyRecord の生成は LAP-010。本チケットは status=aborted + endedAt まで・§3-3）
```

D. ライブカウント（_timer.tsx・"use client"・§3-5）
```
- props: { initial: SessionState, startedAt: string(ISO), snapshot: LapConfig[] }

## 7. マイグレーション戦略

**マイグレーション不要（StudySession・partial unique index は init 既存・スキーマ不変）。**

- `StudySession` モデル（`id/userId/topicId/presetSnapshot(Json)/startedAt/status/endedAt/createdAt`・`@@index([userId,status])`・FK）と partial unique index `studysession_user_running_unique`（`WHERE status='running'`）は init マイグレーション（`20260620172038_init`）で適用済みで、SPEC §7.5/§7.6 と一致。
- 本チケットはフィールド追加・削除・FK 変更を一切行わない。`presetSnapshot` の構造（`[{workSec,breakSec},...]`）はアプリ層の純関数（`parsePresetConfig`）で narrowing するのみで DB スキーマには現れない（JSONB のまま）。
- よって `prisma/schema.prisma` および `prisma/migrations/` は本チケットで一切変更しない。`npm run prisma:validate` は現状のまま通る想定。

## 8. ロールバック戦略

本チケットは新規ファイル追加（純関数 1 + テスト 1 + ページ 1 + client component 1）のみで、schema/migration を触らないため、コミット単位の revert で完全に原状回復できる。DB 側のロールバックは不要。

```bash
git log --oneline
git revert <コミットハッシュ>
# 例: [LAP-009][REVERT] ポモドーロ実行とStudySessionの取り消し
```
- マイグレーションが無いため DB reset は不要。
- 既に作成済みの `StudySession` 行（あれば）は revert 後も残るが、`presetSnapshot` 構造は SPEC §7.1 準拠なので後続再導入時もそのまま利用できる。中断済み（aborted）ランの StudyRecord 生成は LAP-010 が担うため、本チケット revert で過去記録は失われない。
- CLAUDE.md ロールバック規約に従い、done/→active/ 戻し・status を implementation_done に戻す運用は orchestrator が担当。
