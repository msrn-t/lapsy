## 1. 目的

SPEC §3 を実装する。管理者が他ユーザーの管理者フラグを付与・剥奪できる手段を提供し、安全ガードとして
(a) 自己降格不可、(b) 最後の管理者保護（管理者ゼロ状態の防止）、(c) 認可（非管理者は操作不可）を担保する。

## 3. 設計方針

### 3-1. 操作手段の選定（SPEC が architect に委ねる）

**採用: LAP-002 の認可基盤を流用した最小の「管理者用ユーザー一覧 + フラグ・トグル」ページ（`/admin/users`）+ server action。**

- サーバコンポーネントのページでユーザー一覧（email / isAdmin）を表示し、各行に「付与／剥奪」を切り替える server action フォームボタンを置く。専用の凝った管理画面（検索・ページング・ロール編集 UI 等＝§4 Could）は**作らない**。一覧 + トグルのみ。
- 運用で実際にフラグ操作ができること（受け入れ条件）を満たしつつ、UI を最小化する。
- 認可は LAP-003 と同じ二層（後述 3-5）。データ取得・更新ロジックは server action に集約し、**判定ロジックは純関数へ切り出して**単体テスト可能にする（後述 3-2 / SPEC §9）。

**代替案と却下理由:**

| 案 | 却下理由 |
|---|---|
| server action のみ（UI 無し・呼び出し口なし） | 受け入れ条件「運用で実際にフラグ操作ができる手段」を満たしにくい。最小の一覧 + トグルでも実装量はわずかで、運用性が大きく上がる |
| seed / CLI スクリプトで toggle | サーバへの SSH・スクリプト実行が前提になり日常運用に不向き。ガード（自己降格・最後の管理者）を毎回手で担保する必要があり危険 |
| §4 Could の専用管理画面（検索・ページング・ロール一覧 UI） | スコープ外（SPEC §4 Could・MVP では不要）。本チケットは最小手段に限定 |

### 3-2. ガードロジック（純関数化・テスト対象）

フラグ操作の可否判定を **副作用なしの純関数**に切り出し、DB アクセス前のプリチェックとして使う。同じ判定を server action から呼ぶ。

判定対象は SPEC §3 の 3 ガード:

- **(c) 認可**: 操作者が `isAdmin` でなければ拒否（`forbidden`）。
- **(a) 自己降格不可**: 操作が「剥奪」かつ 操作者 id == 対象 id なら拒否（`self_demotion`）。付与の自己操作は無害だが、対象が既に管理者なら no-op 扱い。
- **(b) 最後の管理者保護**: 操作が「剥奪」かつ 対象が現在 `isAdmin=true` かつ 他に管理者が存在しない（剥奪で管理者ゼロになる）なら拒否（`last_admin`）。

純関数は「現在の管理者総数（または『他に管理者が居るか』の真偽）」を引数で受け取り、TOCTOU の原子化は DB 層（3-3）に委ねる。純関数はあくまで早期拒否とテスト対象のためのロジック中心化。**最終的な最後の管理者保護は 3-3 の原子 UPDATE が正**とする（純関数のチェックだけに依存しない多層防御）。

```typescript
// src/lib/admin-guard.ts（純関数・テスト対象）
export type AdminAction = "grant" | "revoke";
export type AdminGuardResult =
  | { ok: true }
  | { ok: false; reason: "forbidden" | "self_demotion" | "last_admin" | "target_not_found" };

export function evaluateAdminFlagChange(input: {
  actorIsAdmin: boolean;     // 操作者が管理者か（認可）
  actorId: string;           // 操作者 id
  targetId: string;          // 対象 id
  targetExists: boolean;     // 対象が存在するか
  targetIsAdmin: boolean;    // 対象の現在 isAdmin
  action: AdminAction;       // grant / revoke
  otherAdminExists: boolean; // 対象以外に isAdmin=true が存在するか（最後の管理者判定の素材）
}): AdminGuardResult;
```

判定順（実装ガイド・実装は implementer）:
1. `actorIsAdmin` が false → `forbidden`
2. `targetExists` が false → `target_not_found`
3. `action === "revoke"`:
   - `actorId === targetId` → `self_demotion`
   - `targetIsAdmin === true && otherAdminExists === false` → `last_admin`
4. それ以外 → `{ ok: true }`（grant、または既に望む状態なら server action 側で no-op として扱う）

### 3-3. 最後の管理者保護の競合対策（TOCTOU）

**採用: ② 条件付き原子 UPDATE（`updateMany` の `where` に保護条件を畳み込み、affected=0 を拒否扱い）。これを `$transaction` でラップして読み取り（一覧再取得は不要）と整合させる。**

剥奪（revoke）時、「他に管理者が存在するか」の COUNT と UPDATE を分離すると、2 人の管理者が互いを同時に剥奪して 0 人化する TOCTOU が起きうる。これを **単一の条件付き UPDATE** で防ぐ。

剥奪の原子 UPDATE（概念。実装は Prisma で表現）:
```
UPDATE "User"
   SET "isAdmin" = false, "sessionVersion" = "sessionVersion" + 1
 WHERE id = :targetId
   AND "isAdmin" = true
   AND id <> :actorId                              -- 自己降格はここでも二重防御
   AND (SELECT COUNT(*) FROM "User" WHERE "isAdmin" = true) > 1   -- 最後の管理者なら 0 行更新
```

- `Prisma.updateMany`（`where` に `isAdmin: true` を含む）で「対象がまだ管理者であること」を原子条件にできる。「管理者が 2 人以上いること」の条件は Prisma の宣言的 `where` では表現しづらいため、**最後の管理者条件のみ raw SQL（`prisma.$executeRaw`）の条件付き UPDATE で表現**し、`affected === 0` を `last_admin`（または競合により既に剥奪済み）として拒否する。`bumpSessionVersion` 相当の `sessionVersion + 1` を同一 UPDATE に畳み込む（3-4 参照）。
- 全体を `prisma.$transaction([...], { isolationLevel: Prisma.TransactionIsolationLevel.Serializable })` で囲み、純関数プリチェック（3-2）→ 原子 UPDATE → affected 判定の一連を1トランザクションにする。PostgreSQL（SPEC §6）で Serializable が利用可能。
- 付与（grant）は 0 人化リスクが無いため、`prisma.user.update({ where:{ id }, data:{ isAdmin: true } })` で十分（必要なら 3-4 の bump 方針に従う）。

**代替案と却下理由:**

| 案 | 却下理由 |
|---|---|
| ① `$transaction(Serializable)` 内で COUNT→UPDATE | 動作はするが、純粋な read→write を Serializable に頼り、競合時はシリアライズ失敗で例外→リトライ実装が必要。条件付き原子 UPDATE の方が「affected=0 を拒否」で意図が明確かつリトライ不要 |
| ③ 行ロック（`SELECT ... FOR UPDATE`） | 全管理者行をロックする設計になり影響範囲が広い。条件付き UPDATE で十分な保護が、より小さな範囲で得られる |
| 素朴な COUNT→UPDATE（トランザクション無し） | TOCTOU で 0 人化する。SPEC §3 のガードを満たさない。却下 |

> 補足: ②でも `$transaction(Serializable)` でラップするのは、プリチェック読み取りと UPDATE の間の一貫性を高めるための保険。条件付き UPDATE 単体でも 0 人化は防げる（保護条件が UPDATE 自身に内包されるため）。Serializable は二重防御。

### 3-4. 強制ログアウト／即時反映（bumpSessionVersion 要否）

**方針: 剥奪（revoke）時は `sessionVersion` を increment する（=強制ログアウト）。付与（grant）時は increment しない。**

- **剥奪時に bump する理由（採用）**: 管理者権限の剥奪はセキュリティ上「即時・確実」に効かせたい。`jwt` callback は次回アクセスで `token.isAdmin` を DB 値へ更新するため値伝播だけなら bump 不要だが、bump で既存トークンを完全失効させ「再ログインを強制」することで、権限剥奪のセマンティクスを明確化・確実化する。LAP-002 設計 §4（line 191）も「管理者フラグ変更・強制ログアウトで bump」を想定。
  - **実装上の注意**: 3-3 の条件付き原子 UPDATE に `sessionVersion = sessionVersion + 1` を畳み込むため、剥奪が成功した（affected=1）ときのみ bump が起きる。`auth-revocation.ts` の `bumpSessionVersion` を別途呼ぶと UPDATE が 2 回（原子性が崩れる）になるため、**剥奪パスでは原子 UPDATE 内で bump を行い、別呼び出しはしない**。`bumpSessionVersion` は付与パスや将来用途のために存置（重複呼び出ししない）。
- **付与時に bump しない理由**: 権限の付与は「次回アクセスで isAdmin=true が反映されれば十分」で、既存セッションを強制失効させて再ログインを強いる必要はない（むしろ UX を損なう）。`jwt` callback が次回 `token.isAdmin = true` を反映する。

> reviewer/implementer 向けメモ: 剥奪の `sessionVersion + 1` は「強制ログアウト」目的であり、最後の管理者保護（affected=0 拒否）とは独立。affected=0（最後の管理者 or 既に剥奪済み）のときは UPDATE が起きないので bump も起きない（正しい挙動）。

### 3-5. 認可（二層）

LAP-003 と同一パターンを踏襲する。

1. **edge 層（middleware / `auth.config.ts` の `authorized`）**: `/admin` 配下をログイン必須で保護。isAdmin 判定は edge では行わない（Prisma が edge 非互換のため。LAP-002 §3 方針5・LAP-003 と同方針）。
   - **重要（develop 起点のため）**: develop の `auth.config.ts` は `/dashboard` のみ保護で `/admin` 保護が無い。本チケットのブランチ内で `authorized` の保護対象に `/admin` 配下を追加する（`nextUrl.pathname.startsWith("/admin")` をログイン必須に含める）。LAP-003 マージ時のコンフリクトは §6 リスクに記載。
2. **node 層（ページ／server action 冒頭）**: `getCurrentUser()` で `isAdmin` を必須化する（非管理者は `/dashboard` へ redirect、未認証は `/login`）。LAP-003 の `requireAdminId()` と同じロジック。
   - LAP-003 では `requireAdminId` がページファイル内ローカル関数だった。LAP-004 では**共通ヘルパとして `src/lib/auth-helpers.ts` に `requireAdmin()`/`requireAdminId()` を追加**し、`/admin/users` ページと server action の両方から使う（重複定義を避け、後続 admin 機能でも再利用）。LAP-003 マージ時にローカル定義と二重化しうる点は §6 リスクに記載。

server action は「`"use server"` 冒頭で `requireAdminId()` を必ず呼ぶ」ことを必須とする（フォーム経由でもサーバ側で再認可する。クライアントの hidden field を信頼しない）。対象ユーザー id は formData から受け取るが、認可は必ずセッション由来の操作者で判定する。

**処理フロー:**

A. 一覧表示（`/admin/users` ページ・サーバコンポーネント）
```
1. requireAdminId()（未認証→/login、非管理者→/dashboard）
2. prisma.user.findMany({ select:{ id, email, isAdmin }, orderBy:{ email:"asc" } })
3. 各行に email / isAdmin と、付与 or 剥奪の server action フォームボタンを描画
   （自分自身の行の「剥奪」ボタンは disabled で描画してもよい＝UX。ただしサーバ側ガードを正とする）
```

B. フラグ変更（server action `toggleAdmin(formData)`）
```
1. "use server"; const actorId = await requireAdminId();    // 二層目認可（必須）
2. const actor = await getCurrentUser();                    // actorIsAdmin / actorId
   const targetId = String(formData.get("targetId"));
   const action = String(formData.get("action")) as AdminAction; // "grant" | "revoke"
3. プリチェック（純関数）:
   - 対象を取得: const target = await prisma.user.findUnique({ where:{ id: targetId }, select:{ id, isAdmin } })
   - 「他に管理者が居るか」: const otherAdminCount = await prisma.user.count({ where:{ isAdmin:true, id:{ not: targetId } } })
   - evaluateAdminFlagChange({ actorIsAdmin: actor.isAdmin, actorId, targetId, targetExists:!!target,
       targetIsAdmin: target?.isAdmin ?? false, action, otherAdminExists: otherAdminCount > 0 })
   - ok=false → result を付けて redirect("/admin/users?result=<reason>")（操作は行わない）
4. 確定（DB 原子化・§3-3）:
   - revoke: $transaction(Serializable) で条件付き原子 UPDATE
       UPDATE "User" SET isAdmin=false, sessionVersion=sessionVersion+1
        WHERE id=:targetId AND isAdmin=true AND id<>:actorId
          AND (SELECT COUNT(*) FROM "User" WHERE isAdmin=true) > 1
       affected=0 → "last_admin"（または競合で既に剥奪済み）として redirect で通知。affected=1 → success
   - grant: prisma.user.update({ where:{ id:targetId }, data:{ isAdmin:true } })（bump しない・§3-4）。
       既に isAdmin=true なら no-op（純関数 ok=true でも実害なし）
5. revalidate or redirect("/admin/users?result=success") で一覧再描画
```

C. 即時反映の伝播
```
- 剥奪成功 → sessionVersion increment 済み → 対象の次回アクセスで jwt callback の照合が不一致 → トークン無効化（強制ログアウト相当）→ /login。
- 付与成功 → 対象の次回アクセスで jwt callback が token.isAdmin=true を反映（強制ログアウトなし）。
```

**`auth.config.ts` の変更（§3-5・develop 起点前提）:**
```

  const isOnProtected =
    nextUrl.pathname.startsWith("/dashboard") || nextUrl.pathname.startsWith("/admin");
  if (isOnProtected) return isLoggedIn;
※ isAdmin 判定は edge で行わない（node 側 requireAdminId が担う二層防御）。
```

## 6. リスク

| リスク | 深刻度 | 軽減策 |
|---|---|---|
| **最後の管理者保護の TOCTOU**（2 管理者が互いを同時剥奪 → 0 人化） | high | §3-3 の条件付き原子 UPDATE（`COUNT(*)>1` を UPDATE の where に内包）+ `$transaction(Serializable)`。affected=0 を拒否。純関数プリチェックは早期拒否のみで、保護の正は DB 層 |
| **`auth.config.ts` のコンフリクト**（LAP-003 も /admin 保護を追加するため、両者が同一ファイルを編集） | medium | LAP-004 は develop 起点で /admin 保護を追加。LAP-003 マージ時に同じ `authorized` を両者が触りコンフリクトしうる。マージ担当が「/admin 保護が二重／差分」を確認し統合。LAP-004 は LAP-003 成果物に依存しない（LAP-002 基盤のみ依存） |
| **`requireAdminId` の重複定義**（LAP-003 はページローカル定義、LAP-004 は auth-helpers 共通化） | low | LAP-004 は共通ヘルパへ集約。LAP-003 マージ時にローカル定義を共通ヘルパへ寄せる（重複は害なく、統合は容易）。本チケットでは共通版を正とする |
| **二重 bump**（原子 UPDATE 内 bump と `bumpSessionVersion` の両呼び出し） | medium | 剥奪パスでは原子 UPDATE 内でのみ bump。`bumpSessionVersion` を剥奪パスで別途呼ばない（§3-4 明記） |
| **自己降格の見落とし**（UI で隠しても API 直叩きで剥奪される） | medium | サーバ側ガードを正とする。純関数（actorId==targetId 拒否）+ 原子 UPDATE の `id<>:actorId` 条件で二重防御。UI の disabled は補助のみ |
| **raw SQL のテーブル/列名（PascalCase クォート）誤り** | low | PostgreSQL は `"User"`/`"isAdmin"` のダブルクォートが必要。implementer は `$executeRaw` のパラメタライズ（SQL インジェクション防止）とクォートを Prisma 6 の作法で確認 |
| **付与/剥奪の状態が UI に即時反映されない** | low | server action 後に `revalidatePath("/admin/users")` または redirect で再取得。剥奪対象本人の反映は次回アクセス（強制ログアウト）で正しく効く |

## 7. マイグレーション戦略

**なし。** `User.isAdmin` / `User.sessionVersion` は既存のためスキーマ変更・マイグレーションは不要（§2）。
万一 implementer が DB 制約追加等を必要と判断した場合は、既存マイグレーションを編集せず**新規マイグレーション**として追加すること（ただし本設計はアプリ層の原子 UPDATE で保護を担保するため、追加マイグレーションは想定しない）。

## 8. ロールバック戦略

本機能は新規追加（純関数・ページ・auth.config 1 行追加）で、コミット単位の revert で原状回復できる。

```bash
git log --oneline
git revert <コミットハッシュ>
# 例: [LAP-004][REVERT] 管理者フラグ管理の取り消し
```
- DB スキーマ変更が無いためマイグレーションのロールバックは不要。
- 剥奪で increment 済みの `sessionVersion` は revert 後も残る（=対象は再ログインが必要）。これは失効の正しい結果でありロールバック対象外。
- CLAUDE.md ロールバック規約に従い、done/→active/ 戻し・status を implementation_done に戻す運用は orchestrator が担当。

## 9. 受け入れ条件

tester/reviewer の検証基準（チケット受け入れ条件を設計観点で具体化）。

- [ ] 管理者は `/admin/users` で他ユーザーの管理者フラグを**付与**できる（付与後、対象の次回アクセスで isAdmin=true が反映される）
- [ ] 管理者は `/admin/users` で他ユーザーの管理者フラグを**剥奪**できる（剥奪後、対象は次回アクセスでトークン失効＝強制ログアウトされる）
- [ ] **自己降格不可**: 操作者 id == 対象 id かつ剥奪は拒否される（純関数 `self_demotion` + 原子 UPDATE の `id<>:actorId`）。UI でも自分の剥奪ボタンは無効化されている
- [ ] **最後の管理者保護**: 剥奪により管理者が 0 人になる場合は拒否される。条件付き原子 UPDATE（`COUNT(*)>1`）で affected=0 を拒否し、同時剥奪の 0 人化も防ぐ（§3-3）
- [ ] **認可**: 非管理者は `/admin/users` 表示・フラグ操作のいずれもできない（edge: /admin はログイン必須 / node: `requireAdminId` で非管理者は /dashboard へ）。server action 直叩きでも非管理者は拒否される
- [ ] 剥奪時に `sessionVersion` が increment される（原子 UPDATE 内）。付与時は increment されない（§3-4）。二重 bump が起きない
- [ ] ガード純関数 `evaluateAdminFlagChange`（認可・自己降格不可・最後の管理者保護・対象不在）に Vitest 単体テストがある（SPEC §9）
- [ ] `src/auth.config.ts` の `authorized` が `/admin` 配下をログイン必須で保護している（develop 起点で追加）
- [ ] `prisma/schema.prisma` に変更が無い（既存 isAdmin/sessionVersion を流用・マイグレーション追加なし）
- [ ] `npm test` / `npx tsc --noEmit`（typecheck）/ `npm run build` が通る
- [ ] コミットメッセージに `[LAP-004]` が含まれる（push は人間）。機密の実値がコミットに含まれない（`git diff` 確認）

**テスト（Vitest）対象（`admin-guard.test.ts`）:**
- 非管理者の操作 → `forbidden`
- 自己剥奪（actorId==targetId かつ revoke）→ `self_demotion`
- 最後の管理者の剥奪（targetIsAdmin=true かつ otherAdminExists=false かつ revoke）→ `last_admin`
- 他に管理者が居る状態での剥奪（otherAdminExists=true）→ `ok:true`
- 付与（grant・他ユーザー）→ `ok:true`
- 自己付与（actorId==targetId かつ grant）→ `ok:true`（自己降格不可は剥奪のみ）
- 対象不在（targetExists=false）→ `target_not_found`
