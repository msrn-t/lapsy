## 1. 目的

SPEC §4(Must 招待関連) を実装する。管理者がメールアドレスを指定して招待メール（Resend）を送信し、被招待者が招待リンクからパスワードを設定して登録を完了する招待制ユーザー登録フローを構築する。以下を担保する:

- 登録済みメールへの招待拒否（§4）
- 有効な pending 招待（未受諾・期限内）の重複送信拒否、**72時間の有効期限切れ後は再招待可**（§4 / §5）
- 招待トークンの72時間有効期限（§5）と既存の部分ユニークインデックス `invitation_email_pending_unique` の活用（LAP-001）
- 招待リンクからのパスワード設定登録、受諾後 accepted で再利用不可、期限切れ/使用済み/不正トークンのエラー処理（§4）
- トークン生成・検証ロジックの単体テスト（§9）

本チケットは LAP-002（認証基盤）に依存し、`getCurrentUser()`(isAdmin) / `requireUserId()` / `hashPassword` / `prisma` / `signIn` を再利用する。

## 3. 設計方針

### 3-A. expired pending の再招待ハンドリング（核論点）

**採用案: ① enum に `expired` を追加し、再招待時に既存の期限切れ pending を `expired` へ遷移させてから新規 INSERT する（軽微マイグレーション 1 本）。**

投資対効果と整合性で選定。理由:

- 部分ユニークインデックスは `WHERE status = 'pending'` に効く。`expired` へ遷移させた瞬間にその行はインデックス対象外になり、**新規 pending の INSERT がユニーク衝突しない**。インデックスを一切変更せず（LAP-001 の制約をそのまま活かす）、DB レベルで「有効 pending は同一メール1件」という不変条件を維持できる。
- 監査性が高い。「招待されたが期限切れになった」事実が履歴として残り、再招待の経緯が追える（②削除は履歴消失、③同レコード再利用は acceptedAt 等の意味が曖昧化し再利用時の整合検証が増える）。
- アプリ層のロジックがシンプル。「pending かつ expiresAt > now」を有効招待、「pending かつ expiresAt ≤ now」を遅延的に expired へ片付ける、という素直な状態機械になる。
- マイグレーションは enum 値の追加のみ（`ALTER TYPE "InvitationStatus" ADD VALUE 'expired';`）。既存データ・インデックス・他テーブルへの影響なし。**新規マイグレーション 1 本**として追加する（既存 `_init` は編集しない）。

**expired への遷移タイミング（遅延評価）:** 専用バッチは設けない。再招待送信時に「同一メールの pending かつ expiresAt ≤ now の行があれば expired に更新してから新規 INSERT」をトランザクション内で行う（§4 処理フロー B）。期限切れ pending の掃除は再招待のトリガでのみ実行すれば足り（有効招待の重複判定は expiresAt で行うため expired 化の遅延は判定に影響しない）、複雑な常駐ジョブを避ける。

**代替案と却下理由（§3-A）:**
| 案 | 却下理由 |
|---|---|
| ② 既存 expired pending を DELETE して再 INSERT | 招待履歴が消える（監査性低下）。物理削除は invitedBy リレーション等の意図も失う。enum 追加を避けられる利点はあるが履歴喪失のデメリットが上回る |
| ③ 同レコード再利用（token・expiresAt を UPDATE し status=pending 維持） | INSERT が無く一見シンプルだが、createdAt が初回のまま・「再招待＝新しい招待」という事実が表現できず、acceptedAt 等のクリア漏れリスク。再招待回数や送信履歴の追跡も不可。判定ロジックは結局 expiresAt 比較が必要で簡潔さの利点も限定的 |

> 補足: enum 追加により受諾・検証ロジックは「status === 'pending' のみを有効候補」とする現行方針で一貫する（accepted / expired はいずれも無効）。

### 3-B. 重複/登録済み判定ロジック

招待送信（server action）の判定順序とトランザクション境界:

1. **認可**: `getCurrentUser()` が null または `isAdmin === false` なら拒否（§3-F）。
2. **入力検証**: email を正規化（trim + 小文字化）。形式不正なら拒否。
3. **登録済み判定**: `prisma.user.findUnique({ where:{ email } })` が存在 → 拒否（「既に登録済み」エラー）。
4. **有効 pending 判定 + expired 掃除 + INSERT を 1 トランザクションで原子化**（`prisma.$transaction`）:
   a. 同一 email の `status='pending'` 行を取得。
   b. その中に `expiresAt > now` があれば → 拒否（「有効な招待が既に存在」エラー）。トランザクションを中断（INSERT しない）。
   c. `expiresAt ≤ now`（期限切れ pending）があれば `status='expired'` へ更新（§3-A）。
   d. トークン生成（§3-C）・`expiresAt = now + 72h`・`status='pending'`・`invitedById = 現在の管理者 id` で新規 INSERT。
   e. 万一の競合（部分ユニーク衝突 = 別リクエストが同時に有効 pending を作った）は INSERT 時に DB が弾く。Prisma の P2002 を捕捉して「有効な招待が既に存在」エラーへ写像（TOCTOU 対策・DB を最終防壁とする）。
5. **メール送信はトランザクションの外**（コミット後）。送信失敗時のハンドリングは §3-D。

> トランザクション境界をユーザー存在チェックではなく「expired 掃除 + INSERT」に置くのは、部分ユニークインデックスとの競合（期限切れ行を消す前に新規を入れると衝突）を原子的に解消するため。ユーザー存在チェックは race の窓が狭く、最終防壁は User.email の `@unique` と受諾時の整合（§3-E）で担保する。

### 3-C. トークン設計

- **生成**: Node 標準 `crypto.randomBytes(32)` を base64url（または hex）でエンコードした暗号学的乱数文字列。推測不能・URL セーフ。外部依存を増やさない。
- **DB 保存形式**: **平文で保存する**。理由 = 既存の `Invitation.token @unique` および `PasswordResetToken.token @unique` がいずれも平文 token を一意キーとして検証する前提で設計されている（LAP-001/SPEC §7.6）。ハッシュ保存にすると `@unique` での O(1) lookup ができず（ハッシュ照合は全件比較が必要）、既存スキーマと不整合になる。トークンは十分長い乱数（256bit）で漏洩経路はメール本文に限られ、72h で失効するため平文保存のリスクは許容範囲。**スキーマの token 列は変更しない**。
  > 将来ハッシュ化が必要になった場合は「token 列にハッシュを格納し lookup もハッシュで行う」設計変更が別途必要（本チケットでは現行 `@unique` 平文方式を踏襲し整合を優先）。
- **有効期限**: 発行時 `expiresAt = now + 72時間`（§5）。期限定数は `INVITE_EXPIRY_HOURS = 72` を1箇所に定義。
- **検証フロー**（受諾ルート / 純関数化してテスト対象に）:
  1. token で `prisma.invitation.findUnique({ where:{ token } })`。不在 → 無効。
  2. `status !== 'pending'` → 無効（accepted=使用済み / expired=期限切れ確定）。
  3. `expiresAt ≤ now` → 期限切れ（無効）。
  4. 上記すべて通過 → 有効。受諾可能。
- **検証の純粋ロジック分離**: 「与えられた invitation レコード（or 不在）と現在時刻から有効/無効と理由を返す」純関数 `evaluateInvitation(inv, now)` を切り出し、DB アクセスとは独立に単体テスト可能にする（§8）。理由種別 = `not_found | already_accepted | expired | valid`。

### 3-D. Resend 抽象化（テスタビリティ・キー無しビルド/テスト緑）

メール送信をインターフェース `Mailer` に抽象化し、招待のビジネスロジック（重複/期限判定・トークン生成検証）を送信から完全分離する。

- **インターフェース**: `Mailer.sendInvitation({ to, inviteUrl }): Promise<{ ok: true } | { ok: false; error: string }>`（送信は throw でなく結果オブジェクトを返す。Resend の `{data,error}` 判別ユニオンに合わせる）。
- **実装**:
  - `ResendMailer`: `new Resend(process.env.RESEND_API_KEY)` を**遅延初期化**（モジュールトップで `new` しない。`send` 呼び出し時に初めて生成）。`resend.emails.send({ from, to, subject, text/html })` を呼び、`error` があれば `{ ok:false, error }`、`data` があれば `{ ok:true }` を返す。
  - キー解決ヘルパ `getMailer()`: `RESEND_API_KEY` 未設定なら **`NoopMailer`（送信せずログ出力して `{ok:true}` を返す or 開発用に inviteUrl をログ）**を返す。設定済みなら `ResendMailer`。これにより **キー無しでも server action 自体は動作し、ビルド・型チェック・テストが緑**になる。
- **キー無しで `npm run build` / `tsc` / `npm run test` が通る根拠**:
  - `Resend` のインスタンス化を遅延化しモジュール読み込み時に env を要求しない（トップレベル副作用なし）→ build / tsc は env 非依存で通る。
  - テストは `Mailer` をモック注入（ビジネスロジック関数に `mailer` を引数 or DI で渡す）→ 実 API キー不要・ネットワーク非依存で緑。
  - `RESEND_API_KEY` 未設定時は `NoopMailer` にフォールバックするため、ローカルで送信を伴わない動作確認も可能。
- **開発の送信元**: テスト用ドメイン `onboarding@resend.dev`（§10 本番ドメイン未定）。送信元アドレスは `MAIL_FROM` 環境変数（既定 `onboarding@resend.dev`）から読む。
- **送信失敗ハンドリング**: 招待レコードは既にコミット済み（§3-B 5）。送信失敗時は server action がユーザーへ「招待は作成したがメール送信に失敗した」旨を返し、再送（= 既存有効 pending があるので「再招待は期限切れ後」）でなく、本チケットでは**エラー表示にとどめる**（明示的な再送 UI は §10 / 後続スコープ。MVP は失敗を可視化すれば足りる）。

### 3-E. 招待受諾 → 登録フロー

- **公開ルート**: `src/app/invite/[token]/page.tsx`（middleware matcher 配下だが authorized が `/dashboard` 以外を true とするため**公開のまま**。追加除外設定は不要 — §2 で確認）。
- **GET（ページ表示）**: token を `evaluateInvitation` で検証 → 無効なら理由に応じたエラー画面（不正/期限切れ/使用済み）。有効ならパスワード設定フォームを表示（email は招待レコードの値を表示・固定）。
- **POST（受諾・server action）**: パスワード受領 → **再検証 + User 作成 + Invitation 更新を 1 トランザクションで原子化**（二重受諾防止）:
  1. トランザクション内で token を再取得し `evaluateInvitation`（valid 以外なら中断・エラー）。
  2. `passwordHash = hashPassword(password)`。
  3. `prisma.user.create({ data:{ email: invitation.email, passwordHash, isAdmin:false } })`。User.email の `@unique` が最終防壁（同時受諾・既存ユーザー化を弾く・P2002 は「既に登録済み」へ写像）。
  4. `prisma.invitation.update({ where:{ token }, data:{ status:'accepted', acceptedAt: now } })`。**条件付き更新で二重受諾を防ぐ**: 更新対象を `status='pending'` に限定（`updateMany({ where:{ token, status:'pending' }})` の affected=0 なら既に受諾済みとして中断）。
  5. パスワード強度の最小検証（長さ等。詳細は実装時。最低限の長さチェックを純関数化してテスト）。
- **受諾後の導線**: **受諾完了後に自動 signIn せず `/login` へ誘導する**（成功メッセージ付き）。理由 = `signIn("credentials", { redirectTo })` は server action 内で動くが、受諾フローは「アカウント作成」と「ログイン」を分離した方が（a）パスワード入力の確認と初回ログインの動作確認が自然、（b）signIn の例外/redirect 制御が受諾トランザクションと混線しない、（c）LAP-002 の login server action をそのまま再利用でき複雑性が増えない。自動ログインは UX 改善として後続検討可（§10 注記・ブロッカーにしない）。
- **エラー処理**: 不正/期限切れ/使用済みトークン、既に登録済み email、二重受諾はいずれも専用メッセージで表示する。

### 3-F. 送信 UI と認可

- **配置**: `(protected)` 配下に管理者専用の招待送信 UI を置く。具体的には `src/app/(protected)/admin/invite/page.tsx`（管理者専用エリア）。
- **認可（多層）**:
  - middleware（`/dashboard` のみ保護）では `/admin/*` は現状カバーされない → **`authorized` の保護判定に `/admin` を追加するか、ページ側 server-side で `getCurrentUser()` を必須化**する。本設計は **(1) `src/auth.config.ts` の `authorized` に `/admin` 配下を保護対象として追加**（未認証は /login へ）し、**(2) ページ/サーバアクション冒頭で `getCurrentUser()?.isAdmin` を必須チェック**（非管理者は 403 相当 = `notFound()` または `/dashboard` リダイレクト）する二層防御とする。認可はサーバ側で必ず行い、UI の出し分けだけに依存しない。
- **実装方式**: **server action**（LAP-002 の login と同じ方式）。フォーム（email 入力）→ server action `sendInvitation(formData)` → 認可チェック → §3-B の判定 → §3-D の送信 → 結果（成功/各種エラー）を画面に反映。
- **スコープ厳守**: 管理者フラグの付与/剥奪（LAP-004）・招待取り消し UI・パスワードリセット（LAP-005）は実装しない。`/admin/invite` は招待送信のみ。

implementer は **develop 起点**で `feature/LAP-003-invitation-flow` を作成する（LAP-002 までマージ済み）。コミットは `[LAP-003]` プレフィックス。push は人間。

### 採用方針サマリ

**採用する方針:** ① enum に `expired` 追加（再招待は expired 化→新規 INSERT・トランザクション原子化）/ token は crypto.randomBytes 256bit を平文 `@unique` 保存（既存方式踏襲）・72h 失効 / `Mailer` 抽象化 + 遅延初期化 + キー無し NoopMailer フォールバックで build/tsc/test 緑 / 受諾は再検証+User作成+Invitation条件付き更新の原子化・受諾後は /login 誘導 / 招待UIは `(protected)/admin/invite` で server action・二層認可。

**代替案と却下理由（全体）:**
| 案 | 却下理由 |
|---|---|
| expired を enum 追加せず ②削除 / ③再利用 | §3-A の通り（履歴喪失 / 整合の曖昧化） |
| token をハッシュ保存 | 既存 `@unique` 平文方式と不整合・O(1) lookup 不可（§3-C） |
| Resend を直接 server action で `new Resend` | テスト不能・キー無しで import 時に落ちるリスク。抽象化と遅延初期化で回避（§3-D） |
| 受諾後に自動 signIn | 受諾トランザクションと signIn の redirect/例外が混線・複雑化。/login 誘導で LAP-002 を再利用（§3-E） |
| 招待 UI を `/dashboard` 内に置く | 管理者専用領域を分離した方が認可境界が明確。`/admin` 配下に集約 |
| 認可を UI 表示の出し分けのみで行う | クライアント側制御は迂回可能。server-side `getCurrentUser().isAdmin` 必須（§3-F） |

```typescript
// src/lib/invitation.ts — 純ロジック（DB/メール非依存・テスト対象）
export const INVITE_EXPIRY_HOURS = 72;

/** crypto.randomBytes による URL セーフな招待トークンを生成する（256bit）。 */
export function generateInviteToken(): string;

/** 発行時刻から有効期限（now + 72h）を算出する。 */
export function computeExpiry(now: Date): Date;

export type InvitationCheck =
  | { valid: true }
  | { valid: false; reason: "not_found" | "already_accepted" | "expired" };

/** 招待レコード（or null）と現在時刻から有効/無効を判定する純関数。 */
export function evaluateInvitation(
  inv: { status: "pending" | "accepted" | "expired"; expiresAt: Date } | null,
  now: Date,
): InvitationCheck;

/** 招待リンク URL を組み立てる（base URL は環境変数 / 引数で受ける）。 */
export function buildInviteUrl(baseUrl: string, token: string): string;

/** 受諾時のパスワード最小要件（長さ等）を検証する純関数。 */
export function validateInvitePassword(pw: string): { ok: true } | { ok: false; error: string };

// src/lib/mailer.ts — 送信抽象化
export interface Mailer {
  sendInvitation(args: { to: string; inviteUrl: string }):
    Promise<{ ok: true } | { ok: false; error: string }>;
}
/** RESEND_API_KEY 未設定なら NoopMailer、設定済みなら ResendMailer を返す（遅延初期化）。 */
export function getMailer(): Mailer;
```

**処理フロー:**

A. 招待送信（管理者 / `(protected)/admin/invite` server action）
```
1. 認可: const me = await getCurrentUser(); if (!me || !me.isAdmin) → 拒否（notFound / redirect）
2. email = normalize(formData.email)（trim + toLowerCase）。形式不正 → エラー返却
3. 登録済み判定: prisma.user.findUnique({where:{email}}) あり → 「既に登録済み」エラー
4. prisma.$transaction(async (tx) => {
     a. const pendings = await tx.invitation.findMany({ where:{ email, status:"pending" } })
     b. if (pendings.some(p => p.expiresAt > now)) → throw 有効招待重複（→ エラー写像）
     c. const expired = pendings.filter(p => p.expiresAt <= now)
        if (expired.length) await tx.invitation.updateMany({
          where:{ id:{ in: expired.map(e=>e.id) } }, data:{ status:"expired" } })
     d. const token = generateInviteToken()
        await tx.invitation.create({ data:{
          email, token, status:"pending",
          expiresAt: computeExpiry(now), invitedById: me.id } })
        // P2002（部分ユニーク衝突）は捕捉して「有効招待重複」へ写像（TOCTOU 最終防壁）
   })
5. （コミット後）const mailer = getMailer();
   const r = await mailer.sendInvitation({ to: email, inviteUrl: buildInviteUrl(baseUrl, token) })
   if (!r.ok) → 「招待は作成したがメール送信に失敗」エラー表示
   else → 成功表示
```

B. 受諾ページ表示（公開 `/invite/[token]` GET）
```
1. const inv = await prisma.invitation.findUnique({ where:{ token } })
2. const check = evaluateInvitation(inv, now)
3. check.valid === false → reason に応じたエラー画面（不正/使用済み/期限切れ）
4. valid → email(=inv.email) を表示するパスワード設定フォームを描画
```

C. 受諾（公開 `/invite/[token]` POST server action）
```
1. password = formData.password; const pv = validateInvitePassword(password)
   if (!pv.ok) → エラー再表示
2. prisma.$transaction(async (tx) => {
     a. const inv = await tx.invitation.findUnique({ where:{ token } })
        const check = evaluateInvitation(inv, now); if (!check.valid) → throw（理由付き）
     b. const passwordHash = await hashPassword(password)
     c. await tx.user.create({ data:{ email: inv.email, passwordHash, isAdmin:false } })
        // User.email @unique が最終防壁。P2002 → 「既に登録済み」
     d. const upd = await tx.invitation.updateMany({
          where:{ token, status:"pending" }, data:{ status:"accepted", acceptedAt: now } })
        if (upd.count === 0) → throw 二重受諾（既に accepted）
   })
3. 成功 → /login?accepted=1 へ redirect（ログイン誘導・成功メッセージ）
   失敗 → 理由別エラー表示
```

D. Mailer 遅延初期化（キー無しでも build/test 緑）
```
getMailer():
  const key = process.env.RESEND_API_KEY
  if (!key) return new NoopMailer()       // 送信せず inviteUrl をログ。{ok:true}
  return new ResendMailer(key)            // send 時に new Resend(key)（遅延）

ResendMailer.sendInvitation({to, inviteUrl}):
  const resend = new Resend(this.key)     // 呼び出し時に初期化（トップレベル副作用なし）
  const { data, error } = await resend.emails.send({
    from: process.env.MAIL_FROM ?? "onboarding@resend.dev",
    to, subject: "Lapsy への招待", text/html: 招待リンク(inviteUrl) })
  return error ? { ok:false, error: error.message } : { ok:true }
```
