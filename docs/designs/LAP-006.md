## 1. 目的

SPEC §4（Must: 学習トピックの作成・編集・削除を個人ごとに管理）を実装し、あわせて SPEC §10 の未決事項「トピック削除時のデータ整合」を確定する。トピックは「タイトル（必須）」「詳細（任意）」「期限日（任意）」を持ち、全クエリで認証セッション由来 userId によるデータ分離（§7.5）を徹底する。削除整合は横断集計（ヒートマップ・7日移動平均, §7.4）の過去 StudyRecord を欠落させない方針を採る。

**確定済みの人間判断（前提・揺らがせない）:**
- 削除整合方針 = **(a) Restrict 維持＋アーカイブ誘導**。既存 FK（`StudySession.topicId→Topic` / `StudyRecord.topicId→Topic` の onDelete Restrict）を変更しない。**マイグレーション不要**。`deletedAt` 列の追加（論理削除）は採用しない。
- 記録（StudyRecord/StudySession）を持つトピックは**物理削除を拒否**し、UI/フローで「アーカイブ（LAP-007）」へ誘導する。記録を持たないトピックのみ物理削除を許可する。
- カスケード物理削除は §7.4 違反のため**不採用**。削除（=記録なしトピックの物理消去）とアーカイブ（=記録を残したまま一覧/トピック別累計から除外, LAP-007）の責務を明確に分離する。

**architect 判断（本設計で確定）:**
- running ラン進行中トピックの削除可否 → **§3 方針 5 で「拒否」に確定**（理由も後述）。

**スコープ外（本チケットで実装しない）:**
- アーカイブ機能本体（`isArchived` のトグル UI・一覧除外・トピック別累計除外）の実装は **LAP-007**。本チケットでは「記録ありトピックはアーカイブへ誘導する」というメッセージ表示と導線（LAP-007 への案内文・遷移先プレースホルダ）までに留め、`isArchived` を変更する操作自体は実装しない。
- StudySession/StudyRecord を生成する機能（ポモドーロ実行）は LAP-009/011。本チケットはトピック CRUD が初出で、記録は存在し得るが本チケットでは作らない。
- 横断集計・ヒートマップ・移動平均の実装（§7.4）は LAP-011。本チケットは「集計の前提データ（過去 StudyRecord）を削除で壊さない」ことを担保するのみ。

## 3. 設計方針

**採用する方針:**

1. **トピック CRUD は `/dashboard/topics` 配下に置く**（edge 保護を継承）。一覧 + 作成を `topics/page.tsx`、編集を `topics/[id]/edit/page.tsx` に置く。削除は一覧/編集画面の `<form action={deleteTopic}>` から実行する。各ページ・各 server action の冒頭で `requireUserId()` を呼び、node 層でも認証・データ分離を再評価する（二層防御）。

2. **データ分離は `requireUserId()` の戻り値のみを userId として使う**（§7.5）。
   - 一覧取得: `prisma.topic.findMany({ where: { userId } })`。
   - 編集/削除対象の取得・更新・削除は必ず `where: { id, userId }` を併用し、他ユーザーの行に触れられないようにする（クライアントから来る `id` を単独で信頼しない）。
   - 更新/削除は `updateMany`/`deleteMany` の `where: { id, userId }` を用い、`count === 0` を「対象なし or 他人の行」として一様に扱う（行の存在有無を漏らさない）。

3. **バリデーション・削除可否判定は DB 非依存の純関数として `src/lib/topic.ts` に切り出す**（既存慣習・テスト容易性）。隣に `src/lib/topic.test.ts` を置く。
   - 入力検証 `validateTopicInput`: タイトル trim 後 1〜N 文字（必須）、詳細は任意（trim、空文字は null 正規化）、期限日は任意（空文字は null、文字列はパース可否を検証）。サーバ側で正規化済みの値だけを DB に渡す。
   - 削除可否判定 `evaluateTopicDeletion`: 「記録（StudyRecord/StudySession）の有無」と「running ランの有無」から削除可否を判定する純関数。DB から数えた件数を入力として受け取り、`{ ok: true } | { ok: false; reason }` を返す（admin-guard と同じ形）。最終的な整合の「正」は DB の FK Restrict（後述 §3-4）。

4. **削除整合は「FK Restrict 維持」を一次防御、「純関数プリチェック」を UX 層、両者を多層防御として組む**。
   - 削除フロー: server action が (i) running ラン件数 (ii) StudyRecord 件数 (iii) StudySession 件数 を `userId+topicId` で数え、`evaluateTopicDeletion` で判定 → 削除可なら `deleteMany({ where: { id, userId } })`、削除不可なら削除せず ResultBanner で「記録があるためアーカイブしてください（LAP-007）」と誘導する。
   - 二次防御: もしプリチェックと実削除の間で記録が生成された場合でも、FK Restrict により DB が `P2003`（外部キー制約違反）を投げる。server action は `P2003` を捕捉し、削除可否判定と同じ「アーカイブ誘導」結果へフォールバックする（TOCTOU 対策。admin/users の原子 UPDATE と同じ思想で、DB 側を最終権威にする）。
   - これにより、記録を持つトピックの過去 StudyRecord は決して物理削除されず、§7.4 の横断集計（アーカイブ済み含む過去履歴）の前提が保たれる。

5. **running ラン進行中トピックの削除可否 = 「拒否」**（architect 判断・確定）。
   - **理由**: (a) running ラン中のトピックは「現に学習が進行中」であり、削除のユースケースとして不自然。(b) 削除を許すと `studysession_user_running_unique`（1ユーザー1 running）が指す進行中ランの親トピックが消える整合崩れを招く。(c) running ランは必ず StudySession 行を持つため、そもそも §3-4 の FK Restrict で物理削除は拒否される（running は記録ありの一形態）。(d) ただし「記録あり（=アーカイブ誘導）」と「running 進行中（=ラン終了が先）」はユーザーへの案内文を分けたい。
   - よって `evaluateTopicDeletion` は running を**最優先で判定**し、`reason: "running"` を返して「実行中のランを終了してから操作してください」と案内する（記録ありより具体的なメッセージ）。running が無く記録のみある場合は `reason: "has_records"` でアーカイブ誘導。記録も running も無ければ `ok: true` で物理削除を許可する。

6. **作成・編集も同じ薄い server action パターン**にする。`<form action={createTopic|updateTopic}>` → `requireUserId()` → `validateTopicInput` → DB 反映 → `revalidatePath("/dashboard/topics")` → `redirect("?result=...")` → `ResultBanner`。バリデーション失敗時は DB に触れず結果コードで通知する。

7. **論理削除（deletedAt 列追加）は採用しない**。理由: マイグレーション増・全 Topic クエリへ `deletedAt IS NULL` 条件を横展開するコストが発生し、かつ「記録を残したまま一覧から消す」需要は LAP-007 のアーカイブ（`isArchived`）が既に満たす。削除は「記録なしトピックの物理消去」に限定し、責務を単純化する。

**削除とアーカイブの責務分界（明確化）:**

| 操作 | 対象 | DB 上の挙動 | 過去 StudyRecord | 横断集計（§7.4） | 担当チケット |
|---|---|---|---|---|---|
| 削除（本チケット） | **記録なし**トピックのみ | 行を物理 DELETE | そもそも無い | 影響なし | LAP-006 |
| アーカイブ（後続） | 記録ありトピック | `isArchived=true`（行は残す） | 残る | 含めて集計（過去欠落なし） | LAP-007 |
| カスケード物理削除 | — | — | — | **§7.4 違反のため不採用** | — |

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| (b) 論理削除（`deletedAt` 列追加） | マイグレーション要・全 Topic クエリへ条件横展開。アーカイブ（LAP-007）と需要が重複。人間判断で (a) に確定済み |
| (c) カスケード物理削除（FK を Cascade に変更） | 過去 StudyRecord が欠落し §7.4（アーカイブ含む過去履歴を欠落させない）に違反。選択肢から除外（確定事項） |
| FK Restrict を変更してマイグレーションを打つ | (a) は既存 Restrict をそのまま使うため不要。schema/FK を触らないことが最小変更で一貫 |
| running トピックの削除を許可（強制 abort してから削除） | ラン進行中の親トピック消去は整合・UX 双方で不自然。running は必ず記録ありで Restrict 対象。終了を先に促す方が安全（§3-5） |
| クライアント入力 id を `where:{id}` のみで使う | 他ユーザーの行を操作され得る（データ分離違反・§7.5）。必ず `{id, userId}` 併用 |
| プリチェックのみで FK Restrict に頼らない | TOCTOU で記録生成と削除が競合し得る。DB の Restrict を最終権威にする多層防御が必要（§3-4） |

**主要なインターフェース（型・I/F 素案。実装は implementer）:**
```typescript
// src/lib/topic.ts — DB 非依存の純ロジック

export const MAX_TITLE_LENGTH = 200;          // タイトル上限（実装時に SPEC と齟齬なければ採用）

export type TopicInput = {
  title: string;
  description?: string | null;
  deadline?: string | null;                    // フォーム由来の文字列（"" は未指定）
};

export type NormalizedTopic = {
  title: string;
  description: string | null;
  deadline: Date | null;
};

// 入力検証 + 正規化。失敗時は理由コードを返し、DB へは渡さない。
export function validateTopicInput(
  input: TopicInput,
): { ok: true; value: NormalizedTopic } | { ok: false; reason: "title_required" | "title_too_long" | "invalid_deadline" };

// 削除可否判定（DB から数えた件数を受け取る純関数）。
// 判定順: running > 記録あり > 削除可。最終権威は DB の FK Restrict（§3-4）。
export function evaluateTopicDeletion(input: {
  runningSessionCount: number;   // この userId+topicId の status=running な StudySession 件数
  studyRecordCount: number;      // この userId+topicId の StudyRecord 件数
  studySessionCount: number;     // この userId+topicId の StudySession 件数（running 以外も含む）
}): { ok: true } | { ok: false; reason: "running" | "has_records" };
```
```typescript
// server action の結果コード（ResultBanner で文言化）
type TopicResultKind =
  | "created" | "updated" | "deleted"
  | "title_required" | "title_too_long" | "invalid_deadline"
  | "not_found"            // 対象なし or 他ユーザーの行（区別せず一様）
  | "delete_running"       // running ラン進行中 → 終了を促す
  | "delete_has_records";  // 記録あり → アーカイブ（LAP-007）へ誘導
```

**処理フロー:**

A. 作成（createTopic）
```
1. requireUserId() で userId を確定（未認証は /login へ）
2. FormData から title/description/deadline を取得
3. validateTopicInput → 失敗なら redirect("/dashboard/topics?result=<reason>")（DB に触れない）
4. prisma.topic.create({ data: { userId, ...normalized } })
5. revalidatePath("/dashboard/topics") → redirect("?result=created")
```

B. 編集（updateTopic）
```
1. requireUserId() で userId 確定
2. FormData から id/title/description/deadline 取得
3. validateTopicInput → 失敗なら ?result=<reason>
4. prisma.topic.updateMany({ where: { id, userId }, data: normalized })
   - count === 0 → ?result=not_found（他人の行 or 不在を一様に扱う・データ分離）
5. revalidatePath → ?result=updated
```

C. 削除（deleteTopic）— 削除整合の核
```
1. requireUserId() で userId 確定
2. FormData から id 取得
3. 件数集計（全て userId+topicId でフィルタ・データ分離）:
   - runningSessionCount = studySession.count({ where:{ userId, topicId:id, status:"running" } })
   - studyRecordCount    = studyRecord.count({ where:{ userId, topicId:id } })
   - studySessionCount   = studySession.count({ where:{ userId, topicId:id } })
4. evaluateTopicDeletion(...) で判定:
   - reason "running"     → ?result=delete_running（削除しない・ラン終了を促す）
   - reason "has_records" → ?result=delete_has_records（削除しない・アーカイブ誘導 LAP-007）
   - ok                   → 5 へ
5. 物理削除（記録なしのみここに到達）:
   try {
     const { count } = await prisma.topic.deleteMany({ where:{ id, userId } });
     if (count === 0) → ?result=not_found
   } catch (P2003) {            // TOCTOU: 直前に記録が生成された
     → ?result=delete_has_records（FK Restrict を最終権威にフォールバック）
   }
6. revalidatePath → ?result=deleted
```

D. 一覧表示（topics/page.tsx）
```
1. requireUserId() → userId
2. const topics = await prisma.topic.findMany({
     where: { userId },              // ← データ分離
     orderBy: [{ createdAt: "desc" }],
     // 一覧表示に必要なフィールドを select。本チケットでは isArchived の出し分けは LAP-007 に委ねる
   });
3. 作成フォーム + 各トピックの編集/削除フォーム + ResultBanner を描画
```

**ResultBanner の文言（要点）:**
- `delete_running`: 「このトピックは実行中のランがあります。ランを終了してから操作してください。」
- `delete_has_records`: 「このトピックには学習記録があるため削除できません。記録を残す場合はアーカイブをご利用ください（アーカイブは後続機能 LAP-007）。」
- `not_found`: 「対象のトピックが見つかりませんでした。」
- 検証系（`title_required`/`title_too_long`/`invalid_deadline`）はフォーム入力エラーとして表示。

## 6. リスク

| リスク | 深刻度 | 軽減策 |
|---|---|---|
| プリチェックと実削除の間に記録が生成される TOCTOU | medium | FK Restrict を最終権威とし、`deleteMany` の `P2003` を捕捉して `delete_has_records` へフォールバック（§3-4・§4-C） |
| クライアント入力 id で他ユーザーの行を操作 | high | 全クエリ `where:{ id, userId }` 併用。`requireUserId()` 由来 userId のみ使用。`count===0` を一様に not_found 扱い（存在有無を漏らさない） |
| 削除可否判定が DB と乖離（漏れ）し記録を物理削除 | high | 純関数判定は UX 層であり、DB の Restrict が「正」。判定漏れがあっても物理削除は DB が拒否（多層防御） |
| 期限日の文字列パースで不正値を DB に渡す | low | `validateTopicInput` で Date 変換可否を検証し、不正は `invalid_deadline` で拒否（DB に触れない） |
| running 判定の意味が「記録あり」と被り冗長 | low | running は必ず StudySession 行を持ち Restrict 対象だが、案内文を分けるため最優先で個別 reason を返す（§3-5）。整合上の害はない |
| isArchived の一覧出し分けを本チケットでやり過ぎる | low | アーカイブの除外ロジックは LAP-007 スコープ。本チケットは全件表示 + 削除導線に留める |
| タイトル上限値が SPEC と不一致 | low | `MAX_TITLE_LENGTH` は実装時に SPEC §4/§7 と照合。未規定なら 200 を採用しテストで固定 |

## 7. マイグレーション戦略

**マイグレーション不要（Restrict 維持）。**

- 既存 FK（`StudySession.topicId→Topic` / `StudyRecord.topicId→Topic` = onDelete Restrict、init マイグレーションで適用済み）を**変更しない**。
- `Topic` モデルにフィールド追加・削除を行わない（`deletedAt` 列も追加しない＝論理削除不採用）。
- よって `prisma/schema.prisma` および `prisma/migrations/` は本チケットで一切変更しない。`npm run prisma:validate` は現状のまま通る想定。
- 削除整合は「既に DB にある Restrict」をアプリ層が利用するだけで、スキーマ変更を伴わない。

## 8. ロールバック戦略

本チケットは新規ファイル追加（純関数 + 2 ページ）のみで、schema/migration を触らないため、コミット単位の revert で完全に原状回復できる。DB 側のロールバックは不要。

```bash
git log --oneline
git revert <コミットハッシュ>
# 例: [LAP-006][REVERT] 学習トピックCRUDの取り消し
```
- マイグレーションが無いため DB reset は不要。
- CLAUDE.md ロールバック規約に従い、done/→active/ 戻し・status を implementation_done に戻す運用は orchestrator が担当。
