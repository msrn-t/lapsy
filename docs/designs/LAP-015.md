## 1. 目的

LAP-014 で導入した共通 app shell（`(protected)/layout.tsx` がサイドナビ + トップバー + `<main>`(padding) を提供）の上に、`(protected)` 配下 7 ページのコンテンツレイアウトを各ワイヤーフレーム（docs/wireframes/04〜10）の構造へ整合させる。WF はグレースケール単色・ダーク非対応であり、`globals.css @theme` の既存トークン（`bg-card` `border-line` `text-ink/-dim` `rounded-card/-ctl` `bg-btn` 等）で表現する。

加えて、人間判断 U1（チケット LAP-015 ログ 2026-06-22 13:05）により、WF にあって現実装に無いデータ表示を**すべて本チケットに含める**:
- (a) Dashboard KPI 4 枚（総学習時間 / 今日 / 7 日平均 / アクティブ数）
- (b) Topics / Archived カードの per-topic 累計学習時間
- (c) Admin-users の 名前・登録日 列
- (d) Admin-invite の 招待履歴テーブル + 再送導線（pending/accepted/expired 一覧クエリ + 再送 server action 新規）

機能（集計・CRUD・認可・データ分離・既存 server action の挙動）は維持し、新規クエリも `requireUserId()` / `requireAdminId()` 由来のスコープを必ず守る（SPEC §5 データ分離 / §7.5）。

**中核ギャップ（investigator 調査メモ）:**
1. **二重 chrome**: dashboard 以外の 6 ページ + 2 edit ページが、shell が既に提供する `<main>`/`<h1>`/`py-12` を自前で重複して持つ → `<main>` 入れ子・余白二重・見出し二重。
2. **デザイン言語不一致**: `gray-*`/`blue-*`/`dark:*` を多用。WF はグレースケール単色・ダーク非対応 → トークン置換 + `dark:` 撤去。
3. **構造不一致 + 欠落データ**: KPI 4 枚（04）、cards c3 カードグリッド（05/06/08）、timer-ring/prog（07）、招待履歴テーブル（09）、tbl テーブル + 名前/登録日（10）。

**壊してはいけない結合（investigator Risk・本設計の不変条件）:**
- ① **server action のフォーム結合**: 各 `<form action={...}>` と `<input name>`（`createTopic`/`archiveTopic`/`deleteTopic`/`restoreTopic`/`updateTopic` の hidden `id`、`startSession`/`abortSession` の `topicId`/`presetId`/`id`、`createPreset`/`deletePreset`/`updatePreset`、`toggleAdmin` の `targetId`/`action`、`invite` の `email`、`LapRows` の `lap-${i}-workSec`/`lap-${i}-breakSec` 名と `collectLaps` の対応）を**一切変えない**。
- ② **認可・データ分離**: `requireUserId()`/`requireAdminId()`、Prisma の `where:{userId}`/`where:{id,userId}`、admin の条件付き原子 UPDATE（`$executeRaw`）は不変。新規クエリも同じスコープを守る。
- ③ **`_timer.tsx` の props 契約**: `initial`(SessionState)/`startedAt`(ISO 文字列)/`snapshot`(LapConfig[])。`deriveSessionState` を毎秒再導出しサーバー時刻が正。リング/進捗バーは `state.segmentElapsedSec/segmentTotalSec`（と `state.elapsedSec/deadlineSec`）からの算出に限る。**新規の DB 読み書き・props 追加はしない**。
- ④ **`nav.ts` のタイトル文字列を変更しない**（`nav.test.ts` が `pageTitleForPath` の戻り値に依存）。WF の per-page 微細タイトル（「トピック / アーカイブ」「管理 / 招待」等）が欲しい場合も `nav.ts` は触らず、各 page 内のコンテンツ見出し（`section-label`/`link` 戻り導線）で表現する。
- ⑤ **DOM/testid 依存テストは無し**（全テストは node 環境の純ロジック）。本チケットの追加テストも純ロジックに限定する。

**関連する既存ファイル:**

## 3. 設計方針

### 3.0 採用する方針（まとめ）

1. **二重 chrome 撤去**: dashboard 以外の 6 ページ + 2 edit ページから、自前 `<main className="...max-w-*...py-12">` と最上位 `<h1>` を撤去する。shell の `<main>`(padding) + Topbar タイトルがこれを担う。各 page のルート要素は `<div className="flex flex-col gap-...">`（または WF の `page-h` を再現する要素）に置き換える。最大幅が必要なページ（フォーム中心の admin-invite・各 edit・timer 実行カード）は WF に従い `max-w-*` をルート直下の要素に局所適用する（shell `<main>` は全幅のまま）。
2. **トークン整合（`dark:` 撤去）**: `gray-*`/`blue-*`/`green-*`/`red-*`/`amber-*` と全 `dark:*` を WF トークンへ置換する。対応表は §3.1。「成功/エラー」のセマンティックカラーも WF は単色のため、成功 = 通常枠（`border-line`）+ ink、エラー = `border-error`（破線）+ `text-error` に寄せる（WF `.form-error`/`.err-msg` 準拠）。
3. **WF コンポーネントの Tailwind 写経**: WF の `.card`/`.kpi`/`.cards.c3`/`.tbl`/`.badge`/`.switch`/`.timer-ring`/`.prog`/`.chip`/`.btn` を Tailwind ユーティリティ + 既存トークンで再現する（§3.1 のクラス対応表）。CSS の新規追加（globals.css への追記）は原則しない。例外として timer-ring の円弧進捗（conic-gradient）と switch のような複雑形状は inline style / 単純な擬似実装に留める（§4 各ページ）。
4. **新規データ (a)-(d) の所在と認可**:
   - (a) KPI: 集計純ロジックを `src/lib/aggregate.ts` に **新規純関数として追加**（`computeDashboardKpis`）。DB クエリは `dashboard/page.tsx`（server component）内で `userId` フィルタして取得し、純関数へ渡す。
   - (b) per-topic 累計: 既存 `joinTopicTotals`（topics 一覧の id↔累計）を topics ページでも使う。topics/page.tsx・archived/page.tsx の server component に `studyRecord.groupBy({ by:["topicId"], where:{ userId } })` を追加し、カードに `formatHm` で表示。
   - (c) 名前・登録日: admin-users/page.tsx の `user.findMany` の `select` に `name`/`createdAt` を追加（admin スコープは `requireAdminId()` 済・全ユーザー対象は仕様どおり）。
   - (d) 招待履歴 + 再送: admin-invite/page.tsx の server component に `invitation.findMany({ where:{ ... } })`（admin 限定ページ・**メールアドレス横断**は招待管理の仕様上正当）を追加。再送は **新規 server action `resendInvite`** をページ内に定義し、既存 `invite` の token 発行・一様 ACK 方針と整合させる（§4-Admin-invite）。
5. **純ロジックの単体テスト**: KPI 算出（`computeDashboardKpis`）と、必要なら timer の進捗率算出ヘルパ（`segmentProgressRatio` 等）を純関数として切り出し `*.test.ts`（node）で検証する。描画（DOM）テストは追加しない（環境未導入・scope 外）。

### 3.2 軽微 Unknown の確定（investigator U2/U3）

| # | 論点 | 決定 |
|---|---|---|
| U2 | 作成/編集フォームをモーダル化するか | **常時展開のまま整える**（モーダル化しない）。理由: WF はモーダルを「注記（notes）」で示すのみで、現実装は server action + `?result=` リダイレクトの SSR フォーム。モーダル化は client state / dialog 導入 = scope 肥大で、フォーム name 結合（不変条件①）のリスクが上がる。トピック/プリセットの新規作成は WF の `.card` に収めた常時展開フォーム、編集は既存の独立 edit ルートを WF カード調に整える。**「＋ 新規」ボタンはページ内フォームへのアンカー/見出し**として残す。 |
| U3 | timer の準備/実行を chip タブで見せるか | **装飾の chip を WF どおり表示するが、実体は `running` 有無の分岐を維持**。準備モードでは `準備`=active chip + `実行中`=idle chip、実行モードでは逆。chip はナビゲーション要素ではなく状態表示（クリックで遷移はしない／`running` の有無で自動決定）。 |

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| 作成/編集をモーダル化（client dialog） | client state 増・フォーム name 結合の改修リスク・scope 肥大。SSR + `?result=` の現行フローを崩す |
| KPI 算出を page.tsx 内にインラインで書く | テスト不能。`aggregate.ts` の純関数方針（time/TZ 注入・node テスト）と不整合 |
| timer-ring を SVG circle + stroke-dasharray で厳密実装 | MVP 過剰。conic-gradient（CSS）で十分に WF を再現でき、`segmentProgressRatio` 純関数でテストできる |
| 招待履歴の再送で新トークンを発行せず既存 token を再送 | 既存 `invite` は期限切れ pending を expired 化して新規発行する設計。再送も同方針（期限延長 = 新トークン）に揃える方が一貫（§4-Admin-invite） |
| WF の微細グレーを globals.css に新トークン追加 | トークン語彙の肥大。数箇所の装飾は arbitrary value で足り、共通基盤を汚さない |

## 4. 実装詳細（ページ別）

各ページ共通: **ルートから自前 `<main>`/`<h1>`/`py-12` を撤去**し、`<div className="flex flex-col gap-6">` 等に置換。`ResultBanner` は WF の単色（成功=`border-line`、エラー=`border-dashed border-error text-error`）へトークン整合（name/挙動は不変）。

### 4-1. Dashboard（04 → dashboard/page.tsx・_charts.tsx）

**WF 構造**: KPI `cards c4`（総学習時間 / 今日 / 7 日平均 / アクティブ）→ `cards c2`（ヒートマップ / 7 日移動平均）→ `cards c2`（トピック別累計バー / 期限カウントダウン）。

**採用マークアップ**: ルート `<div className="flex flex-col gap-4">`。①KPI 行 = §3.1 `cards.c4`、各 KPI は `.kpi`。②③④⑤ は `.card` を `grid gap-4 lg:grid-cols-2` で 2 段。各 `.card` 内に `section-label` 見出し + 既存チャート。`_charts.tsx` の `TopicTotalsChart`/`HeatmapChart`/`MovingAverageChart`/`CountdownList` は**ロジック不変・配色のみトークン化**（`bg-blue-500`→`bg-line-strong`、heatmap の green 段階→WF の `#E6E6E6/#D2D2D2/#B4B4B4/#979797/#7C7C7C` グレー段階、`dark:*` 撤去）。

**維持すべき form/name/server action**: dashboard は server action 無し（読み取り専用）。`requireUserId()` と全 `where:{userId}` クエリは不変。

**新規クエリ (a) KPI — 所在: dashboard/page.tsx server component / 認可: `requireUserId()` 由来 userId**:
- 総学習時間 = 全 StudyRecord の `SUM(countedSeconds)`（アーカイブ含む＝全期間累計）: `prisma.studyRecord.aggregate({ where:{ userId }, _sum:{ countedSeconds:true } })`。
- 今日 = 既存 `daily` 系列の末尾日（`endKey`）の totalSeconds（既存 `fillDailySeries` 結果を再利用・追加クエリ不要）。
- 7 日平均 = 既存 `ma`（movingAverage）の末尾点 `averageSeconds`（追加クエリ不要）。
- アクティブ数 = 既存 `activeTopics.length`（`topic.findMany({ where:{ userId, isArchived:false } })`・追加クエリ不要）。

→ 追加 DB クエリは **総学習時間の aggregate 1 本のみ**。残り 3 つは既存集計から導出。これらを純関数 `computeDashboardKpis` に集約:
```ts
// src/lib/aggregate.ts に追加（DB 非依存・テスト対象）
export type DashboardKpis = {
  totalSeconds: number;       // 全期間累計（aggregate から注入）
  todaySeconds: number;       // daily 末尾日
  sevenDayAvgSeconds: number; // ma 末尾点
  activeTopicCount: number;   // アーカイブ外トピック数
};
export function computeDashboardKpis(input: {
  totalSeconds: number;
  daily: ReadonlyArray<DailyTotal>;     // fillDailySeries 済み（昇順）
  movingAverage: ReadonlyArray<MovingAveragePoint>;
  activeTopicCount: number;
}): DashboardKpis;
// 空配列は 0 を返す（防御）。表示整形（h 単位）は _charts.tsx の formatHm を流用。
```
KPI 表示の `128h` 形式は `formatHm` の「時間」を WF 風に `h` 表記するヘルパを `_charts.tsx` に追加してよい（純粋表示・任意）。

### 4-2. Topics（05 → topics/page.tsx）

**WF 構造**: `page-h`（h3「トピック」+ spacer + link「アーカイブを見る」+ btn「＋新規トピック」）→ `cards c3`（トピックカード: タイトル / 詳細抜粋 / 期限 badge / 累計 / ⋯メニュー）。新規作成フォームは WF では notes のモーダルだが、U2 により**常時展開の `.card` フォーム**として page-h 下に置く。

**採用マークアップ**: ルート `<div className="flex flex-col gap-6">`。`page-h` 行（`flex flex-wrap items-center gap-3`）に「アーカイブ済みを表示」Link（`.link`）と作成フォームへのアンカー。作成フォーム = `.card` 内に既存 `createTopic` フォーム（name 不変）。一覧 = 行 `<ul>` を `cards c3`（§3.1）へ。各カード = `.card`、タイトル `font-fredoka`、詳細 `text-[11px] text-ink-dim`、下段に期限 `.badge`（超過は `.badge.warn`）+ 累計 `累計 {formatHm}`。編集/アーカイブ/削除は WF の「⋯メニュー」相当だが、**現行の編集 Link + アーカイブ form + 削除 form をカード内に温存**（⋯ドロップダウン化は client 化を伴うため避ける。3 つを小ボタン群でカード下部に並べる）。

**維持すべき form/name/server action**: `createTopic`（`title`/`description`/`deadline`）、`archiveTopic`（hidden `id`）、`deleteTopic`（hidden `id`）、編集 Link `/dashboard/topics/${t.id}/edit` を**完全保持**。`ResultBanner`/`ResultKind`/`?result=` も不変。

**新規クエリ (b) per-topic 累計 — 所在: topics/page.tsx server component / 認可: `where:{ userId }`**:
```ts
const sumsRaw = await prisma.studyRecord.groupBy({
  by: ["topicId"],
  where: { userId },               // データ分離（§7.5）。アーカイブ外のみ表示するが id 結合で絞られる
  _sum: { countedSeconds: true },

```

// 進捗率 = segmentElapsedSec / max(1, segmentTotalSec)（0..1 にクランプ）
function segmentProgressRatio(s: SessionState): number {
  if (s.expired || s.segmentTotalSec <= 0) return 1;
  return Math.min(1, Math.max(0, s.segmentElapsedSec / s.segmentTotalSec));
}
