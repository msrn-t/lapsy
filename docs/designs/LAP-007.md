## 1. 目的

SPEC §4（Must: トピックの手動アーカイブ／復元、アーカイブ済みは通常一覧・トピック別累計から除外し別画面で閲覧）を実装する。`Topic.isArchived` / `archivedAt`（既存フィールド）をトグルし、通常一覧を `isArchived: false` で除外、専用画面（`/dashboard/topics/archived`）でアーカイブ済みを閲覧・復元できるようにする。全クエリで認証セッション由来 userId によるデータ分離（§7.5）を徹底する。

**確定済みの前提（investigator 調査・揺らがせない）:**
- `Topic.isArchived Boolean @default(false)` / `archivedAt DateTime?` / `@@index([userId, isArchived])` は **schema・init マイグレーションに既存**（`prisma/schema.prisma` 89-90,97行 / init SQL 57-58,159行）。**本チケットはマイグレーション不要・スキーマ変更なし**。アーカイブ／復元はフィールド更新＝`UPDATE` のみ。
- アーカイブは「記録を残したまま一覧／トピック別累計から外す」操作であり、StudyRecord/StudySession 行は**物理削除しない**（§7.4 の横断集計の前提を壊さない）。

**スコープ外（本チケットで実装しない）— 集計責務の境界（最重要）:**
- **横断集計（ヒートマップ・7日移動平均）の実装・検証は LAP-011 の責務**。`dashboard/page.tsx` は LAP-002 の最小プレースホルダで集計は未実装（`studyRecord` 参照・`groupBy` ともゼロ）であり、`tickets/active/LAP-011`（status: todo）の受け入れ条件に「トピック別累計はアーカイブ除外、横断集計はアーカイブ済みの過去記録も含める（§7.4 / LAP-007 と整合）」が明記され、依存に LAP-007 が記載されている。
- したがって LAP-007 は **集計を一切実装しない**。受け入れ条件5「横断集計はアーカイブ済みの過去 StudyRecord も含めて集計する（§7.4）」について、**LAP-007 側の責務は「アーカイブを `UPDATE` のみで行い StudyRecord を物理削除しない（=§7.4 の前提を壊さない）」ことの担保に限定**する。集計の実装・検証は LAP-011。
- 「トピック別累計の除外（アーカイブ済みを累計から外す）」の集計実装も LAP-011。LAP-007 は **通常トピック一覧の表示除外**（`isArchived: false`）までを担い、トピック別累計クエリを書く LAP-011 が同様にアーカイブを除外する旨を方針として申し送る（§3-2）。

## 3. 設計方針

**採用する方針:**

1. **アーカイブ／復元は LAP-006 と同形の薄い server action**にする。`<form action={archiveTopic|restoreTopic}>` + hidden `id` → `requireUserId()` → `updateMany({ where: { id, userId, ... }, data })` → `count === 0` を `not_found` → `revalidatePath` → `redirect("?result=...")` → `ResultBanner`。新しい状態遷移ロジックのみ純関数化する（§3-4）。

2. **通常一覧（`topics/page.tsx`）はアーカイブ済みを除外**する。`findMany({ where: { userId, isArchived: false } })` とし、`@@index([userId, isArchived])` を活かす。
   - **トピック別累計（将来 LAP-011）も同様にアーカイブ除外**する方針を申し送る（§7.4 の「トピック別累計の表示から除外」に対応）。LAP-007 では集計を書かないため実装はしないが、設計上の方針として明記し LAP-011 が踏襲する。
   - 通常一覧の各トピック行に「アーカイブ」フォーム（`<form action={archiveTopic}>` + hidden `id`、編集／削除と並べる）を追加。
   - 通常一覧から「アーカイブ一覧」へのリンク導線（`<Link href="/dashboard/topics/archived">`）を追加。

3. **アーカイブ一覧画面 `/dashboard/topics/archived/page.tsx` を新設**する。`requireUserId()` → `findMany({ where: { userId, isArchived: true }, orderBy: [{ archivedAt: "desc" }] })`。各行に「復元」フォーム（`<form action={restoreTopic}>` + hidden `id`）と通常一覧へ戻る導線。`/dashboard` 配下なので edge 保護を継承し、ページ冒頭でも `requireUserId()`（二層防御）。result バナーは通常一覧と同様に `?result=` で表示。

4. **状態遷移・mutation 生成を `src/lib/topic.ts` の純関数として追加**し（DB 非依存・LAP-006 慣習）、隣の `src/lib/topic.test.ts` で検証する（§9）。
   - `computeArchiveMutation(now: Date): { isArchived: true; archivedAt: Date }` — アーカイブ時の data。`archivedAt` に現在時刻を設定（§3-5）。
   - `computeRestoreMutation(): { isArchived: false; archivedAt: null }` — 復元時の data。`archivedAt` を `null` クリア（§3-5）。
   - これにより server action は「件数判定」を持たず（アーカイブは削除と違い事前件数判定が不要）、`requireUserId()` + mutation 生成（純関数）+ `updateMany` の薄い組み合わせになる。テストは mutation の形（フラグ／`archivedAt` の設定・クリア）を固定する。

5. **二重操作の結果コードは `not_found` 一様化**（LAP-006 慣習に合わせて確定）。
   - アーカイブ: `updateMany({ where: { id, userId, isArchived: false }, data: computeArchiveMutation(new Date()) })`。`where` に `isArchived: false` を含めることで、既にアーカイブ済み・不在・他人の行はすべて `count === 0` になり `not_found` で一様化する。
   - 復元: `updateMany({ where: { id, userId, isArchived: true }, data: computeRestoreMutation() })`。同様に未アーカイブ・不在・他人の行は `count === 0` → `not_found`。
   - **判断の根拠**: LAP-006 が `updateMany`+`count===0`→`not_found` を確立済みで、`already_archived` / `not_archived` の専用コードを足すと `ResultKind` と文言が増え整合コストが上がる。二重操作はUI上ほぼ発生せず（アーカイブ済みは別画面、操作後 `revalidatePath` で再描画）、`not_found`（=「対象が見つからない」）で実害なく案内できる。`where` に現状 `isArchived` を含める設計は冪等性も担保する。

6. **データ分離は `requireUserId()` 由来 userId のみを使用**する（§7.5）。全 `findMany`・`updateMany` を `userId` でフィルタし、`updateMany` は `where: { id, userId }` を併用してクライアント入力 `id` を単独で信頼しない。`count === 0` を `not_found` に一様化し、行の存在有無を漏らさない。

**アーカイブと集計の責務分界（明確化・最重要）:**

| 操作／表示 | LAP-007 の責務 | LAP-011 の責務 |
|---|---|---|
| アーカイブ／復元（`isArchived` トグル） | **実装する**（server action + 純関数 + UI） | — |
| 通常トピック一覧の表示除外 | **実装する**（`isArchived: false`） | — |
| アーカイブ一覧画面・復元導線 | **実装する** | — |
| トピック別累計の集計除外 | 方針申し送りのみ（集計は書かない） | **実装する**（アーカイブ除外） |
| 横断集計（ヒートマップ・7日移動平均） | **実装しない**。「StudyRecord を物理削除しない（`UPDATE` のみ）」で前提を担保するのみ | **実装する**（アーカイブ済みの過去 StudyRecord も含めて集計） |

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| LAP-007 で横断集計（ヒートマップ・移動平均）を実装 | dashboard 集計は未実装で、LAP-011 受け入れ条件・依存に集計の二分（トピック別累計＝除外／横断集計＝含める）が明記済み。責務はLAP-011。LAP-007 は前提（記録を消さない）の担保に限定（§1スコープ外） |
| 復元時 `archivedAt` を保持（最後のアーカイブ日時を残す） | 状態を素直に表現する `null` クリアの方が一貫。`archivedAt` は「現在アーカイブ中か」と対応させ、復元で null に戻すと不変条件（`isArchived===false ⟺ archivedAt===null`）が明快。履歴が必要になれば別途監査列で対応 |
| 二重操作に `already_archived`/`not_archived` 専用コード | `ResultKind`・文言・分岐が増え整合コスト増。LAP-006 の `not_found` 一様化に合わせる方が一貫。`where` に `isArchived` 現状値を含め冪等化（§3-5） |
| 通常一覧で全件表示しUI側でフィルタ／グレーアウト | アーカイブ済みを取得し続けるのは §4「除外」と乖離。クエリで `isArchived: false` 除外し index を活かす方が正 |
| クライアント入力 id を `where:{id}` のみで使う | 他ユーザーの行を操作され得る（§7.5 違反）。必ず `{id, userId}` 併用・`count===0`→`not_found` |
| アーカイブで物理削除や状態列の追加 | §7.4 の横断集計が過去 StudyRecord を必要とする。アーカイブは `UPDATE` のみで行を残す。schema 変更も不要 |

**主要なインターフェース（型・I/F 素案。実装は implementer）:**
```typescript
// src/lib/topic.ts — DB 非依存の純ロジック（追記）

export type ArchiveMutation = { isArchived: true; archivedAt: Date };
export type RestoreMutation = { isArchived: false; archivedAt: null };

// アーカイブ時の更新 data。archivedAt に現在時刻をセット（§3-5）。
// 引数で now を受け取り、テストで固定値を渡せるようにする（純関数・時刻非依存テスト）。
export function computeArchiveMutation(now: Date): ArchiveMutation;

// 復元時の更新 data。archivedAt を null クリア（§3-5）。
export function computeRestoreMutation(): RestoreMutation;
```
```typescript
// page.tsx 側の ResultKind 拡張（ResultBanner で文言化）。
// 既存（created/updated/deleted/title_*/invalid_deadline/not_found/delete_*）に追加:
//   "archived"   … アーカイブ成功（SUCCESS_KINDS に含める）
//   "restored"   … 復元成功（SUCCESS_KINDS に含める）
// 二重操作・不在・他人の行は既存 "not_found" を流用（§3-5）。
```

**処理フロー:**

A. アーカイブ（archiveTopic / 通常一覧 page.tsx 内）
```
1. requireUserId() で userId 確定（未認証は /login）
2. FormData から id 取得
3. updateMany({ where: { id, userId, isArchived: false },
               data: computeArchiveMutation(new Date()) })
   - count === 0 → redirect("/dashboard/topics?result=not_found")
4. revalidatePath("/dashboard/topics") → redirect("?result=archived")
```

B. 復元（restoreTopic / archived/page.tsx 内）
```
1. requireUserId() で userId 確定
2. FormData から id 取得
3. updateMany({ where: { id, userId, isArchived: true },
               data: computeRestoreMutation() })
   - count === 0 → redirect("/dashboard/topics/archived?result=not_found")
4. revalidatePath("/dashboard/topics"); revalidatePath("/dashboard/topics/archived")
   → redirect("/dashboard/topics/archived?result=restored")
```
> 復元後の戻り先はアーカイブ一覧（復元された行が一覧から消えたことを確認できる）。両画面の再描画のため両パスを revalidate する。

C. 通常一覧表示（topics/page.tsx・変更点）
```
1. requireUserId() → userId
2. findMany({ where: { userId, isArchived: false }, ... })   ← ★ 除外を追加
3. 各行に 編集 / 削除 に加え「アーカイブ」フォームを追加
4. 「アーカイブ済みを表示」リンク（/dashboard/topics/archived）を追加
5. ResultKind に archived を加え ResultBanner / SUCCESS_KINDS / isResultKind を更新
```

D. アーカイブ一覧表示（archived/page.tsx・新規）
```
1. requireUserId() → userId
2. findMany({ where: { userId, isArchived: true },
              orderBy: [{ archivedAt: "desc" }],
              select: { id, title, description, deadline, archivedAt } })
3. 各行に「復元」フォーム（restoreTopic）を描画。空なら「アーカイブ済みはありません」
4. 通常一覧へ戻る導線 + ResultBanner（restored / not_found 等）
```

**ResultBanner の文言（追加分）:**
- `archived`: 「トピックをアーカイブしました。」（成功）
- `restored`: 「トピックを復元しました。」（成功）
- `not_found`: 既存文言を流用（「対象のトピックが見つかりませんでした。」）— 二重操作・不在・他人の行を一様に案内。
