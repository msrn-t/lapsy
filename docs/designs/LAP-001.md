## 3. 設計方針

**採用する方針:**

1. **scaffold は手動構成を基本とする。** `create-next-app` は対話的でループキット既存ファイル（CLAUDE.md / tickets / .claude 等）と衝突しうるため、リポジトリ直下に必要な設定ファイル（package.json / tsconfig.json / next.config.ts / postcss.config.mjs / tailwind 設定 / src/app 配下）を implementer が手動で作成する。`create-next-app` を使う場合は一時ディレクトリで生成し必要物のみリポジトリ直下へ移送する運用とし、既存ループキットファイルを破壊しないこと。
2. **App Router + TypeScript + Tailwind の最小構成。** `src/app/layout.tsx`（ルートレイアウト・`<html lang="ja">`・Tailwind 読み込み）、`src/app/page.tsx`（`/` health-check となる最小ページ・200 を返す）、`src/app/globals.css`（Tailwind 読み込み）を置く。レスポンシブのベースは Tailwind のモバイルファースト（`sm/md/lg`）方針をルートレイアウトに最小限のコンテナ（`max-w-*`・`mx-auto`・`px-*`）として適用する。複雑なデザインシステムは作らない（機能チケットで拡張）。
3. **依存は「基盤で使うもの」と「導入のみ・実装は後続」を明確に分離する。** prisma / @prisma/client は基盤で使う（スキーマ反映）。next-auth / resend / bcrypt は後続チケットで実装するが、基盤段階では **導入しない**（不要な依存を先に入れない）。SPEC §6 が要求するライブラリはチケット粒度で後続導入する方が依存の意図が明確になる。※本チケットの受け入れ条件・investigator メモは「依存パッケージの導入と Adapter 用モデルのスキーマ反映までに留める」とするが、Adapter モデルは schema.prisma 上のモデル定義のみで成立し next-auth パッケージ導入は不要。よって next-auth/resend は schema 反映の前提にならず、後続チケットで導入する。
4. **部分ユニークインデックスはマイグレーション SQL に raw SQL を手動追記する。** Prisma 標準構文では表現不可（§7.6 補足）。初期マイグレーション（全テーブル生成と同一マイグレーション）の `migration.sql` 末尾に追記し、1マイグレーション内で完結させる。後続 `migrate dev` で喪失しない運用ルールを §4・§7 に明記する。
5. **DB は docker-compose で provision する。** ネイティブ Postgres 不在のため。検証はこの Docker DB を相手に `migrate dev` を実行する（U2）。
6. **Node v22 を前提とする。** `engines.node >=22` を package.json に明記し、`.nvmrc`（`22`）を置く。volta 設定は任意（package.json `volta` フィールド）。

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| `create-next-app` をリポジトリ直下で対話実行 | 既存ループキットファイル（CLAUDE.md / tickets / .claude / docs）と衝突・上書きの危険。グリーンフィールドだがアプリ用空ではない |
| 基盤で next-auth / resend / bcrypt も導入 | 実装しない依存を先に入れると意図が不明瞭。Adapter モデルは schema 定義のみで成立し、パッケージ導入は不要。後続チケットで導入する方が境界が明確 |
| 部分ユニークインデックスを別の追加マイグレーションに分離 | 初期マイグレーションと一体化した方が「スキーマの初期状態」が1マイグレーションで完結し追跡が容易。分離は順序依存リスクを増やす |
| ネイティブ Postgres をローカルにインストールして検証 | 環境に存在せず、Docker が稼働済み（U2 で docker-compose 方針が確定済み） |
| Tailwind を基盤で本格的なデザイントークン化 | 基盤の責務外。最小レスポンシブベースに留め、機能チケットで拡張する |

**prisma/schema.prisma 反映方針:**

**部分ユニークインデックスの raw SQL 手動追記（重要・正確な文面）:**

初期マイグレーション生成後、生成された `prisma/migrations/<timestamp>_init/migration.sql` の **末尾**に以下 2 文を手動追記する（DDL は対象テーブル CREATE 後に実行されるため末尾でよい）。enum 値は Postgres 上で文字列リテラル比較（`'pending'` / `'running'`）となる点に注意（§7.6 補足・investigator メモ）。

```sql
-- 同一メールへの有効な招待は1件まで（status=pending）（SPEC §4 / §7.6）
CREATE UNIQUE INDEX "invitation_email_pending_unique"
  ON "Invitation"("email") WHERE "status" = 'pending';

-- 1ユーザー1アクティブラン（status=running）（SPEC §7.5 / §7.6）
CREATE UNIQUE INDEX "studysession_user_running_unique"
  ON "StudySession"("userId") WHERE "status" = 'running';
```
> enum 物理型: Prisma は `SessionStatus` / `InvitationStatus` を Postgres の enum 型として生成する。`WHERE "status" = 'pending'` のリテラルは enum 型に対する比較として有効（Postgres は enum を文字列リテラルからキャストする）。マイグレーション適用後に `\d "Invitation"` 等で部分インデックスが作成されたことを検証すること。

**手動 SQL を後続 migrate dev で喪失させない運用ルール（必須・docs / README に明記）:**
1. 追記した raw SQL は **既存マイグレーションファイルの一部**であり、Prisma は適用済みマイグレーションを再生成・上書きしない。よって初回作成した `_init` マイグレーションに追記すれば、以降の `migrate dev` では再生成されず保持される。**適用前のマイグレーションにのみ追記する**こと（適用後に同ファイルを書き換えると drift / checksum 不整合の原因になる）。
2. **schema.prisma と DB の drift に注意。** 部分ユニークは schema 側に表現が無いため、`migrate dev` 実行時に Prisma が「schema にインデックスが無い」と誤認して drift 検出することは無い（Prisma は raw な部分インデックスを管理対象として追跡しない）。逆に schema 変更で新規マイグレーションを作る際、Prisma が部分インデックスを認識せず別途 DROP/再作成しないため、原則は維持される。ただし将来テーブル定義を大きく変える場合は、新規マイグレーションへ同等の `CREATE UNIQUE INDEX ... WHERE ...` を再追記する必要が生じうる。手順を README に記載する。
3. 推奨ワークフロー: `schema.prisma` 編集 → `prisma migrate dev --name <名前>`（マイグレーション生成・**まだ DB 未適用の状態を確認**）→ 生成 SQL に raw SQL 追記 → 同コマンド再実行 or `prisma migrate dev` で適用。`--create-only` を使うと「生成のみ・適用前」を確実に作れるため、raw SQL 追記が絡むマイグレーションでは `prisma migrate dev --create-only --name init` → SQL 追記 → `prisma migrate dev` の 2 段階を推奨する。これを README に明記する。

**docker-compose.yml 方針:**
- service: `db`（PostgreSQL）。image: `postgres:16`（安定版・任意で 17 可）。

| docker DB のポート 5432 競合 | low | compose の ports を環境に応じて変更可能に。`.env` の DATABASE_URL と一致させる |

## 7. マイグレーション戦略

DB スキーマの初期化マイグレーションを新規作成する（既存 DB なし＝後方互換考慮不要）。

- **初期マイグレーション 1 本**で全テーブル + 2 つの部分ユニークインデックスを作成する。
- 生成手順（raw SQL 追記が絡むため `--create-only` 2 段階）:
  1. `prisma migrate dev --create-only --name init`（生成・未適用）
  2. `prisma/migrations/<ts>_init/migration.sql` 末尾に `CREATE UNIQUE INDEX "invitation_email_pending_unique" ...` / `CREATE UNIQUE INDEX "studysession_user_running_unique" ...` を追記（文面は §4 参照）
  3. `prisma migrate dev`（適用）
- **後続 migrate での保持ルール:** 適用済みマイグレーションは編集しない。Prisma は raw な部分インデックスを管理対象として追跡しないため自動 DROP されない。将来テーブルを再生成する大規模変更を行う場合のみ、新規マイグレーションへ同等の部分インデックス DDL を再追記する（README に明記）。
- **検証:** docker DB に対し `prisma migrate dev` 成功 + `prisma validate` 成功 + psql `\d "Invitation"` / `\d "StudySession"` で部分インデックス存在確認。

## 8. ロールバック戦略

基盤チケットのため、コミット単位の revert で原状回復可能（DB はローカル/開発用）。

```bash
# コミットを取り消す（履歴保持）
git log --oneline
git revert <コミットハッシュ>
# 例: [LAP-001][REVERT] プロジェクト基盤の取り消し

# ローカル DB を破棄してやり直す場合（開発環境のみ）
docker compose down -v        # 名前付きボリュームごと削除
# その後 docker compose up -d → prisma migrate dev で再構築
```
- 本番 DB は存在しないため `migrate reset` の本番影響は無い。開発 DB のリセットは `prisma migrate reset` または `docker compose down -v` で可。
- CLAUDE.md ロールバック規約に従い、done/→active/ 戻し・status を implementation_done に戻す運用は orchestrator が担当。
