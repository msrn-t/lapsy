## 3. 設計方針

**採用する方針:**

1. **Auth.js (NextAuth) v5 を Credentials + JWT 戦略・Adapter なしで構成する。**
   - Credentials + JWT では `@auth/prisma-adapter` は**不要**（Adapter は主に DB セッション / OAuth アカウント永続のためのもの。Credentials は `authorize` で自前検証し、セッションは JWT cookie に載るため Adapter の Account/Session/VerificationToken テーブルを使わない）。依存と複雑性を増やさないため **Adapter は導入しない**。
   - `authorize` 内で Prisma を直接使い、`email` でユーザー取得 → パスワード検証 → 成功時に `{ id, email, name, isAdmin, sessionVersion }` を返す。
2. **即時無効化は `User.sessionVersion`（Int）と JWT クレームの照合で代替する。** ログイン時に現在の `sessionVersion` を JWT へ焼き込み、`jwt`/`session` コールバックの検証時に DB の最新 `sessionVersion` と照合。不一致なら無効化（`session` を返さない＝未認証扱い）。招待取り消し・強制ログアウト時は `sessionVersion` をインクリメントすれば、cookie 期限前でも次回アクセスで弾ける。
3. **スキーマ整理: Session モデル削除 + User へ `sessionVersion Int @default(0)` 追加。** Account / VerificationToken は本構成（Credentials のみ・OAuth なし）では不要。ただし将来の招待(LAP-003)/リセット(LAP-005)は **独自の `Invitation` / `PasswordResetToken` モデル（既存）** で扱う設計であり Adapter の VerificationToken を使わない。よって **Account / Session / VerificationToken の 3 つとも削除する**（YAGNI。将来 OAuth を入れる時に Adapter ごと再導入する方が構成が一貫する）。
4. **bcryptjs を採用する**（後述の比較参照）。pure JS でネイティブビルド不要、VPS(Ubuntu)/Docker での運用・CI が安定。
5. **保護は middleware（`src/middleware.ts`）で一元化する。** ルートごとの個別ガードより、保護対象（`/dashboard` 等）の集合を 1 箇所で管理でき、未認証→`/login` リダイレクトが一貫する。`auth.config.ts`（edge 互換の最小設定）を middleware が import する分割構成にする（Auth.js v5 推奨。Prisma/bcryptjs は edge 非互換なため `authorize` を含む重い設定は `auth.ts` 側に置く）。
6. **データ分離ヘルパ `getCurrentUser()` / `requireUserId()` をサーバ側に用意する**（§7.5）。クライアント入力 id を信頼せず、必ず認証セッション由来 userId をクエリフィルタに使う。後続 LAP-003〜011 の全クエリの核。
7. **初期管理者 seed（`prisma/seed.ts`）は冪等**（`upsert` ベース）。`ADMIN_EMAIL` / `ADMIN_PASSWORD` を環境変数から読み、bcryptjs でハッシュ化して保存。ハードコード禁止。
8. **Vitest を導入**し、純ロジック（パスワード検証ユーティリティ・失効バージョン照合・seed 冪等性のユニット可能部分）をテストする。

**bcrypt vs bcryptjs の選定:**

| 観点 | bcrypt（native） | bcryptjs（pure JS）★採用 |
|---|---|---|
| ネイティブビルド | node-gyp/node-pre-gyp 依存。Node メジャー更新・glibc/musl 差異でビルド失敗リスク | 不要。どの環境でも同一挙動 |
| VPS(Ubuntu)/Docker 運用 | ビルドツールチェーンが必要。Alpine/musl で詰まりやすい | デプロイが単純・再現性高い |
| パフォーマンス | やや高速 | 純 JS のためやや低速だが、ログイン/seed の頻度（低頻度・cost=10 程度）では実用上問題なし |
| 互換 | $2b$ 形式 | $2a$/$2b$ 互換ハッシュを生成・検証可 |

→ 本アプリは個人〜少人数・低頻度ログイン（SPEC §5 可用性）。**運用容易性・再現性を優先し bcryptjs を採用**。investigator の指摘とも整合。型は `@types/bcryptjs`（bcryptjs 本体が型同梱でなければ）を devDependencies へ。

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| (a) DB セッション手動生成（jwt encode/decode override） | Auth.js 内部実装依存の非公式 hack。v5 で動作不安定報告あり（investigator）。人間判断で (b) に確定済み |
| (c) Lucia 等へ変更 | SPEC §6（NextAuth 前提）逸脱。Lucia は 2025 年に非推奨化方針。人間判断で (b) に確定済み |
| `@auth/prisma-adapter` を併用 | Credentials+JWT では Account/Session/VerificationToken を使わず、Adapter は無用な複雑性。OAuth を入れる時に再検討 |
| Account / VerificationToken を残す | 本構成で参照されない死蔵テーブル。招待/リセットは独自モデルで扱う。残すと「Adapter 使用」と誤読される。削除して意図を明確化 |
| 保護を layout/page レベルの個別ガードで実装 | 保護対象が増えるほど漏れリスク。middleware 一元化の方が一貫し監査が容易 |
| bcrypt（native）採用 | VPS/Docker でのネイティブビルド失敗リスク・運用負荷。低頻度ログインで速度差は無視できる |

export function hashPassword(plain: string): Promise<string>;     // cost=10 程度

// auth.ts — Credentials authorize の返却（DB から取得して検証後）
// 返却オブジェクトに sessionVersion を含め、jwt callback で token へ焼き込む
type AuthorizedUser = {

  email: string;
  name: string | null;

export async function getCurrentUser():

// 失効バージョンを上げる操作の置き場所（後続 LAP-003/004 が呼ぶ I/F 素案。本チケットでは「置き場所と関数シグネチャ」のみ定義し、呼び出し元の実装はしない）
// src/lib/auth-revocation.ts
export async function bumpSessionVersion(userId: string): Promise<void>;
//   → prisma.user.update({ where:{id}, data:{ sessionVersion: { increment: 1 } } })
//   LAP-003（招待取り消し時に対象ユーザーがいれば）/ LAP-004（管理者によるフラグ変更・強制ログアウト）が呼ぶ。
```

**処理フロー:**

A. ログイン（Credentials + JWT）
```
1. /login でメール+パスワード送信（server action 経由で signIn("credentials", {...}, { redirectTo: "/dashboard" })）
2. authorize(credentials):
   a. prisma.user.findUnique({ where:{ email } })。無ければ null（→ 認証失敗）
   b. verifyPassword(password, user.passwordHash)。false なら null
   c. 成功 → { id, email, name, isAdmin, sessionVersion } を返す
3. jwt callback:
   - 初回（user あり）: token.id/isAdmin/sessionVersion を user からコピー
   - 以降（user なし＝既存トークン検証時）: 後述 D の失効照合を実施
4. session callback: session.user.id/isAdmin = token から。session 返却
5. 失敗時: signIn が AuthError を投げる → /login で「メールまたはパスワードが正しくありません」を表示
```

B. ログアウト
```
- server action: signOut({ redirectTo: "/login" })。JWT cookie を破棄
```

C. 保護ルート（middleware）
```
- src/middleware.ts: auth.config.ts の callbacks.authorized で req.auth(=セッション有無)を判定
- matcher で保護対象（例: /dashboard 以下、/ は §SPEC により後続で要否判断）を指定
- 未認証アクセス → /login へリダイレクト（next-auth が pages.signIn:"/login" を使う）
- /login 自体・/api/auth/* は除外（matcher または authorized で許可）
```

D. 失効バージョン照合（即時無効化の代替・本設計の核）
```
- jwt callback で、user が無い（既存トークンの再検証）場合に DB 照合を行う:
    const fresh = await prisma.user.findUnique({ where:{ id: token.id }, select:{ sessionVersion:true, isAdmin:true } });
    if (!fresh || fresh.sessionVersion !== token.sessionVersion) return null; // ← トークン無効化
    token.isAdmin = fresh.isAdmin; // 最新フラグを反映（任意）
    return token;
- jwt callback が null を返すとセッションは確立しない＝未認証扱いになる。
- 招待取り消し/強制ログアウト/管理者フラグ剥奪（LAP-003/004）で bumpSessionVersion(userId) を呼べば、
  対象ユーザーの既存 cookie は次アクセスで弾かれる（cookie 自体は期限まで残るが照合で無効化）。
- 注意（実装時 implementer が確認）: jwt callback での毎リクエスト DB 照合は「edge 非互換（Prisma）」と
  「リクエストごとのクエリ増」のトレードオフがある。middleware は auth.config（DB 照合なし）を使い、
  サーバコンポーネント/Route Handler 側の auth() で重い照合を行う分割を基本とする。照合頻度・edge 配置の
  最終判断は実装時に Auth.js v5 の最新挙動で確認（設計のブロッカーにはしない）。
```

E. 初期管理者 seed（冪等）
```
- prisma/seed.ts:

   未設定なら明示エラーで終了（ハードコード禁止）

## 6. リスク

| リスク | 深刻度 | 軽減策 |
|---|---|---|
| jwt callback での毎リクエスト DB 照合が edge 非互換 / クエリ増 | medium | middleware は DB 照合なしの auth.config を使い、重い照合は node 側 auth() に分離（§4-D）。照合頻度の最終判断は実装時に確認 |
| Adapter を入れない構成で v5 の型・signIn 挙動が想定と異なる | medium | context7 で v5 の Credentials+JWT パターン確認済み（authorize/jwt/session/handlers）。不確実点は implementer が install 版で確認。設計のブロッカーにはしない |
| 既存 _init を誤編集して drift/checksum 不整合 | medium | 既存マイグレーションは不変。変更は新規マイグレーションのみ。docs に明記 |
| seed が ADMIN_PASSWORD 未設定で平文/空ハッシュを作る | high | seed 冒頭で env 必須チェック → 未設定は即エラー終了。upsert の update を {} にして再実行で上書きしない |
| AUTH_SECRET 未設定で JWT 署名不能/起動失敗 | medium | .env.example に必須明記。setup docs に生成コマンド記載。本番は必須 |
| bcryptjs の速度がログイン体感に影響 | low | cost=10・低頻度ログインで実用上問題なし（§3 比較） |
| Session 削除で将来 OAuth 導入時に再追加が必要 | low | OAuth は SPEC スコープ外（招待制）。導入時に Adapter ごと再導入する方針で一貫 |
| 失効バージョン照合の取りこぼし（呼び忘れ） | medium | `bumpSessionVersion()` を単一の関数に集約し、LAP-003/004 が必ずこれを経由する設計を明記。本チケットで関数とユニットテストを用意 |

## 7. マイグレーション戦略

LAP-001 の初期マイグレーション（`20260620172038_init`・適用済み）に対し、**新規マイグレーション 1 本**を追加する。既存マイグレーションは編集しない（§6）。

**schema.prisma 変更内容:**
- `model Session { ... }` を削除
- `model Account { ... }` を削除
- `model VerificationToken { ... }` を削除
- `User` から `accounts Account[]` / `sessions Session[]` のリレーション行を削除
- `User` に `sessionVersion Int @default(0)` を追加（`emailVerified` は Adapter 専用だが残置可。NextAuth Credentials では未使用。削除は任意 — 本設計では**残置**し、影響を最小化する。implementer が削除する場合はマイグレーションに含める）

**生成手順（raw SQL 不要。通常の migrate でよい）:**
```
1. schema.prisma を上記の通り編集
2. npx prisma migrate dev --name auth_session_strategy
   → DROP TABLE "Session"; DROP TABLE "Account"; DROP TABLE "VerificationToken";
     ALTER TABLE "User" ADD COLUMN "sessionVersion" INTEGER NOT NULL DEFAULT 0;
     （関連 FK・インデックスの DROP は Prisma が自動生成）
3. npx prisma generate
```
> **§7.6 の部分ユニークインデックスへの影響なし**を確認: 2 本の部分インデックスは `Invitation`(email) と `StudySession`(userId) に対するもので、Session/Account/VerificationToken テーブルとは無関係。本マイグレーションは User 列追加と認証 3 テーブル削除のみで、Invitation/StudySession テーブルに触れない。よって部分インデックスは保持される（migrate 後に `\d "Invitation"` / `\d "StudySession"` で再確認推奨）。

**docs/lapsy-local-setup.md 追記方針:**
- 「6. 認証・初期管理者」セクションを追加: `AUTH_SECRET` 生成（`openssl rand -base64 32`）、`ADMIN_EMAIL`/`ADMIN_PASSWORD` を `.env` に設定、`npm run db:seed` で初期管理者投入（冪等）、`/login` でログイン確認。
- 新規マイグレーション適用手順（`npx prisma migrate dev`）と「既存 _init は編集しない」注意を追記。
