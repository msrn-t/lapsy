## 1. 目的

SPEC §4（Must: 完了作業ブロックは計画作業時間で記録／中断は実作業時間を aborted で記録／status 保持）、§7.2（記録値ルール）、§7.3（materialize step1〜5・<60s 除外）を実装する。LAP-009 が「進行中の状態導出（読み取り専用）」と「ランの状態遷移（running 作成 / aborted UPDATE）」に留め、StudyRecord への書き込みを `expired` 境界で LAP-010 に委ねた（LAP-009 §3-3）。本チケットはその続きとして:

1. 凍結された `presetSnapshot` と確定点（cutoff）から、各作業ブロックを `StudyRecord` 相当のプレーンオブジェクト配列へ分解する **DB 非依存の純関数 `computeMaterialize`** を提供する（completed/aborted/3h キャップ/<60s 除外/休憩区間中断/日跨ぎ completedAt）。
2. 確定点（cutoff）を「ユーザー中断 = endedAt」「遅延評価 = `min(startedAt+totalSec, startedAt+3h)`」で決め、completed（総時間≤3h を放置→全ブロック completed）と 3h-aborted（総時間>3h が 3h 時点で作業中→aborted）を分岐する。
3. 「running 取得 + 確定期限経過なら materialize」を **冪等な共通ヘルパ**に切り出し、LAP-009 の `sessions/page.tsx`（再 open）とユーザー中断、将来の LAP-011 集計入口の全てから漏れなく呼べる形にする（専用バッチ不要・§7.3）。冪等性は `updateMany({status:"running"})` の `count===1` を勝者にし `$transaction` 内で `createMany(StudyRecord)` する（invite/password-reset で確立済みパターン）。

**スコープ外（本チケットで実装しない）:**
- 集計（トピック別累計・ヒートマップ・7日移動平均）と **Asia/Tokyo 日割り解釈は LAP-011**。本チケットは `completedAt` に **UTC の Date を書くのみ**（§7.4 の TZ 解釈は集計側）。
- StudyRecord スキーマの変更（不要・後述 §7）。
- ライブタイマー UI そのもの（LAP-009 の `_timer.tsx`）。本チケットは expired 表示を「確定済み」へ差し替える server 側の接続のみ。

## 3. 設計方針

### 3-0. 全体方針（純ロジックと I/O の分離）

materialize を **2 層**に分ける。LAP-008/009 の「純関数 + 薄い server 層 + 純関数の単体テスト」慣習を踏襲する。

1. **純ロジック層（DB 非依存）`src/lib/materialize.ts`**: `computeMaterialize({snapshot, startedAt, cutoff})` が「cutoff までに確定すべき作業ブロックのプレーンオブジェクト配列」を返す。completed/aborted の振り分け・countedSeconds 計算・<60s 除外・休憩区間中断・日跨ぎ completedAt をすべてここに閉じ込め、`now`/`cutoff` を引数注入して時刻非依存に単体テストする（§9・SPEC §9）。
2. **I/O 層（DB 書き込み・冪等）`materializeIfDue` ヘルパ（`materialize.ts` に同居）**: running の StudySession を受け取り、cutoff を決め、`$transaction` 内で「`updateMany`(status guard) → 勝者のみ `createMany(StudyRecord)`」を原子化する。`sessions/page.tsx` の再 open（遅延評価）・abortSession（ユーザー中断）・LAP-011 集計入口の 3 経路から呼べる単一エントリにする。

> **配置の結論（Unknown #1）**: **新規 `src/lib/materialize.ts`（+ `src/lib/materialize.test.ts`）** とする。`session.ts` 同居は却下（後述 §3 代替案）。`session.ts` の `MAX_RUN_SECONDS` は **既存 export をそのまま import 再利用**（非破壊・新規 export 追加不要）。`deriveSessionState` は本チケットでは使わない（materialize は独自にブロック列挙するため。`deriveSessionState` のシグネチャは一切変更しない）。

### 3-1. cutoff（確定点）の決定ロジックと completed vs aborted 分岐（Unknown #2）

**結論: cutoff は「呼び出し側（I/O 層）が決定」し、純関数 `computeMaterialize` は cutoff を所与として受け取りブロック分解のみ行う。** completed/aborted の分岐は cutoff の値から純関数内で自然に決まる（`cutoff ≥ startedAt+totalSec` なら全ブロック completed、`cutoff` が work セグメント途中に当たれば当該ブロックのみ aborted）。これにより「completed か aborted か」を呼び出し側が事前判定する必要がなく、判定が純関数内の半開区間消化に一本化される。

**cutoff の算出（I/O 層 `materializeIfDue` 内）:**

| 経路 | cutoff |
|---|---|
| (a) ユーザー中断（abortSession） | `endedAt`（= server action 内 `new Date()`。LAP-009 が UPDATE 済みのサーバー時刻） |
| (b) 遅延評価（再 open / 参照 / 集計入口） | `cutoffSec = min(totalSec, MAX_RUN_SECONDS)` を秒として `cutoff = new Date(startedAt.getTime() + cutoffSec*1000)` |

- **発火条件（遅延評価）**: `now ≥ startedAt + cutoffSec`（= LAP-009 の `expired`）。これを満たさない running は materialize しない（まだ進行中・早期リターン）。
- **completed / 3h-aborted の分岐は cutoff の位置で決まる（純関数任せ）:**
  - 総時間 ≤ 3h（`totalSec ≤ MAX_RUN_SECONDS`）: `cutoffSec = totalSec` → cutoff はラン終端 → 全 work ブロックが cutoff までに完全終了 → **全 completed**（§7.3 step3。放置 completed もここ）。
  - 総時間 > 3h（`totalSec > MAX_RUN_SECONDS`）: `cutoffSec = 10800` → cutoff が 3h 時点。3h がどのセグメントに当たるかで分岐:
    - 3h が work セグメント途中 → 当該 work が **aborted**（実作業秒数）、それ以前は completed（§7.3 step5・3h キャップ）。
    - 3h が break セグメント途中 / セグメント境界 → 直前 work は completed 扱い・部分記録なし（§7.3 step4 の休憩区間中断と同じ扱い）。
- **ユーザー中断（cutoff=endedAt）**も同じ純関数で処理する。endedAt が work 途中なら当該 work aborted、break 途中/境界なら直前 work まで completed・部分記録なし（§7.3 step4）。endedAt が `startedAt+3h` を超えるケースは理論上起きない（3h 前に遅延評価で先に completed/aborted 確定されるため）が、堅牢性として cutoff は内部で `min(cutoff, startedAt+totalSec)` にクランプする（cutoff がラン終端を超えても全 completed で頭打ち）。

> **取り違え防止の要点（§7.3 step5）**: 「3h キャップで aborted にする」のは **総時間 > 3h かつ 3h 時点で work 中** の場合のみ。総時間 ≤ 3h は cutoffSec=totalSec=ラン終端なので、放置されても aborted 化されず全 completed になる。この不変条件は「cutoffSec = min(totalSec, MAX_RUN_SECONDS)」という 1 行に集約され、純関数の半開区間消化が自動的に正しい分岐を導く。

### 3-2. ブロック分解アルゴリズム（Unknown #3）

`computeMaterialize` は `snapshot` を先頭から半開区間で消化し、`cutoffSec = floor((cutoff - startedAt)/1000)`（負はクランプ）までに登場する work セグメントを列挙する。`deriveSessionState` と同じ「`[acc, acc+sec)` 半開区間」モデルを使い、境界の所属を一貫させる（下端は次セグメント）。

**各 work ブロック i（accWork = ブロック開始の累積秒）の判定:**

| ケース | 条件 | 記録 |
|---|---|---|
| 完全終了 work（completed） | `cutoffSec ≥ accWork + workSec`（work セグメントが cutoff までに丸ごと終わった） | status=completed, plannedSeconds=workSec, **countedSeconds=workSec**, startedAt=ラン startedAt+accWork 秒, completedAt=ラン startedAt+(accWork+workSec) 秒 |
| cutoff が当たった work（aborted） | `accWork ≤ cutoffSec < accWork + workSec`（work 途中で cutoff） | status=aborted, plannedSeconds=workSec, **countedSeconds=cutoffSec−accWork**（実作業秒）, startedAt=ラン startedAt+accWork 秒, completedAt=ラン startedAt+cutoffSec 秒（=cutoff） |
| cutoff が break に当たった / break 境界 | 直前 work は上の「完全終了」で既に completed 計上済み。break 区間は記録しない | （§7.3 step4: 直前 work=completed 扱い・部分記録を生まない） |
| cutoff 到達後の未着手 work | `cutoffSec ≤ accWork`（cutoff より後に始まる work） | 記録しない（ループ break） |

**休憩区間は completed/aborted いずれも記録しない（§7.2）**: break セグメントは accumulate するだけで StudyRecord を生成しない。cutoff が break 途中で当たっても直前 work は既に completed として計上済みなので、aborted の部分記録は発生しない（step4 の核心）。

**<60s 除外（§7.3）**: 生成した各ブロックのうち `countedSeconds < 60` のものを **最後にフィルタで除外**する。completed は `workSec ≥ MIN_WORK_SEC(60)`（LAP-008 の制約）により常に 60 以上で影響なし。実質的に「開始直後に中断した aborted の部分ブロック（実作業 < 60s）」のみが除外対象（§7.3 注記）。除外は列挙の最後に行い、列挙ロジック自体は <60s を意識しない（責務分離・テスト容易性）。

**日跨ぎ completedAt（§7.4）**: 各ブロックの `startedAt`/`completedAt` は `ラン startedAt + 累積秒` の UTC Date を計算するのみ。日付をまたいでも分割せず、`completedAt` をそのまま書く（Asia/Tokyo 日割りは LAP-011 が集計時に解釈）。本チケットは UTC Date を 1 個書くだけで、TZ ヘルパは導入しない。

**擬似コード（implementer 向け・確定アルゴリズム）:**
```
computeMaterialize({ snapshot, startedAt, cutoff }) -> MaterializedRecord[]:
  totalSec = Σ(workSec_i + breakSec_i)
  cutoffSec = max(0, floor((cutoff - startedAt)/1000))
  cutoffSec = min(cutoffSec, totalSec)          // ラン終端を超えても頭打ち（堅牢性・§3-1）

  records = []
  acc = 0                                         // 累積秒（work/break セグメント開始境界）
  for i in 0..snapshot.length-1:
    { workSec, breakSec } = snapshot[i]
    accWork = acc                                 // この work セグメント開始の累積秒

    if cutoffSec <= accWork:
      break                                       // cutoff より後の work は未着手 → 以降は記録しない

    blockStartedAt = new Date(startedAt + accWork*1000)
    if cutoffSec >= accWork + workSec:
      // 完全終了 work → completed（計画値・§7.2）
      records.push({
        lapIndex: i, plannedSeconds: workSec, countedSeconds: workSec,
        status: "completed",
        startedAt: blockStartedAt,
        completedAt: new Date(startedAt + (accWork + workSec)*1000),
      })
    else:
      // accWork <= cutoffSec < accWork+workSec → cutoff が work 途中 → aborted（実作業秒・§7.2）
      counted = cutoffSec - accWork               // 実作業秒（≥0）
      records.push({
        lapIndex: i, plannedSeconds: workSec, countedSeconds: counted,
        status: "aborted",
        startedAt: blockStartedAt,
        completedAt: new Date(startedAt + cutoffSec*1000),  // = cutoff
      })
      break                                       // aborted ブロックでランは終わる
    acc += workSec
    // break セグメントは記録対象外（§7.2）。次 work の境界まで accumulate するのみ。
    // cutoff が break 途中で当たっても直前 work は上で completed 済み・部分記録なし（§7.3 step4）。
    acc += breakSec

  // <60s 除外（§7.3）。completed は workSec≥60 で常に通過、aborted の極小部分のみ除外。
  return records.filter(r => r.countedSeconds >= 60)
```

> **break 途中 cutoff の取り扱い（§7.3 step4 の確認）**: 直前 work が「完全終了」分岐で completed 済みのため `acc += workSec` まで進んでいる。次のループ先頭で `cutoffSec <= accWork(=次 work 開始)` が真になり `break` する。よって break 区間で止まったランは「直前 work まで completed・部分記録なし」になる。aborted 分岐に入るのは cutoff が **work 区間内**のときだけ。

### 3-3. 冪等な materialize（$transaction + status guard）（Unknown #4）

**結論: status guard 一本（`updateMany({status:"running"})` の `count===1` を勝者条件）+ `$transaction` で `createMany` を原子化する。StudyRecord へ unique 制約は追加しない（スキーマ不変）。** invite/password-reset の「条件付き `updateMany` の `count` で勝者判定 + `$transaction` で副作用を原子化」と同型。

```
materializeSession(tx, session, cutoff, targetStatus):
  // 1. 状態遷移を勝者条件にする（同時実行・並行リクエストで1回だけ通る）。
  const { count } = await tx.studySession.updateMany({
    where: { id: session.id, userId: session.userId, status: "running" },
    data: { status: targetStatus, endedAt: cutoff },   // completed or aborted
  })
  if (count === 0) return { materialized: false }       // 既に確定済み（敗者）→ 何もしない（冪等）

  // 2. 勝者のみ StudyRecord を生成（同一 Tx 内で原子化）。
  const records = computeMaterialize({ snapshot, startedAt: session.startedAt, cutoff })
  if (records.length > 0) {
    await tx.studyRecord.createMany({
      data: records.map(r => ({
        sessionId: session.id, userId: session.userId, topicId: session.topicId,
        lapIndex: r.lapIndex, plannedSeconds: r.plannedSeconds, countedSeconds: r.countedSeconds,
        status: r.status, startedAt: r.startedAt, completedAt: r.completedAt,
      })),
    })
  }
  return { materialized: true }
```

- **targetStatus の決定**: `computeMaterialize` の結果に **aborted ブロックが含まれる**（= cutoff が work 途中）なら `StudySession.status="aborted"`、それ以外（全 completed or 0 件）なら `"completed"`。ユーザー中断経路でも、cutoff(endedAt) が break/境界で work を割らなければ「実質完了」として completed にする（§7.3 step4 の「中断が休憩区間 → 直前 work completed・部分記録なし」と整合）。これにより「中断したのに全 completed → status=completed」という一貫した結果になる。
- **count===0（敗者）= 何もしない**: 別リクエストが先に materialize 済み。StudyRecord を二重生成しないのは status guard が `running` のみ通すため（StudyRecord 側 unique 不要）。`$transaction` で「updateMany と createMany」を束ね、updateMany が通った Tx だけが createMany する（部分適用なし）。
- **records.length===0（<60s 全除外 / cutoffSec=0）**: StudyRecord は作らないが status は遷移させる（running を放置しない）。例: 開始 5 秒で中断 → aborted 部分が <60s で全除外 → StudyRecord 0 件・status=aborted。これは仕様（破棄ではなく「記録に値しない極小ブロックの除外」§7.3）。

> **スキーマ不変の結論**: StudyRecord に `@@unique([sessionId, lapIndex])` 等の追加は **しない**。理由: (1) status guard で勝者が 1 回だけ createMany するため二重生成が原理的に起きない、(2) unique 追加はマイグレーションを生み「アプリ層完結」の前提を崩す、(3) invite/password-reset も副作用側に unique を足さず status/usedAt guard 一本で冪等を達成している（前例踏襲）。

### 3-4. 遅延評価ヘルパと発火点（Unknown #5）

**結論: 単一エントリ `materializeIfDue(session, now)` を `materialize.ts` に置き、3 経路から呼ぶ。**

```
materializeIfDue(session, now): Promise<MaterializeOutcome>
  // session: { id, userId, topicId, presetSnapshot, startedAt, status } の running 行
  入力前提: status==="running"（呼び出し側が running を渡す）
  1. snapshot = parsePresetConfig(session.presetSnapshot)        // JSONB を信頼しない
  2. totalSec = Σ(snapshot); cutoffSec = min(totalSec, MAX_RUN_SECONDS)
  3. elapsedSec = floor((now - startedAt)/1000)
     if elapsedSec < cutoffSec: return { due: false }             // まだ確定期限前 → 何もしない
  4. cutoff = new Date(startedAt + cutoffSec*1000)                // 遅延評価の cutoff（§3-1 (b)）
  5. outcome = await prisma.$transaction(tx => materializeSession(tx, session, snapshot, cutoff))
  6. return { due: true, ...outcome }
```

| 発火点 | 呼び方 | 備考 |
|---|---|---|
| (1) 再 open / 参照（`sessions/page.tsx`） | running 取得直後に `materializeIfDue(running, new Date())`。`due:true` なら running は確定済み → **再取得**して null 表示（または直接「確定しました」表示）。`due:false` なら従来通り `deriveSessionState` で進行中表示 | LAP-009 の expired 静的表示を「実 materialize → 開始フォームへ」に差し替え（§3-5） |
| (2) ユーザー中断（`abortSession`） | cutoff = `endedAt`（中断はその場で確定するので `due` 判定を経ず直接 materialize）。専用エントリ `materializeOnAbort(session, abortedAt)` を用意し `$transaction` で `materializeSession(tx, session, snapshot, abortedAt)` を呼ぶ | endedAt はサーバー時刻（改ざん対策）。LAP-009 の「updateMany→aborted のみ」を「materialize（updateMany + createMany）」へ昇格（§3-5） |
| (3) LAP-011 集計入口（将来） | 集計クエリ前に当該ユーザーの running を取得し `materializeIfDue` を呼ぶ（確定漏れを集計時に回収） | 本チケットでは接続しない（ヘルパを再利用可能な形で提供するのみ・申し送り §10） |

> **ユーザー中断と遅延評価の cutoff 差**: 中断は cutoff=endedAt（任意の中断時刻）、遅延評価は cutoff=`min(totalSec,3h)` 時点。両方とも同じ `materializeSession`（status guard + computeMaterialize + createMany）を通る。中断専用に `materializeIfDue` の `due` 判定をスキップするのは「中断は今すぐ確定」だからで、`materializeIfDue` の中の `materializeSession` を共有することでロジック重複を避ける。

### 3-5. LAP-009 `sessions/page.tsx` への接続（具体差分）

**(A) 再 open / 参照（RunningView 手前）:**
```
現状: const running = findFirst({status:"running"}); RunningView が deriveSessionState で expired 静的表示
変更: running 取得後、materialize を試みる:
  if (running) {
    const outcome = await materializeIfDue(running, new Date());
    if (outcome.due) {
      // 確定された → running はもう存在しない。再取得 or リダイレクトで反映。
      redirect("/dashboard/sessions?result=materialized");  // ResultKind に "materialized" 追加（成功扱い）
    }
  }
  // due:false（進行中）→ 従来の RunningView（deriveSessionState 表示）へ
```
- これにより「ブラウザを閉じたまま総時間が経過 → 次に開いた瞬間に completed 確定」（§7.3 step3）と「総時間>3h を 3h 放置 → 3h-aborted 確定」（step5）が再 open の遅延評価で成立する。`_timer.tsx` の expired 静的表示には基本到達しない（server 側で先に確定するため）。expired 表示は「materialize と同一リクエスト内の競合で稀に残る」保険として残置してよい（実害なし）。

**(B) ユーザー中断（abortSession 差し替え）:**
```
現状: updateMany({status:"running"})→{status:"aborted",endedAt:new Date()}; count===0→not_found
変更: abortedAt = new Date() を cutoff に、$transaction で materializeSession を回す:
  const session = await prisma.studySession.findFirst({
    where: { id, userId, status: "running" },
    select: { id, userId, topicId, presetSnapshot, startedAt },
  });
  if (!session) back("not_found");                          // 不在・他人・既確定を一様化
  const outcome = await prisma.$transaction(tx =>
    materializeSession(tx, { ...session }, parsePresetConfig(session.presetSnapshot), abortedAt));
  if (!outcome.materialized) back("not_found");             // 並行で先に確定された（敗者）
  revalidatePath(...); back("aborted");
```
- LAP-009 の「abort は status=aborted+endedAt まで・StudyRecord 0 件で残す」を、本チケットで「abort 時に completed 済みブロック + 中断 work(aborted) を materialize」へ昇格する（§7.3 step4 完全実装）。`endedAt` は引き続きサーバー時刻 `new Date()`（改ざん対策）。
- targetStatus は §3-3 の規則（aborted ブロックを含むかで completed/aborted）。中断 UI 文言（"aborted"）はそのまま使え、status 自体は materialize 結果で決まる（中断が break に当たれば completed になり得る）。

**(C) ResultKind 追加:** `page.tsx` の `ResultKind` に **`"materialized"`**（成功・緑バナー）を追加し、文言「学習記録を確定しました。」を ResultBanner に足す。`SUCCESS_KINDS` に含める。

```typescript
// src/lib/materialize.ts — DB 非依存の確定ロジック（SPEC §7.2 / §7.3）

import type { LapConfig } from "@/lib/preset";
import { MAX_RUN_SECONDS } from "@/lib/session"; // 3h キャップ（既存 export を非破壊再利用）

/** computeMaterialize が返す StudyRecord 相当のプレーンオブジェクト（DB 列名に揃える）。 */
export type MaterializedRecord = {
  lapIndex: number;        // ラン内のラップ番号（0 始まり）
  plannedSeconds: number;  // そのラップの計画作業秒（= snapshot[i].workSec）
  countedSeconds: number;  // completed=workSec / aborted=実作業秒（cutoffSec-accWork）
  status: "completed" | "aborted"; // RecordStatus と一致
  startedAt: Date;         // ブロック開始の実時刻 = ラン startedAt + accWork 秒（UTC）
  completedAt: Date;       // completed=ブロック終端 / aborted=cutoff（UTC・日割りは LAP-011）
};

export type ComputeMaterializeInput = {
  snapshot: LapConfig[]; // 凍結ラップ構成（parsePresetConfig で narrowing 済みを渡す）
  startedAt: Date;       // ラン開始（DB の startedAt）
  cutoff: Date;          // 確定点（中断=endedAt / 遅延評価=min(startedAt+totalSec, startedAt+3h)）
};

/**
 * 確定点 cutoff までに確定すべき作業ブロックを StudyRecord 相当の配列へ分解する純関数。
 * - 完全終了 work = completed（countedSeconds=plannedSeconds=workSec）
 * - cutoff が work 途中 = aborted（countedSeconds=cutoffSec-accWork の実作業秒）でランは終了
 * - cutoff が break 途中/境界 = 直前 work は completed 済み・部分記録なし（§7.3 step4）
 * - 休憩区間は記録しない（§7.2）／ countedSeconds<60 のブロックは最後に除外（§7.3）
 * - completedAt は UTC Date をそのまま書く（Asia/Tokyo 日割りは LAP-011・§7.4）
 * - cutoffSec は内部で min(.., totalSec) にクランプ（ラン終端超過→全 completed 頭打ち）
 */
export function computeMaterialize(input: ComputeMaterializeInput): MaterializedRecord[];

// ── I/O 層（DB 書き込み・冪等。$transaction の tx を受け取る）──

export type MaterializeOutcome = { materialized: boolean };

type RunningSession = {
  id: string; userId: string; topicId: string;
  startedAt: Date;
};

/**
 * status guard（updateMany running）の count===1 を勝者にし、勝者のみ createMany(StudyRecord)。
 * targetStatus は computeMaterialize の結果に aborted ブロックがあれば "aborted"、無ければ "completed"。
 * Prisma.TransactionClient を受け取り、呼び出し側の $transaction 内で原子化する（invite/password-reset 同型）。
 */
export async function materializeSession(
  tx: Prisma.TransactionClient,
  session: RunningSession,
  snapshot: LapConfig[],
  cutoff: Date,
): Promise<MaterializeOutcome>;

/**
 * 遅延評価エントリ。now が確定期限以降なら $transaction で materializeSession を回す。
 * 確定期限前（due:false）は何もしない。再 open / 参照 / 集計入口（LAP-011）から呼ぶ。
 */
export async function materializeIfDue(
  session: RunningSession & { presetSnapshot: unknown },
  now: Date,
): Promise<{ due: boolean } & Partial<MaterializeOutcome>>;
```

**処理フロー:**

A. 純ブロック分解（computeMaterialize・§3-2）
```
1. totalSec = Σ(workSec+breakSec); cutoffSec = clamp(floor((cutoff-startedAt)/1000), 0, totalSec)
2. acc=0 で snapshot を走査:
     cutoffSec <= accWork → break（未着手 work）
     cutoffSec >= accWork+workSec → completed ブロック push（counted=workSec）, acc+=workSec, acc+=breakSec
     else（work 途中）→ aborted ブロック push（counted=cutoffSec-accWork）, break
3. records.filter(countedSeconds >= 60) を返す（<60s 除外）
```

B. 冪等 materialize（materializeSession・§3-3）
```
1. records = computeMaterialize({snapshot, startedAt, cutoff})
2. targetStatus = records.some(r=>r.status==="aborted") ? "aborted" : "completed"
3. { count } = tx.studySession.updateMany({where:{id,userId,status:"running"}, data:{status:targetStatus, endedAt:cutoff}})
4. count===0 → return {materialized:false}（敗者・冪等）
5. records.length>0 → tx.studyRecord.createMany({data: records→DB 列マッピング（sessionId/userId/topicId 付与）})
6. return {materialized:true}
```

C. 遅延評価（materializeIfDue・§3-4）+ page.tsx 接続（§3-5）
```
再 open: running 取得 → materializeIfDue(running, new Date())
          due:true → redirect(?result=materialized) / due:false → 従来 RunningView
中断:    findFirst running → $transaction(materializeSession(tx, session, snapshot, new Date()))
          materialized:false → not_found / true → aborted
```
