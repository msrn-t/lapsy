## 3. 設計方針

### 3-0. 全体方針（純ロジックと I/O の分離）

LAP-008/009/010 の「純関数 + 薄い server 層 + 純関数の単体テスト」慣習を踏襲し、**2 層**に分ける。

1. **純ロジック層（DB 非依存）`src/lib/aggregate.ts`**: UTC→JST 暦日変換・日次バケツ化・ゼロ埋め日次系列・7日移動平均・期限カウントダウンをすべて純関数として閉じ込め、`now`/`timeZone` を引数注入して時刻非依存に単体テストする（§9・SPEC §9）。
2. **I/O 層（DB クエリ + materialize）`dashboard/page.tsx`（server component）**: `requireUserId()` で userId を確定 → 集計入口で `materializeIfDue` → Prisma で生レコードを取得 → 純関数で整形 → SVG/CSS で描画。

> 純関数を `aggregate.ts` に新設する（`topic.ts`/`materialize.ts` 同居は却下）。理由: 集計は materialize/トピック CRUD と関心が異なり、本チケット固有の関数群（日割り・移動平均・カウントダウン）が複数になるため、独立ファイルの方が凝集度・テスト見通しが良い（`session.ts`/`materialize.ts` をそれぞれ独立させた前例と一貫）。

### 3-1. Asia/Tokyo 日次バケツ化の方式（裁量 #1 → 決定）

**結論: アプリ層の純関数で「UTC `completedAt` Date → JST 暦日キー `"YYYY-MM-DD"`」へ変換する。JST オフセットは固定 +9h を手動加算する（DST なし）。** `$queryRaw` の `AT TIME ZONE` による DB 集計は採用しない。

**変換アルゴリズム（純関数 `toJstDateKey(date: Date): string`）:**
```
jstMs = date.getTime() + 9*60*60*1000          // UTC ミリ秒に +9h（JST は DST なし・固定）
d     = new Date(jstMs)
// UTC ゲッターで「+9h ずらした時刻」の暦日を読む（ローカル TZ 非依存・サーバ TZ に左右されない）
key   = `${d.getUTCFullYear()}-${pad2(d.getUTCMonth()+1)}-${pad2(d.getUTCDate())}`
```
- ポイントは **`getUTC*` ゲッターで読む**こと。`+9h` した Date を `getUTCFullYear/Month/Date` で読むと、サーバの OS タイムゾーン（VPS は Ubuntu・UTC 想定だが保証しない）に一切依存せず JST 暦日が得られる。`getFullYear()` 等のローカルゲッターはサーバ TZ 依存になるため使わない。
- 手動 +9h を採用し `Intl.DateTimeFormat`（`timeZone: "Asia/Tokyo"`）は採用しない（§3 代替案）。

**採用理由・トレードオフ:**

| 観点 | アプリ層純関数（採用） | $queryRaw `AT TIME ZONE`（却下） |
|---|---|---|
| テスト容易性 | ◎ DB 不要・`completedAt` Date を直接渡し境界（日跨ぎ・年跨ぎ）を単体テスト（SPEC §9） | △ DB 接続前提でロジックを単体テストしにくい |
| index 活用 | ◎ 後述 §3-7 の期間窓 `where:{userId, completedAt:{gte}}` が `@@index([userId,completedAt])` に効く。日割りはアプリ層で N≦~数千件を集約（§5 で問題なし） | ○ DB 側で日付化・GROUP BY できるが、`AT TIME ZONE 'Asia/Tokyo'` を式に使うと completedAt の index range が効きにくくなる懸念 |
| 慣習一貫性 | ◎ 全集計純関数を `aggregate.ts` に一本化し vitest で網羅（LAP-008/009/010 と同形） | △ 生 SQL が `admin/users` 以外に増え、Prisma 型安全から外れる |
| DST | ◎ JST は DST なしのため +9h 固定で常に正しい | ◎ DB も Asia/Tokyo で正しい |

> **トレードオフの結論**: 期間窓フィルタ（直近 N 日）を Prisma の型安全な `where` で行い index を効かせた上で、**取得した行をアプリ層で JST 日割り集約**する。1 ユーザーの直近 N 日分（後述 §3-7 で N=90 日上限、StudyRecord は作業ブロック単位で 1 日あたり高々数十件程度）なら集約対象は数千件以下で、§5（2 秒以内）に十分収まる。テスト容易性・型安全・慣習一貫性が DB 集計の僅かな利点を上回る。

### 3-2. 集計クエリ方式（裁量 #2 → 決定）

**結論: Prisma の型安全 API（`groupBy` / `aggregate` / `findMany`）を使う。`$queryRaw` は使わない。** 全クエリに `requireUserId()` 由来の `userId` フィルタを必須化する（クライアント入力 id を信頼しない・§7.5）。

| 集計 | クエリ | アーカイブ扱い | index |
|---|---|---|---|
| トピック別累計 | `studyRecord.groupBy({ by:["topicId"], where:{ userId, topic:{ isArchived:false } }, _sum:{ countedSeconds:true } })` + 表示名のため対象 `topicId` の `Topic` を別途取得（または下記注） | **除外**（`topic:{ isArchived:false }`・リレーションフィルタ） | `@@index([userId, topicId])` |
| ヒートマップ・移動平均（横断） | `studyRecord.findMany({ where:{ userId, completedAt:{ gte: windowStart } }, select:{ completedAt:true, countedSeconds:true } })` → アプリ層で JST 日割り・ゼロ埋め・移動平均 | **含める**（`isArchived` 条件を付けない） | `@@index([userId, completedAt])`（range が効く） |
| 期限カウントダウン | `topic.findMany({ where:{ userId, isArchived:false, deadline:{ not:null } }, select:{ id,title,deadline } })` | **除外**（アーカイブ済みは表示しない） | `@@index([userId, isArchived])` |

- **トピック別累計のアーカイブ除外**: `groupBy` の `where` に `topic: { isArchived: false }`（Prisma リレーションフィルタ）を指定する。これで「アーカイブ済みトピックの StudyRecord」が累計から外れる（LAP-007 §3 / SPEC §7.4）。
  - **表示名の取得**: `groupBy` は `topicId` と `_sum` のみ返すため、トピック名が要る。`Topic.findMany({ where:{ userId, isArchived:false }, select:{ id, title } })` を別途取得し、アプリ層（純関数 §3-4 `joinTopicTotals`）で topicId をキーに突き合わせる。**累計 0 のアーカイブ外トピックも 0 として表示**できる（学習記録のないトピックを一覧から落とさない）。userId は両クエリで必須。
- **横断集計はアーカイブ条件を付けない**: ヒートマップ・移動平均は `findMany` に `isArchived` 条件を一切付けず、アーカイブ済みトピックの過去 StudyRecord も含める（SPEC §7.4・過去日の学習量欠落を防ぐ）。期間窓 `completedAt:{ gte: windowStart }` のみで絞る（§3-7）。
- **`$queryRaw` 却下理由**: §3-1 のとおり JST 日割りをアプリ層で行うため DB 側の日付式 SQL が不要。Prisma 型安全 API で全集計が表現でき、`admin/users` 以外に生 SQL を増やさない方が一貫（architect.md「新規抽象を安易に導入しない」）。

### 3-3. 集計前 materialize 接続（裁量 #3 → 決定）

**結論: 集計クエリの前に、当該ユーザーの running を `materializeIfDue(running, new Date())` で確定する。`sessions/page.tsx:108-128` と同一パターンを `dashboard/page.tsx` に置く。**

```
1. userId = await requireUserId()
2. running = prisma.studySession.findFirst({
     where:{ userId, status:"running" },
     select:{ id, userId, topicId, presetSnapshot, startedAt },
   })
3. if (running) {
     const outcome = await materializeIfDue(running, new Date())
     // due:true なら StudyRecord が新たに生成された → 後続の集計クエリがその行を拾う
   }
4. （以降）集計クエリ群を実行 → 純関数で整形 → 描画
```

- **参照系での書き込み副作用について**: ダッシュボードは読み取り画面だが、確定期限を過ぎた running を集計入口で materialize するのは LAP-010 §10 の設計意図（「再 open されないまま確定期限を過ぎたランを集計時に回収」）。`materializeIfDue` は冪等（status guard `count===1` を勝者・LAP-010 §3-3）で、`due:false`（まだ進行中）なら書き込まない。副作用は「確定漏れ 1 件の回収」に限定され、何度開いても二重生成されない。
- **materialize → 集計の順序保証**: `materializeIfDue` を `await` してから集計クエリを実行するため、同一リクエスト内で新規 StudyRecord が集計に反映される（横断集計・トピック別累計の両方）。
- **Next.js キャッシュ / revalidate の扱い**:
  - `dashboard/page.tsx` は server component で `requireUserId()`（= `auth()` で `headers()`/`cookies()` を読む）を呼ぶため **動的レンダリング**になり、`fetch` キャッシュや full-route cache に乗らない（リクエストごとに最新を集計）。Prisma クエリは Next.js Data Cache の対象外（`fetch` ではない）なので、`force-dynamic` 等の明示は不要だが、堅牢性のため `export const dynamic = "force-dynamic"` を付けてよい（implementer 裁量）。
  - **`revalidatePath` は呼ばない**: ダッシュボードは GET 表示のみで mutation を持たない。`materializeIfDue` 内部の書き込みは同一リクエストの後続クエリが直接拾うため、`revalidatePath` での再検証は不要（`sessions/page.tsx` は materialize 後に `redirect` するが、ダッシュボードは同一描画内で集計するため redirect も不要）。
- **失敗時の堅牢性**: `materializeIfDue` が稀に失敗しても集計表示自体を止めない方が UX 上望ましいが、本 MVP では LAP-010 の `materializeIfDue`（`$transaction`）の例外はそのまま伝播させる（既存 `sessions/page.tsx` と同じ挙動・特別なエラーハンドリングは追加しない）。implementer はここに try/catch を**足さない**（挙動の一貫性）。

### 3-4. 純関数の入出力契約（裁量 #4・#8 → 決定）

`src/lib/aggregate.ts` に以下の DB 非依存純関数を置く。すべて `Date`/数値/プレーン配列の入出力で、`now`/`timeZone`（既定 JST）/`windowDays` を引数注入してテストする。

```typescript
// src/lib/aggregate.ts — ダッシュボード集計の純ロジック（SPEC §7.4 / §9）。DB 非依存。

/** Asia/Tokyo 固定オフセット（DST なし・§3-1）。 */
export const JST_OFFSET_MINUTES = 9 * 60;

/** ヒートマップ・移動平均の期間窓（直近 N 日・§3-7）。 */
export const HEATMAP_WINDOW_DAYS = 90;
/** 移動平均の窓（7 日・SPEC §4/§7.4）。 */
export const MOVING_AVERAGE_WINDOW = 7;

/** UTC Date を JST 暦日キー "YYYY-MM-DD" へ変換する（§3-1）。getUTC* で読みサーバ TZ 非依存。 */
export function toJstDateKey(date: Date, offsetMinutes?: number): string;

/** JST 暦日キー "YYYY-MM-DD" を、その JST 0:00 を表す UTC Date へ戻す（期間窓の境界計算用）。 */
export function jstDateKeyToUtcStart(dateKey: string, offsetMinutes?: number): Date;

export type StudyRecordLike = { completedAt: Date; countedSeconds: number };
export type DailyTotal = { dateKey: string; totalSeconds: number };

/**
 * StudyRecord 群を JST 暦日でバケツ化し countedSeconds を合算する（§7.2 status 不問・§7.4）。
 * 日跨ぎブロックは分割せず completedAt の JST 日に丸計上する（§7.4）。
 * 戻りは dateKey 昇順。学習のある日のみを含む（ゼロ埋めは fillDailySeries が行う）。
 */
export function bucketByJstDay(
  records: ReadonlyArray<StudyRecordLike>,
  offsetMinutes?: number,
): DailyTotal[];

/**
 * 日次系列を [startKey, endKey]（両端含む・JST 暦日）で連続化し、
 * 学習ゼロの日を totalSeconds=0 で埋める（§7.4）。戻りは dateKey 昇順・欠損なし。
 * end は通常「今日（JST）」、start は end から windowDays-1 日前（§3-7）。
 */
export function fillDailySeries(
  totals: ReadonlyArray<DailyTotal>,
  startKey: string,
  endKey: string,
): DailyTotal[];

export type MovingAveragePoint = { dateKey: string; averageSeconds: number };

/**
 * ゼロ埋め済み連続日次系列に対し 7 日移動平均を算出する（§7.4・裁量 #4）。
 * - 各日 i の平均 = 直近 min(i+1, window) 日の totalSeconds 平均（後方移動平均）。
 * - 系列が window 未満の期間は存在する日数での部分平均（先頭ほど少ない日数で割る・SPEC §4）。
 * - 入力はゼロ埋め済み連続系列を前提（呼び出し側が fillDailySeries を通す）。
 * 戻りは入力と同じ長さ・同じ dateKey 順。
 */
export function movingAverage(
  series: ReadonlyArray<DailyTotal>,
  window?: number, // 既定 MOVING_AVERAGE_WINDOW(7)
): MovingAveragePoint[];

export type TopicTotalInput = { id: string; title: string }; // isArchived:false のトピック
export type TopicSum = { topicId: string; totalSeconds: number }; // groupBy 結果
export type TopicTotal = { topicId: string; title: string; totalSeconds: number };

/**
 * アーカイブ外トピック一覧と groupBy 合算を突き合わせる（§3-2）。
 * 記録のないトピックは totalSeconds=0 で含める。totalSeconds 降順 → title 昇順で安定ソート。
 */
export function joinTopicTotals(
  topics: ReadonlyArray<TopicTotalInput>,
  sums: ReadonlyArray<TopicSum>,
): TopicTotal[];

export type DeadlineInput = { id: string; title: string; deadline: Date };
export type DeadlineCountdown = {
  id: string;
  title: string;
  deadline: Date;
  daysRemaining: number; // JST 暦日差。今日=0、明日=1、昨日=-1
  isOverdue: boolean;    // daysRemaining < 0（§3-5・期限超過）
};

/**
 * 各トピックの期限日までの JST 暦日差を算出する（裁量 #5・SPEC §4/Should）。
 * daysRemaining = (deadline の JST 暦日) - (now の JST 暦日)（暦日単位の差・時刻は無視）。
 * isOverdue = daysRemaining < 0。自動アーカイブはしない（§3-5）。
 * 戻りは daysRemaining 昇順（期限が近い/超過が先頭）。
 */
export function computeDeadlineCountdowns(
  topics: ReadonlyArray<DeadlineInput>,
  now: Date,
  offsetMinutes?: number,
): DeadlineCountdown[];
```

- **暦日差の算出（カウントダウン・移動平均境界）**: `toJstDateKey` で両者を `"YYYY-MM-DD"` 化 → `jstDateKeyToUtcStart` で JST 0:00 の UTC Date 2 つに戻し → ミリ秒差を 86_400_000 で割って `Math.round`（DST なしのため除算は厳密に整数日。`round` は浮動小数誤差の保険）。時刻成分を捨てて「暦日の差」を取るのが要点（23:50→00:10 を 1 日と数える等の時刻依存を排除）。

### 3-5. カウントダウンと期限超過表示（裁量 #5 → 決定）

- カウントダウン日数 = `computeDeadlineCountdowns` の `daysRemaining`（JST 暦日差）。今日が期限なら 0、過ぎていれば負。
- **期限超過の識別表示（Should）**: `isOverdue`（`daysRemaining < 0`）のトピックを警告色（赤系のバッジ/ボーダー、`role` は付けず視覚＋テキスト「期限超過」）で識別表示する。`daysRemaining` の絶対値で「N 日超過」と表示してよい（implementer 裁量）。
- **自動アーカイブはしない**（SPEC §4 Should・LAP-007 はユーザー操作のみ）。表示のみで状態を変えない。
- 対象は **アーカイブ外（`isArchived:false`）かつ `deadline != null`** のトピックのみ。期限なしトピックはカウントダウン一覧に出さない。

### 3-6. 可視化手段（裁量 #6 → 決定）

**結論: グラフライブラリを新規導入せず、SVG/CSS（Tailwind）で自作する。** recharts 等は入れない。

**採用理由（architect.md「新規抽象/依存を安易に導入しない」制約に従う）:**
- MVP の可視化要件（ヒートマップ・折れ線/棒の移動平均・累計バー・カウントダウン）は SVG/CSS で十分表現でき、recharts（+ d3 依存群）を入れるとバンドル肥大・SSR 互換・依存追加のレビューコストが生じる。
- 既存依存は Next/React/Prisma/NextAuth/Resend のみ（package.json）。グラフ専用依存はゼロ。新規追加は強い正当化が必要だが、MVP 表示には不要。
- データ整形は純関数（§3-4）で完結し、描画は薄い presentational コンポーネントに閉じる（テスト対象は純関数側）。

**描画方針（implementer 向けガイド・詳細は裁量）:**
- **ヒートマップ**: JST 日次系列（直近 90 日）を週グリッド（GitHub 風・7 行 × 週数列）または月別グリッドで CSS グリッド表示。各セルの背景濃淡を `totalSeconds` の段階（例: 0 / ~30分 / ~1h / ~2h / 2h+ の 5 段階）で塗り分け。セルに `title`（ツールチップ）で「日付・学習時間」を付与。
- **7日移動平均**: `MovingAveragePoint[]` を SVG `<polyline>`（折れ線）で描画。x=日付、y=平均秒（分換算表示）。軸ラベルは最小限（開始日・終了日・最大値）。
- **トピック別累計**: `TopicTotal[]` を水平バー（CSS の幅 % = `totalSeconds / max`）+ 数値（時間:分）で一覧。累計 0 のトピックも 0 幅バーで表示。
- **カウントダウン**: `DeadlineCountdown[]` をカード/行リストで「トピック名・期限日・残り N 日 / N 日超過（警告色）」表示。
- すべて Tailwind・レスポンシブ（`max-w-*`・横スクロール許容のヒートマップは `overflow-x-auto`）。`dashboard/page.tsx` は既存の `LogoutButton`・ログイン情報表示を保持しつつ集計セクションを追加する。

> コンポーネント分割は implementer 裁量（`dashboard/page.tsx` 内のローカル関数コンポーネント、または `dashboard/_heatmap.tsx` 等の隣接ファイル）。純関数で整形済みのデータを props で受け取る presentational に徹し、DB/集計ロジックを描画層に持ち込まない。

### 3-7. 集計期間窓（裁量 #7 → 決定）

**結論: ヒートマップ・移動平均の期間窓は「今日（JST）を含む直近 90 日」（`HEATMAP_WINDOW_DAYS = 90`）とする。トピック別累計は全期間（窓を設けない）。**

- **窓の境界**: `endKey = toJstDateKey(now)`（今日 JST）、`startKey = endKey の 89 日前`（両端含めて 90 日）。クエリは `where:{ userId, completedAt:{ gte: jstDateKeyToUtcStart(startKey) } }`。`jstDateKeyToUtcStart` が JST 0:00 を UTC Date（= startKey 前日 15:00 UTC）に変換し、`@@index([userId, completedAt])` の range スキャンに効く（§5・§7.5）。
- **採用理由**: 90 日はヒートマップの一覧性（四半期相当）と移動平均の傾向把握に十分で、1 ユーザーの取得行数を抑え §5（2 秒以内）に収まる。7 日移動平均は窓 90 日系列の各日に対し後方 7 日平均を取る（先頭 6 日は部分平均・SPEC §4）。
- **トピック別累計は全期間**: 累計は「これまでの総学習時間」が要件（SPEC §4）。期間窓を設けず `groupBy` で全 StudyRecord（アーカイブ外トピック）を合算する。`@@index([userId, topicId])` が効き、件数は materialize 済みブロック総数（数千件規模）で §5 に収まる。
- **将来拡張**: 窓日数・移動平均窓は `aggregate.ts` の定数で一元管理し、変更時は定数のみ触る（描画/クエリは定数参照）。

### 3-8. 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| `$queryRaw` で `date(completedAt AT TIME ZONE 'Asia/Tokyo')` を GROUP BY して DB 集計 | アプリ層純関数で日割りする方がテスト容易（DB 不要）・型安全・慣習一貫。日付式が completedAt の index range を阻害する懸念。1 ユーザー直近 90 日の集約はアプリ層で §5 に収まる（§3-1） |
| `Intl.DateTimeFormat({ timeZone:"Asia/Tokyo" })` で日割り | JST は DST なしのため +9h 固定で十分かつ高速・依存最小。Intl はロケール/環境依存の懸念と単体テストの再現性で劣る（§3-1） |
| recharts / Chart.js 等のグラフライブラリ導入 | MVP 表示は SVG/CSS で充足。依存追加（バンドル肥大・SSR 互換・レビューコスト）は architect.md 制約に反する強い正当化が必要だが不在（§3-6） |
| トピック別累計に期間窓を設ける | 累計は「総学習時間」が要件（SPEC §4）。窓は要件外（§3-7） |
| 横断集計でアーカイブ済みを除外 | SPEC §7.4 が「横断集計はアーカイブ済みの過去記録も含める」と明記。除外すると過去日の学習量が欠落（§3-2） |
| 集計入口で materialize しない | 再 open されないまま確定期限を過ぎた running の確定が漏れ、集計に反映されない（LAP-010 §10 申し送り違反・§3-3） |
| 移動平均を「学習のある日のみ」で算出（ゼロ埋めしない） | SPEC §7.4 が「学習ゼロの日も 0 として埋めた上で 7 日窓」と明記。ゼロ埋めしないと平均が過大表示される（§3-4） |
| 期限超過トピックを自動アーカイブ | SPEC §4 Should「自動アーカイブはせず、判断はユーザーに委ねる」。表示のみ（§3-5） |

**処理フロー（`dashboard/page.tsx`・server component）:**
```
1. userId = await requireUserId()                          // 二層防御（edge + node）
2. now = new Date()
3. running = findFirst({ where:{userId,status:"running"}, select:{id,userId,topicId,presetSnapshot,startedAt} })
   if (running) await materializeIfDue(running, now)        // 集計入口の確定漏れ回収（§3-3）
4. 集計クエリ（すべて userId 必須・§3-2）:
   a. topicSums = studyRecord.groupBy({ by:["topicId"], where:{ userId, topic:{isArchived:false} },
                    _sum:{ countedSeconds:true } })
   b. activeTopics = topic.findMany({ where:{ userId, isArchived:false },
                       select:{ id, title } })
   c. endKey   = toJstDateKey(now)
      startKey = （endKey の HEATMAP_WINDOW_DAYS-1 日前。jstDateKeyToUtcStart で日付計算）
      records  = studyRecord.findMany({ where:{ userId, completedAt:{ gte: jstDateKeyToUtcStart(startKey) } },
                   select:{ completedAt:true, countedSeconds:true } })   // アーカイブ含む（§3-2）
   d. deadlineTopics = topic.findMany({ where:{ userId, isArchived:false, deadline:{ not:null } },
                         select:{ id, title, deadline:true } })
5. 純関数整形（§3-4）:
   - topicTotals = joinTopicTotals(activeTopics, topicSums→{topicId,totalSeconds})
   - daily       = fillDailySeries(bucketByJstDay(records), startKey, endKey)
   - ma          = movingAverage(daily)                    // 7日・ゼロ埋め前提
   - countdowns  = computeDeadlineCountdowns(deadlineTopics(deadline 非null), now)
6. 描画（SVG/CSS・§3-6）: ヒートマップ(daily) / 折れ線(ma) / 累計バー(topicTotals) /
   カウントダウン(countdowns・期限超過は警告色)。既存のログイン情報・LogoutButton は保持。
```
> `topic.deadline` は nullable のため、(d) で `deadline:{ not:null }` で絞った上で `computeDeadlineCountdowns` には `deadline:Date`（非 null）を渡す（型を `Date` に narrow）。

**処理フロー（純関数・§3-4 の補足アルゴリズム）:**
```
toJstDateKey(date): new Date(date.getTime()+9h) を getUTC* で "YYYY-MM-DD" 化
jstDateKeyToUtcStart(key): key の JST 0:00 = UTC で key の前日 15:00 → new Date(Date.UTC(y,m-1,d) - 9h)
bucketByJstDay: Map<dateKey, sum> に countedSeconds 合算 → dateKey 昇順配列
fillDailySeries(totals,start,end): start..end を 1 日刻みで走査し、無い日は 0 で埋める
movingAverage(series,w): 各 i で series[max(0,i-w+1)..i] の totalSeconds 平均（部分平均は実日数で割る）
joinTopicTotals(topics,sums): sums を Map 化 → topics 各々に total（無ければ 0）→ total desc, title asc ソート
computeDeadlineCountdowns(topics,now): days = (deadlineKey - nowKey) 暦日差 → isOverdue=days<0 → days asc ソート
```

|---|---|---|
| T-TZ-MIDDAY | `toJstDateKey(2026-06-22T03:00:00Z)`（JST 12:00） | `"2026-06-22"` |

| T-TZ-YEAR | `toJstDateKey(2026-12-31T15:00:00Z)` | `"2027-01-01"`（年跨ぎ） |

## 10. Open Questions

なし。investigator の積み残し Unknowns はなく、architect 裁量事項（#1〜#8）はすべて本設計で結論済み（§3-1〜§3-8）。後続への申し送りのみ:

- **期間窓・移動平均窓は `aggregate.ts` の定数で一元管理**（`HEATMAP_WINDOW_DAYS=90` / `MOVING_AVERAGE_WINDOW=7`）。将来 UI で期間切替を足す場合は定数を引数化する（本 MVP では固定）。

- **集計の DB 側移行**（性能逼迫時に `groupBy`/日割りを SQL へ）は本 MVP では不要（§3-1/§5）。純関数を残したまま I/O 層のみ差し替え可能な分離にしてある。
